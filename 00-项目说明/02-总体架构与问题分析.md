## 第 1 章：全项目 Workflow 架构总览

全项目数据流：

```text
原始文献层
  04-项目文献/A-原著原典/*.md
  04-项目文献/D-标注/*.docx
  05-归档文献/*
    ↓
文本规范化层
  markdown_preprocess.py
  docx_to_full_json / run.py
    ↓
passage 层
  passages.jsonl
  inline_notes.jsonl
  title_anomalies.jsonl
    ↓
候选层
  parser v2 -> parsed_items / candidate_items / skipped_items
  AI input builder -> ai_input_json
    ↓
AI 草稿层
  model -> ai_output_json
  validate_ai_json -> db_import_json
    ↓
人工标注层
  annotations.db
  annotation_case JSON
  human_review
  gold cases / benchmark
    ↓
主库层
  main.db / dictionary.db v2
  passages / cases / term_relations / evidences / terms / method tables
    ↓
网站展示层
  sqlite snapshot
  view_config.json
  case detail / passage detail / knowledge page / benchmark dashboard
```

关键原则：

| 原则 | 含义 |
| --- | --- |
| 先 passage，后 case | 没有可定位原文，就不要扩大结构化案例 |
| AI 只做草稿 | AI 输出必须经过 quote、schema、枚举和人工审校 |
| 关系和方法分开 | `term_relations` 写"证明了什么"；`method_profile` 写"怎么证明" |
| 三库并行 | `candidate.db` 可重建，`annotations.db` 管审校，`main.db` 管长期展示 |
| JSON 分层 | full/source、ai_input、ai_output、db_import、annotation_case 不混用 |
| 网站配置驱动 | 前端展示依赖 schema 和 field registry，不提前写死所有字段 |

### 三个数据库边界

| 数据库 | 责任 | 可删除重建吗 | 是否直接展示 |
| --- | --- | --- | --- |
| `candidate.db` / `workspace.db` | passage preview、标题异常、parser 候选、AI 运行记录 | 可以反复重建 | 默认不直接展示 |
| `annotations.db` | 人工标注、五步、AI 草稿、人工审校、gold cases | 不应随意重建 | 可展示审校状态和标注案例 |
| `main.db` / `dictionary.db v2` | 长期主库、网站索引、已整理案例、terms 重组结果 | 不应随意重建 | 是网站主展示来源 |

数据流：

```text
candidate.db -> annotations.db -> main.db -> website snapshot
```

不建议从旧 `terms` 反推 case。新主库的字词应从已整理案例和 `term_occurrences` 反向生成。

> Parser 纯机器方案（五步）和 AI 辅助方案（四阶段）的完整设计见 [§3.1](#31-parser-v2候选生成--风险标记--损耗审计)。

### 2.2 `source.txt` 与 Markdown：谁是长期主输入

旧主库直接来源是 `02-数据库/main/source.txt`，链路是 `source.txt -> parser.py -> importer.py -> dictionary.db -> sqlite_bridge.py -> sqlite-snapshot.json`。`source.txt` 可继续作为旧 parser 的兼容输入，但长期主输入应转向四部 Markdown——它们有标题层级、段落、小字信息和更接近阅读本的结构，适合建 passage。旧 `source.txt` 行号不可作为通用定位，且不能覆盖《经义述闻》《经传释词》《读书杂志》的结构化原文层。

风险：不能把旧 parser 的 `SOURCE_FILE` 直接替换为 Markdown。实测数据清楚说明了这点：`source.txt` 可得 7166 个 parsed terms、832 个词头组、4101 条 skipped；直接读 `广雅疏证_王念孙.md` 只得 6010 个 parsed terms、784 个词头组、5166 条 skipped。旧 parser 对 `<small>`、标题、空行和脚注没有预处理，导致小字标签、标题、脚注、空行共同增加误判。

正确做法是新建 Markdown 解析管线：先把 `<small>` 解析成结构化 inline note，保留 `raw_text` 和 `plain_text` 两版；再按标题路径切 passage；最后在 passage 内识别词头、训义、证据和小字角色。

关于页码：四份 A 类 Markdown 并不稳定支持页码。`广雅疏证` 页码命中极少，`经义述闻` 基本没有页码，`经传释词` 很少，`读书杂志` 有少量但不统一。Markdown 的优势不是页码，而是标题路径、段落、行号、小字和可计算 hash。

### 2.3 四份 Markdown 结构与标题重建

**问题**：四份 Markdown 是否能统一为三级标题，自动重建是否可靠，如何处理 `经传释词` 卷名混在 H3 等异常。

**现状**：四份 Markdown 总体相似——都有一个 H1 文件名，正文主要靠 H2/H3——但没有明示"章/节/条"的严格结构。真实差异：

| 作品 | H1 | H2 | H3 | 特点 |
| --- | --- | --- | --- | --- |
| 广雅疏证 | 1 | 13 | 426 | H2 常见序、表、卷；H3 可为篇名或词群条目 |
| 经义述闻 | 1 | 33 | 2317 | H2 常见卷；H3 多为案例题名 |
| 经传释词 | 1 | 0 | 160 | 无 H2，需要从卷名 H3 合成 section |
| 读书杂志 | 1 | 515 | 4955 | H2 常见目标书和卷；H3 多为条目题名 |

**分析**：自动化重建三级标题可作为工程路线，但不能假设"四书标题语义完全一致"。更准确的说法是：统一成三级定位路径，而不是统一成同一种学术目录。另外，四份 Markdown 基本没有统一页码；没有稳定 passage id；没有显式区分"卷、篇、条、序跋、整理说明"的机器字段；H1 只是文件名；部分标题含 `<small>` 或长词群，需要先清洗再做 id。

**建议**：

```text
work_title = 文件名、H1 或人工映射
section_title = H2；若无 H2，则由卷名 H3、序跋标记或 default_section 合成
entry_title = H3 中非卷名、非序跋、非编辑说明的标题
entry_kind = preface / section / volume / term_group / case_title / function_word / editorial / unknown
```

异常处理：

| 异常 | 处理 |
| --- | --- |
| `经传释词` 没有稳定 H2 | 从 H3 中识别卷名（如 `### 卷二卷二` → `section_title=卷二`），生成 synthetic section；词条 H3 仍做 entry |
| H3 既可能是卷名又可能是条目 | 用标题模式、相邻段落长度、是否含"卷"字判断；无法判断则 `entry_kind=unknown` |
| 序、表、凡例、编辑说明混入 | `entry_kind=preface/editorial`，不进入 parser 候选抽取 |
| H1 缺失或只是文件名 | 用文件名映射 `work_title` |
| 标题路径异常 | 输出到 `title_anomalies.jsonl`，人工抽检 |


数据清洗按以下顺序执行：

1. **去掉转换说明**——识别并移除文件开头的转换说明 blockquote，原文存入 `source_note`。
2. **标题清洗**——移除标题中的 Markdown `#` 前缀；移除 `<small>` 标签但将其内文字保留到 `inline_notes`；压缩多余空白，生成 `clean_title`。
3. **标题分类**——H1 → `work_title`；H2 → `section_title`；H3 → `entry_title`。`经传释词` 缺 H2 时，从 H3 中识别卷名合成 `section_title`。
4. **条目类型初判**——为每个 entry 标记 `entry_kind`（preface / section / volume / term_group / case_title / function_word / editorial / unknown），仅辅助，不影响后续 passage 切分。
5. **正文清洗**——生成三个版本：`raw_text`（保留原始转写）、`plain_text`（去 HTML 标签保留文字）、`normalized_text`（空白归一）；完善 `inline_notes[]`。
6. **生成 passage id**——组合 `work_key + title_path_slug + local_ordinal` 生成可读 id；对 raw_text 和 normalized_text 分别计算 sha256 作为漂移校验指纹。

第一版标准不是"目录学上完全准确"，而是 passage 能稳定定位：同一段原文能通过 `work_title + section_title + entry_title + local_ordinal + hash` 回找。

### 2.4 `<small>` 标签处理

**问题**：去掉 `<small>` 后是否还能审计来源，是否有必要保留标签。

**现状与数据**：`<small>` 标签本身不是原典正文的一部分，但标签里的文字有信息价值。真实数据：`广雅疏证` 小字约 5797 处（含"反"约 300 处，2 字以内约 4236 处，校勘相关约 445 处）；`经义述闻` 约 4718 处（校勘相关约 534 处）；`读书杂志` 约 5230 处（校勘相关约 815 处）；`经传释词` 基本没有小字。内容包括反切/音注、校勘说明、补正和整理标记。对照 DOCX 可知 `<small>` 来自 Word 小字号 run。

**分析**：长期正本不需要保留 HTML 标签。真正有价值的是"这段文字是否小字/注记/整理说明"这一元信息。`<small>` 是转换格式，不是训诂语义；继续作为正文标签会干扰 parser、检索、quote 校验和前端展示。但内容删掉又会丢反切、音注、校勘。折中方案是正文去标签、内容同权，来源信息进 `inline_notes[]`。

**建议**：采用三份材料：

| 材料 | 作用 |
| --- | --- |
| 原始 DOCX / 原始 Markdown | 归档，不改，保留 small、版式、小字等原貌 |
| 工作 Markdown | 标题重建、去掉 `<small>` 标签、保留标签内文字，供 parser 和 passage 构建 |
| passage JSON | 记录 `source_file_sha256`、`archive_file_ref`、`inline_notes[]` |

数据形态：

| 层 | `<small>` 处理 | 用途 |
| --- | --- | --- |
| 原始归档 Markdown | 保留 `<small>`；若已完全去标签，依赖 DOCX 追溯 | 追溯转换结果 |
| 规范化 passage | 去掉标签，小字内容同权并入正文 | `plain_text` 用于 parser、检索、quote 校验 |
| 小字结构表 | `inline_notes[]` 记录内容、位置、类型、置信度 | 来源审计 |
| 网站展示 | 默认同权展示，需要时可打开来源提示 | 不让格式差异干扰阅读 |

`inline_notes` 最小字段：

```json
{
  "note_id": "gy_sz_000001",
  "passage_id": "...",
  "text": "戶瓜反",
  "start_char": 42,
  "end_char": 45,
  "note_type": "fanqie",
  "source_marker": "docx_small_run",
  "confidence": "rule_high"
}
```

`note_type` 初始范围：`fanqie`、`phonetic_note`、`variant_or_collation`、`supplement`、`editorial_note`、`plain_note`、`unknown`。没有 small 归档也不阻塞 parser，只是来源审计能力下降。

### 2.5 Passage 定位

页码不统一，不能作为主定位键。行号只适合当前文件快速跳转，不具备跨版本稳定性。passage 是当前最优先补齐的主库缺口——没有 passage，terms、cases、evidences 都无法稳定回到原文。

通用定位采用多重锚：`work_key + title_path + local_ordinal + raw_text_sha256 + normalized_text_sha256 + quote_exact + quote_offset`。

| 中文字段 | 英文字段 | 作用 | 例子 |
| --- | --- | --- | --- |
| 作品键 | `work_key` | 哪部书 | `guangya_shuzheng` |
| 标题路径 | `title_path` | 人能读懂的位置 | `廣雅疏證卷第一上 > 釋詁` |
| 局部序号 | `local_ordinal` | 同一标题下第几段 | 1 |
| Markdown 行号 | `md_line_start/md_line_end` | 当前文件快速定位 | 55-75 |
| 原文 | `raw_text` | 保留 `<small>` 等原始转写 | |
| 纯文本 | `plain_text` / `normalized_text` | 去标签后便于检索 | |
| 内容指纹 | `raw_text_sha256` | 判断文本是否变过 | |
| 引文锚 | `quote_exact/quote_offset/quote_sha256` | case/evidence 指向 passage 内具体句子 | |

标题路径粗定位，局部序号保证段落顺序，hash 发现文本漂移，quote 和 offset 精确定位证据。行号保留但只作本地跳转，不作学术定位主键。

以 `广雅疏证`"古、昔、先……始也"为例：

```json
{
  "work_key": "guangya_shuzheng",
  "title_path": ["廣雅疏證卷第一上", "釋詁"],
  "local_ordinal": 1,
  "md_line_start": 55,
  "md_line_end": 75,
  "raw_text": "古、昔、先、創、方、作、造、朔、萌、芽、本、根、櫱、鼃、 <small>戶瓜反</small> 䔞、 <small>律</small> 昌、孟、鼻、業，始也。...",
  "plain_text": "古、昔、先、創、方、作、造、朔、萌、芽、本、根、櫱、鼃、戶瓜反 䔞、律 昌、孟、鼻、業，始也。...",
  "raw_text_sha256": "..."
}
```

evidence 不只保存 quote，还保存 `passage_id`、`quote_exact`、`quote_start_char`、`quote_end_char`、`quote_sha256`。以后行号变了，只要标题路径和 quote/hash 能匹配，仍能找回原文。

## 第 3 章：Passage → Candidate 层（Parser）

### 3.1 Parser v2：候选生成 + 风险标记 + 损耗审计

旧 parser 主要围绕《广雅疏证》识别"若干词头，某义也"的词群条目，不是完整训诂 parser。问题包括：不该摘的被摘入、该摘的被跳过、证据被错误归属、case 被模板包装成确定结论。

解决方案不是只改正则，而是改为"候选生成 + 风险标记 + 可审计跳过"。输出分 `parsed_items`、`candidate_items`、`skipped_items`，并为每项记录 `rule_hits`、`risk_flags`、`skipped_reason`。不能把旧 parser 的 `SOURCE_FILE` 直接改成 Markdown——那会把标题、`<small>`、序跋、转换说明、空行都混进旧正则逻辑，得到更多 skipped 和更多假阳。正确次序是先 `markdown_preprocess`，再 `passage_builder`，最后才是 `candidate_extractor`。

纯机器方案分五步：

| 步骤 | 目标 | 具体做法 |
| --- | --- | --- |
| Markdown 预处理 | 把 md 变成可解析文本 | 解析标题、段落、`<small>`、脚注；生成 raw_text/plain_text/inline_notes |
| passage 切分 | 先定位，不解释 | 按 work > 卷 > 篇/条 > 段落序号切块，记录行号和 hash |
| candidate 抽取 | 给出候选，不直接定稿 | 识别词头行、训义、引用书名、补正、校勘、反切、小字角色；输出置信度和命中规则 |
| rule_auditor | 机器自动标记风险 | 对每个候选写 rule_hits、risk_flags、skipped_reason，区分假阳风险和假阴风险 |
| human_preview | 人工抽检高风险项 | 把高风险候选和 skipped 列给人看，不直接写成确定 case；确认通过后进入 AI 辅助复核 |

机器方案的重点是"可解释的候选"。例如一个词头行可以带风险标记：`has_small_tags=true`、`gloss_single_char=true`、`has_multiple_books=true`、`shared_body=true`、`possible_collapsed_terms=true`。这样即使抽错，也能知道为什么错。

以上五步是流水线关系——每步的输出是下一步的输入。机器方案产出 `candidate_items` 和 `skipped_items` 后，AI 辅助方案接手进行语义复核：机器第三步（candidate 抽取）的输出作为 AI 第一阶段（候选复核）的输入，机器第四步（rule_auditor）中的 skipped 项作为 AI 第四阶段（异常解释）的输入。

AI 辅助方案分四阶段：

| 阶段 | AI 输入 | AI 输出 | 审计要求 |
| --- | --- | --- | --- |
| 候选复核 | 单个 passage + 机器候选 | 判断是否为词头/校勘/补正/证据 | quote 必须原文子串 |
| 关系抽取 | passage + term candidates | 原字/训字/校正字关系 | 必须给 source span |
| 五步草稿 | 已确认 case + evidence | 发疑、设问、取证、释理、结论草稿 | 允许缺项，不许硬凑 |
| 异常解释 | skipped 或低置信候选 | 为什么难判、建议人工看什么 | 只作审校提示 |

纯机器方案负责"稳定、可复现、可批量"；AI 辅助方案负责"复杂语义、关系初判、五步草稿"。二者共同原则：AI 输出永远是候选或草稿，不能自动覆盖主库。

### 3.2 旧 parser / importer 的处置

当前 `importer.py` 把 parser 结果包装成 `terms/cases/evidences/works`。`cases` 高度模板化——每个字段的问题都很明确：

| 字段 | 当前值 | 来源 | 问题 |
| --- | --- | --- | --- |
| `title` | `广雅疏证「X也」词条群（行N）` | importer 模板 | 不是原文标题 |
| `problem` | `疏通「X也」诸字之义例、声训、通假、书证` | importer 模板 | 不是逐案疑点 |
| `method` | `声训、通假、书证、义证、语法对文` | importer 固定字符串 | 不是逐案识别 |
| `conclusion` | `以上诸字均有「X」义...` | importer 模板 | 不是人工结论 |
| `certainty` | 全部"确定" | importer 固定 | 不可信 |
| `status` | 全部"草稿" | importer 固定 | 只说明未审校 |
| `process_text` | 空 | 未生成 | 没有五步过程 |

`certainty=确定` 和 `status=草稿` 的组合尤其容易误导。

取舍结论：主库不继续扩展这种模板 case。旧数据保留为展示线索；新主库 v2 保存裸原文结构化和候选索引，不应再把 case 包装成模板研究结论。五步推理放入人工库。

## 第 4 章：核心字段设计

### 4.1 `term_relations` 与 `method_profile` 的分离

**问题**：`relation_type`、`method_concepts`、`method_expressions` 三个字段容易让人觉得都在说"训诂方法"。关键问题是：`relation_type` 能不能被双层方法词表替代？

**分析**：不能。方法回答"怎么证明"，关系回答"证明了什么"。例如同样使用书证和义证，一个案例可能证明"通假"，另一个可能证明"误字"，第三个可能证明"虚词用法"。如果没有关系字段，后续无法稳定检索。`relation_type` 不是方法字段，而是案例结论字段。

另外，`term_type`（字/词/短语的粒度）实际价值低，从核心 schema 中摒弃。`category` 容易成为第三套模糊分类（既像关系，又像方法，又像页面栏目），降级为可选——用 `relation_type` 和 `method_profile.concepts` 生成页面分组即可，人工不必直接填写。

**建议**：最终保留两个核心块：

| 用户看到的块 | 数据字段 | 含义 | 是否必填 |
| --- | --- | --- | --- |
| 字词关系 / 训释关系 | `term_relations[]`，内部含 `source_term`、`target_term`、`relation_type`、`relation_subtype` | 说明 A 与 B 的结论关系，即"证明了什么" | 必填基础项 |
| 方法画像 / 论证方法 | `method_profile`，内部含 `concepts[]`、`expressions[]` | 说明二王怎样证明，以及可归入哪些现代方法概念，即"怎么证明" | AI 可生成，审校确认 |

最小结构：

```json
{
  "term_relations": [
    {
      "source_term": "造",
      "target_term": "相比次",
      "relation_type": "训释",
      "relation_subtype": "声转释义"
    }
  ],
  "method_profile": {
    "concepts": ["声训", "书证", "义证", "旧注辨驳"],
    "expressions": [
      {"quote": "造之言曹", "passage_id": "..."},
      {"quote": "造、次一声之转", "passage_id": "..."}
    ]
  }
}
```

核心字段总结：

| 字段 | 反映什么 | 以"造舟于河"为例 | 是否核心 |
| --- | --- | --- | --- |
| `term_type` | 对象形态 | `造` 是字，`造舟` 是词组 | 摒弃 |
| `category` | case 或义项的粗类别 | 训释案例、校释案例 | 可生成/可选 |
| `relation_type` + `relation_subtype` | 原文对象与训释对象之间的关系 | `造 -> 相比次`，训释/声转释义 | 核心 |
| `method_profile` | 得出该关系时使用的证据和方法 | 声训、书证、义证、旧注辨驳、比较互证 | 核心 |

`relation_type` 是结论，`method_profile` 是方法。二者不能合并——一个 case 可以有一个主要关系，但使用多个方法证明它。若合并，数据会无法表达"同一结论由多种方法支持"。

### 4.2 `relation_type` 二级分类

**问题**：`relation_type` 候选关系很多（训释、同义、反训、声转释义、通假、异体、古今字、误字、当作、衍文、脱文、倒文、虚词用法、句义解释等），它们不在同一层级。如果做成 `relation_type[]`，同一个关系可能同时挂多个标签，主分类不清。

**分析**：第一版不建议用 `relation_type[]`。数组看似灵活，但会让"主关系"消失——比如同时填 `["校勘", "误字", "当作"]`，校勘是大类，误字/当作是细项，混在数组里查询和统计会很乱。更稳的方案是一个关系行只保留一个主关系，多个独立关系写多条 `term_relations[]`。

**建议**：使用 `relation_type + relation_subtype`。

| 一级 `relation_type` | 二级 `relation_subtype` 候选 | 用途 |
| --- | --- | --- |
| `训释` | 同义、反训、声转释义、义界 | A 被解释为 B |
| `校勘` | 误字、当作、衍文、脱文、倒文 | A 应改作 B，或文本有讹脱衍倒 |
| `字际关系` | 通假、异体、古今字 | A 与 B 是字形、字音、用字关系 |
| `虚词用法` | 语气、连词、介词、代词、助词 | A 是虚词，其功能被说明 |
| `句义解释` | 句读、语法、上下文解释 | 重点不是单字 A->B，而是整句文义 |
| `未定` | 待核、疑似多类 | 暂时不能判断 |

表单上成员只必填一级；二级可由 AI 建议、审校确认。

> 早期讨论中曾使用扁平枚举（`训释`、`通假`、`异体`……等 14 项），已由上述二级结构替代。这些枚举成员仍可作为候选池参考。

### 4.3 双层方法词表

**问题**：`训诂术语.md` 能不能直接作为现代方法词表？王宁《训诂学原理（增补本）》是否足够作为唯一权威来源？

**分析**：王宁《训诂学原理》很重要，但不宜作为唯一词表。它的价值在于提供理论骨架和术语层级意识，书中也强调旧术语常有定义不严、层级混杂的问题。`训诂术语.md` 可作为第一批候选词，王宁可作为理论校准来源，二王四书中的真实表达才是项目自己的证据来源。该文件本身没有列出参考书目或出处说明，不能当作有明确来源的权威词表。

**建议**：双层词表服务于 `method_profile`，不替代 `relation_type`。

| 层 | 字段 | 来源 | 作用 |
| --- | --- | --- | --- |
| 现代方法概念 | `method_profile.concepts[]` | `训诂术语.md`、王宁《训诂学原理》、课程大纲、后续人工审定 | 统一检索和展示 |
| 二王原文表达 | `method_profile.expressions[]` | 二王四书 passage 原文 | 保留二王实际说法 |

第一版可以把 `训诂术语.md` 导入为候选级概念，每个概念增加 `source_ref`、`definition`、`review_status=pending`。最终升级为 `approved` 的词，必须能挂接至少一个二王案例。

数据库实现上，二王术语与现代术语的连接需要多级结构：现代规范层（`method_concepts` 表）、二王表达层（`method_expressions` 表）、映射层（`method_expression_links`，一个概念可挂多个表达，反之亦然，标置信度）、案例使用层（`case_method_links`，记录某 case 实际用了哪些方法，证据来自哪个 passage）。

### 4.4 `core_meaning` 的替代方案

旧 `terms.core_meaning` 把第一次导入摘要当成核心释义，容易丢掉多义、多 case 和审校状态。新方案：不要把它作为人工写死字段。全部出现进入 `term_occurrences`；核心释义用 `term_core_profiles` 记录代表性 `primary_occurrence_ids`、`primary_case_ids` 和可生成摘要。

```text
terms(id, normalized_term)
cases(id, title, review_status)
term_occurrences(id, term_id, passage_id, case_id, surface_form, role, quote, gloss, relation_type, method_profile, review_status)
term_core_profiles(term_id, primary_occurrence_ids, primary_case_ids, generated_summary, generated_from_hash, generated_at)
```

页面显示"核心释义"时，从已审校 occurrences 中选代表性义项，按频次、可信度、作品来源生成摘要；未审校材料只参与检索，不参与权威释义。最小版本可以不生成自然语言摘要，只显示"已审校 case id 列表 + 代表 quote"。

### 4.5 works 引用映射

旧 `works` 主要来自预设书名和篇名映射（`CANONICAL_WORK_NAMES` 和 `_CHAP_TO_WORK`），不是动态从原文完整统计。它有粗粒度浏览价值，但不能证明精确出处。

新方案是"规范作品表 + 动态候选 + 原标签保留"。遇到 `皋陶謨` 这类篇名时，同时保存：`raw_work_label='皋陶謨'`、`normalized_work='尚书'`、`chapter_or_section='皋陶謨'`、`mapping_rule='chapter_to_work'`、`confidence='high/medium/low'`。不能只保留映射后结果。未知作品进入候选，等待人工合并。

## 第 5 章：Candidate → AI 草稿层

### 5.1 AI 检索场景与本地工具桥

项目会有多处 AI，不同场景的检索目标不同，不能混成一个"RAG"。至少有四类：

| 场景 | 何时检索 | 检索对象 | 输出 |
| --- | --- | --- | --- |
| DOCX 标注整理 | full_json 生成后 | 当前 DOCX 段落、批注、锚点；必要时查 passage | `ai_output_json` 草稿 |
| parser 候选审核 | parser 生成 candidate 后 | candidate 所在 passage、相邻 passage、方法词表 | 是否候选成立、关系和方法建议 |
| 人工标注辅助 | 成员选定 case 后 | 原文 passage、已有 gold cases、二王表达词表 | 五步草稿、证据核对提示 |
| 网站/智能体问答 | 用户在线提问时 | 已审校案例、passages、method_concepts；默认不查未审校草稿 | 可解释回答和引用 |

线上线下不同：线下工具可以访问本地全量文件；线上网站应只访问已发布快照或服务端索引。第一版先做线下 AI：`search_passages -> build_ai_input_json -> model -> validate_ai_json`。

当前 AI 链路（DOCX 转 full_json → slim 输入 → DeepSeek → ai_json → annotations.db）的问题是 AI 没有真正查询四部 Markdown、主库或方法说明。API 模型不能直接读本地文件，可行方案是本地工具桥——本地程序注册 `search_passages`、`get_passage`、`validate_quote`、`get_method_vocab` 等函数，模型返回工具调用意图，本地执行查询后只把必要片段返回模型。具体流程：

1. 本地启动 `annotation_agent.py`，注册检索函数。
2. 程序把用户任务和工具 schema 发给模型。
3. 模型返回工具调用，本地执行查询，只返回 top-k passage。
4. 模型基于片段生成 `ai_output_json`。
5. 本地校验 quote、passage_id、枚举、hash、五步完整性。
6. 通过者进入人工审核队列；失败者只保留日志。

这条路在 10000 元预算内可行，主要花开发时间和少量 API 费用。所有 AI 检索都必须返回 `passage_id` 和 quote，不能只返回自然语言解释。

### 5.2 JSON 四层体系

AI 相关 JSON 分四层，每层职责单一：

| JSON | 任务定位 | 应保留 | 可省略 | 谁用 |
| --- | --- | --- | --- | --- |
| `source_json/full_json` | 档案层：完整保存 DOCX/Markdown 抽取结果 | 段落、批注、锚点、表格、notes、run、checksum、package_inventory | 不省略 | 工程与审计 |
| `ai_input_json` | 任务包：只放本次 AI 需要看的材料 | source_file、doc_type、非空段落、批注、anchor_text、受控词表、必要 passage id | package_inventory、run 格式、checksum、空段落 | 模型调用 |
| `ai_output_json` | 草稿层：保存模型输出 | cases、term links、evidence、五步、来源索引、置信度 | 不应包含无法追溯的自由发挥 | 机器审计和人工复核 |
| `db_import_json` | 入库层：校验通过后的数据包 | 已校验字段、raw_ai_json、raw_full_json_ref、review 状态 | 不直接导入未校验结论 | importer |

AI 输出不能直接入库，必须通过 quote 子串、passage_id、hash、枚举、五步字段、relation_type、method_profile、human_review 等校验。

### 5.3 DeepSeek 配置

当前 `run.py` 配置：`DEEPSEEK_URL = https://api.deepseek.com/chat/completions`，`DEFAULT_MODEL = deepseek-v4-flash`，`CURRENT_MAX_TOKENS = 8192`，`temperature=0`，`response_format=json_object`。

推荐配置（保守）：

```python
client_base_url = "https://api.deepseek.com"
model = os.getenv("DEEPSEEK_MODEL", "deepseek-v4-flash")
temperature = 0
max_tokens = 4096  # 单 case 草稿默认够用；长案例再升到 8192
response_format = {"type": "json_object"}
timeout_seconds = 60
retry = {"max_attempts": 3, "backoff": "exponential"}
log_fields = ["model", "prompt_version", "schema_version", "usage", "latency_ms", "input_sha256", "output_sha256"]
```

上线前需核对模型名是否仍可用。无论模型是否支持 JSON mode 或 tool calls，本地都必须做 `json.loads()` 和 schema 校验。注意：官方 Tool Calls 文档说明函数能力由用户侧提供，模型只返回工具调用意图——本地文件查询必须由程序执行，模型不能自己读硬盘。

### 5.4 字段命名与 certainty/status 区分

审计字段统一为两个对象：`machine_result`（parser/AI 的候选结果）和 `human_review`（人工审计结果）。人员字段使用 `submitted_by`（提交者/标注者）、`reviewed_by`（审校者），避免使用 `author`（容易和王念孙、王引之、原书作者混淆）。

命名规则：全项目统一使用 `machine_result` 和 `human_review`。不再区分 JSON/API 层和 SQL 层命名；即使数据库中保存的是 JSON 文本，也仍使用同名字段，由 schema、字段类型或注释说明存储形态。不要再使用 `machine_draft_json`、`machine_result_json`、`human_review_json`。

`certainty` 和 `status` 不冲突：`certainty` 是学术可信度（确定、较可靠、存疑、待核），`status` 是工作流状态（草稿、待复核、已审校、已发布）。一个案例可以 `certainty=较可靠` 且 `status=草稿`（证据较强但尚未审校），也可以 `certainty=待核` 且 `status=已审校`（审校者确认存疑）。

`status` 使用一个全局小枚举：`pending` / `draft` / `approved` / `rejected` / `uncertain`。所有 `status` / `review_status` 字段都从这五个值中取子集，不再另造同义值。

| 字段 | 枚举值 | 含义 |
| --- | --- | --- |
| `machine_result.status` | `pending` / `draft` / `approved` / `rejected` | 未运行或待生成 / 已生成草稿 / 机器校验通过 / 机器校验失败 |
| `human_review.status` | `pending` / `approved` / `rejected` / `uncertain` | 待审 / 通过 / 退回或拒绝 / 存疑 |
| SQL `review_status` | `pending` / `approved` / `rejected` / `uncertain` | 可查询的人工审校汇总状态 |
| `method_concepts.review_status` | `pending` / `approved` / `rejected` | 候选待审 / 已审定 / 不采用 |

`machine_result` 和 `human_review` 的完整字段结构见 [§6.1 完整模板](#61-标注字段与最小填写要求)，此处不重复。

## 第 6 章：人工标注层

### 6.1 标注字段与最小填写要求

**问题**：人工库字段多，成员不可能每次完整填写。需要明确"最小 case"是什么，哪些由成员填、哪些由机器补、哪些由审校确认。

**分析**：字段多可以接受，但必须分角色。成员初标只需提供最关键的人类判断；机器可以补 passage_id、quote hash、候选方法；审校者确认关系、方法和可信度。

**建议**：

| 层级-谁填 | 中文 | 英文字段 | 填写要求 |
| --- | --- | --- | --- |
| 必填-成员 | 案例标题 | `case_title` | 能识别案例即可 |
| 必填-成员 | 二王出处 | `source_work` | 例如《经义述闻》 |
| 必填-成员 | 被考据作品 | `target_work` | 例如《左传》 |
| 必填-成员 | 被考据原文 | `target_text` | 例如"造舟于河" |
| 必填-成员 | 原文对象 | `term_relations[].source_term` | 被解释、被校的字词 |
| 必填-成员 | 训释/校正对象 | `term_relations[].target_term` | 解释后、校正后的字词或义项 |
| 必填-成员 | 结论 | `conclusion` | 一句话说明本案结论 |
| 推荐-成员/AI | 发疑 | `problem_discovery` | 为什么这里有问题 |
| 推荐-成员/AI | 设问 | `research_question` | 本案要解决什么问题 |
| 推荐-成员/AI | 取证 | `evidence_collection` | 用了哪些证据 |
| 推荐-成员/AI | 释理 | `reasoning` | 证据如何推出结论 |
| 机器补-程序 | passage id | `source_passage_id`、`evidences[].passage_id` | 由检索和 quote 校验补 |
| 机器补-程序 | quote hash | `quote_sha256` | 用于审计引用未被改写 |
| 审校定-审校者 | 关系类型 | `relation_type`、`relation_subtype` | AI 可建议，审校确认 |
| 审校定-审校者 | 方法画像 | `method_profile` | AI 可建议，审校确认 |
| 审校定-审校者 | 审校结论 | `human_review` | 通过、退回、存疑 |

完整模板（成员可复制使用，`_field_notes` 是说明，入库前可剥离）：

### 6.2 五步推理

五步固定为"发疑、设问、取证、释理、结论"，在 JSON/API 层使用五个并列字段（`problem_discovery`、`research_question`、`evidence_collection`、`reasoning`、`conclusion`），不使用 `steps[]` 数组。固定步骤用并列字段有三个好处：表单更直接，校验更简单，前端展示更稳定。缺项也更容易显式标为 `missing`。"造舟于河.md"中的"预设"可作为历史写法映射到"设问"，但数据库 schema 不再保留"预设"作为并列主步骤。

| step_type | 英文 | 可为空 | 说明 |
| --- | --- | --- | --- |
| 发疑 | problem_discovery | 可为空但要标 missing | 疑点从哪里来 |
| 设问 | research_question | 可为空但要标 missing | 把疑点转成可验证问题 |
| 取证 | evidence_collection | 不应为空 | 引哪些材料 |
| 释理 | reasoning | 可为空但要标 missing | 证据如何支持判断 |
| 结论 | conclusion | 不应为空 | 最终训释/校勘/解释 |

以"造舟于河"为例：

| 五步 | 内容 |
| --- | --- |
| 发疑 | 旧注对"造舟"的解释分歧，且"至舟、作舟、诣舟、成舟"等解释与上下文不稳 |
| 设问 | "造舟于河"的"造"是否应解释为"相比次/比舟" |
| 取证 | 《说文》"艁，古文造"；"造之言曹""造、次一声之转"；《左传》《诗经》《尔雅》及李巡、孙炎、薛综等例证 |
| 释理 | 以形索义、因声求义、旁证切合、比较互证，并与文义事理相通 |
| 结论 | "造舟于河"之"造"应训为"比舟/相比次" |

### 6.3 人工库表设计

人工库前端显示一个 case，底层规范化拆表。`annotation_cases` 是表，`case_title` 是字段。`term_relations[]` 不能被单个 `source_term + target_term` 覆盖，因为一个 case 可有多组关系。

| 表 | 作用 |
| --- | --- |
| `annotation_cases` | case 主表，含五步字段和审校状态 |
| `case_term_relations` | 一案多组 A -> B 关系 |
| `case_evidences` | 一案多条证据 |
| `case_method_concepts` | case 使用的现代方法概念 |
| `case_method_expressions` | case 中出现的二王方法表达 |
| `reviews` | 人工审校记录 |
| `ai_runs` | AI 调用、prompt、模型、输入输出 hash |
| `gold_cases` | benchmark 标准案例集合 |

中英对照：

| 中文对象 | 英文字段/表 | 层级 | 含义 | 示例 |
| --- | --- | --- | --- | --- |
| 案例主表 | `annotation_cases` | case | 一条可审校的训诂/校勘问题 | 平原之隰 |
| 案例标题 | `case_title` | case | 人可读标题 | 平原之隰 |
| 二王出处 | `source_work/source_passage_id` | case | 二王论述所在书和 passage | 读书杂志 |
| 被考据对象 | `target_work/target_text` | case | 被解释或被校的原书和原句 | 管子 |
| 提交者 | `submitted_by` | case | 提交或创建案例的人/系统 | human:卢飞宇 |
| 审计者 | `reviewed_by` | review | 做人工审校的人 | human:审校员A |
| 原文-训释关系 | `term_relations[]` / `case_term_links` | relation | 一个 case 下可有多组 | 原 -> 隰；隰 -> 封 |
| 原文对象 | `source_term` | relation | 被解释、被校的字词 | 原 |
| 训释对象 | `target_term` | relation | 王氏训义、校正字、通假字 | 隰 |
| 关系类型 | `relation_type` | relation | 两对象之间的关系 | 训释/校勘/字际关系/虚词/句义/未定 |
| 证据 | `case_evidences[]` | evidence | 引文、旧注、异文或旁证 | 言平隰之泽 |
| 证据作用 | `evidence_role` | evidence | 证据在论证中的功能 | 支持校改、反驳旧说 |
| 发疑 | `problem_discovery` | process | 疑点从哪里来 | 今本与文义不协 |
| 设问 | `research_question` | process | 把疑点转成可验证问题 | 是否当作"平隰之封" |
| 取证 | `evidence_collection` | process | 引哪些材料 | 取《管子》注文与上下文 |
| 释理 | `reasoning` | process | 证据如何支持判断 | 由注文"小封"反证今本不协 |
| 结论 | `conclusion` | process | 最终训释、校勘或解释 | 当作"平隰之封" |
| 机器草稿 | `machine_result` | audit | parser/AI 的候选结果 | pending/draft/approved/rejected |
| 人工审计 | `human_review` | audit | 人工是否通过、可信度 | approved/uncertain/rejected |

### 6.4 人工标注的任务定位

人工标注不是让 AI 全部整理，也不是只复制原文。核心任务是建立可复核 gold standard：明确案例边界、原文对象、训释对象、关系、证据、五步、结论、审校状态。AI 可以生成草稿和提示遗漏，人工负责确认来源、引文、关系和推理。

## 第 9 章：Benchmark 与评估

**命名规范**：暂时不训练模型时，应使用以下命名体系：

| 名称 | 是否训练模型 | 用途 |
| --- | --- | --- |
| gold set | 不一定 | 人工确认的标准答案集合 |
| dev set | 不一定 | 调 parser、prompt、schema、RAG 的开发样本 |
| test set | 不训练 | 锁定不动，用来检验改动是否真的变好 |
| benchmark | 不训练 | 一套任务、数据和指标 |
| training set | 只有微调时才需要 | 用于 SFT/LoRA/RAFT 等训练 |

**评分流程**：

1. 人工选 30-50 个 gold cases，覆盖四书。
2. 每个 gold case 固定标准答案：passage、target_text、term_relations、evidences、relation_type、method_profile、五步、conclusion。
3. parser 跑一遍，评覆盖率、误报率、跳过原因是否合理。
4. AI 在同样输入下生成草稿，评 quote 命中率、关系准确率、方法概念准确率、五步缺项率。
5. 人工审校记录修改量，形成 `ai_revision_rate`。
6. 每次规则或 prompt 改动后重跑 benchmark。

初始指标：

| 指标 | 说明 | 评估对象 |
| --- | --- | --- |
| `quote_match_rate` | AI/候选 quote 是否能在 passage 中匹配 | AI 草稿 |
| `passage_hit_rate` | 是否找到正确 passage | 整体链路 |
| `term_relation_f1` | 原文对象/训释对象关系是否完整 | AI 草稿 |
| `relation_type_accuracy` | 关系类型是否与 gold 一致 | AI 草稿 |
| `method_concept_accuracy` | 现代方法概念是否合理 | AI 草稿 |
| `step_completion_rate` | 五步字段是否完整或正确标缺 | AI 草稿 |
| `human_revision_rate` | 人工修改比例 | 整体链路 |

**预算约束**：硬上限 10000 元。优先路线是 API 模型 + 本地结构化数据库 + 混合检索 RAG + 强校验。不优先本地部署大模型、LoRA、PEFT 或 RAFT。没有足够高质量 gold cases 前，不训练。

## 第 10 章：校验规则汇总

入库前至少校验：

| 校验 | 目标 | 执行方式 |
| --- | --- | --- |
| schema 校验 | JSON 字段完整、类型正确 | `jsonschema.validate()` 或 Pydantic，对照 `annotation_case.v1` schema |
| quote 校验 | quote 是 passage 子串或可归一匹配 | `quote_text in passage.plain_text`，必要时空白归一后再匹配 |
| hash 校验 | source、passage、quote 未被悄悄改写 | 入库前对比 `sha256(当前内容)` 与已有记录的 hash 值 |
| enum 校验 | relation_type、relation_subtype、status 在受控表中；method concept 至少标明 pending/approved/free_text | 查 `method_concepts`、`relation_types`、status 枚举表，不在表中的标 `unlisted` |
| 五步校验 | 五个字段存在；缺项显式为空 | 检查 5 个 key 均存在；`null` 或 `""` 视为有效缺项 |
| 审校校验 | machine_result 与 human_review 不混写 | 两字段必须独立填写，不得互相复制 |

## 第 11 章：当前实施顺序

1. **固定工作 Markdown**：标题重建、去 `<small>` 标签但保留文字，原始版本归档。生成 `plain_text`、`inline_notes`、标题路径和 hash。
2. **生成 passage**：`passages.jsonl`、`inline_notes.jsonl`、`title_anomalies.jsonl`。统一 `work_title / section_title / entry_title` 三层；`经传释词` 缺 H2 时合成 section。
3. **建 candidate.db**：跑 parser v2，输出 `parsed_items/candidate_items/skipped_items/audit_flags`，量化假阳/假阴损耗。
4. **建 AI input builder**：只给模型 top-k passage 和 schema。
5. **建 `validate_ai_json()`**：先做 quote/schema/enum/hash 校验。改 AI JSON 流程为 `source_json → ai_input_json → ai_output_json → db_import_json`，每层职责单一。
6. **组织人工标注**：用本文 §6.1 模板，向成员提供可复制的 JSON 模板和最低填写指引，启动首批标注任务。
7. **建 annotations.db v2 与人工库 schema**：建库保存五步、AI 草稿和人工审校。设计人工库表结构（见 §6.3）——统一 case JSON，底层拆 `term_relations / evidences / review`，五步保持五个固定字段。
8. **实现本地 AI 工具**：`search_passages / get_passage / validate_quote / get_method_vocab`，控制 top-k、窗口和缓存。
9. **建立 benchmark**：选 30-50 个 gold cases（以"造舟于河"等为起点），先评估 parser/RAG/AI 草稿质量。
10. **迁移到 main.db v2**：从已审校 annotation cases 迁移。设计主库 v2 schema（见 §7），停止扩展模板化 case。
11. **网站改造**：field registry + view config 驱动展示。
12. **训练评估**：最后再考虑。没有足够已审校 gold cases 前，不做 LoRA/RAFT/PEFT。
