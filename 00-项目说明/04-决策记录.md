# 决策记录

本文是项目的决策档案——解释"为什么这样做"。每节遵循统一格式：**Decision**（决定了什么）、**Why**（理由）、**Alternatives considered**（拒绝的方案及原因）。工程规范见 `03-工程实施规范.md`。

---

## 1. 文档放置与文件分工

**Decision**: 项目说明文档统一放在 `00-项目说明/`，分工如下：

| 文件 | 作用 |
| --- | --- |
| `01-项目介绍与标注指南.md` | 面向成员的项目介绍和标注指南 |
| `02-总体架构与问题分析.md` | 总体架构、问题分析和待验证点 |
| `03-工程实施规范.md` | 已确认的工程规范，写代码和改 schema 以此为准 |
| `04-决策记录.md` | 完整记录问题、分析、取舍和原因（本文） |
| `05-工程启动评估.md` | 当前是否可开工、先做什么、还有哪些落地风险 |
| `06-Git协作指南.md` | Git、分支、提交和 PR 基本流程 |

**Why**: 这些文档是项目级说明，不属于数据库、网站或文献单线。`00-` 前缀排在根目录前部，便于成员先读。四份文件各司其职——介绍给成员看，工程规范给开发者看，本文存档决策过程，问题分析存放待决事项。

**Alternatives considered**: 曾考虑合并为一份大文档，但角色混杂会导致读者难以定位所需信息——新成员需要指南，开发者需要规范，审校者需要回顾决策理由。分离后每份文件的目标读者和写作风格都更清晰。

## 2. source.txt 与 Markdown

**Decision**: `source.txt` 继续作为旧 parser 的兼容输入，但长期主输入转向四部 Markdown。

**Why**: 四部 Markdown 有标题层级、段落、小字信息和更接近阅读本的结构，适合建 passage。旧 `source.txt` 行号不可作为通用定位，且不能覆盖《经义述闻》《经传释词》《读书杂志》的结构化原文层。

实测数据证明了不能简单替换：旧 parser 读 `source.txt` 可得 7166 个 parsed terms、832 个词头组、4101 条 skipped；直接读 `广雅疏证_王念孙.md` 只得 6010 个 parsed terms、784 个词头组、5166 条 skipped。Markdown 内容更全，但旧 parser 对 `<small>`、标题、空行和脚注没有预处理，导致更多误判。

**Alternatives considered**: 直接把 `SOURCE_FILE` 从 txt 改成 md——这会增加 skipped 和假阳，因为标题、`<small>`、序跋、转换说明、空行会一起混进旧正则逻辑。正确次序是先 `markdown_preprocess`，再 `passage_builder`，最后才是 `candidate_extractor`。

## 3. 四份 Markdown 结构

**Decision**: 统一为 `document_title / section_title / entry_title` 三级定位路径，`经传释词` 缺 H2 时从卷名 H3 合成 section。`entry_kind` 辅助区分篇名、词群条目、案例题名等，但不影响 passage 切分。

**Why**: 四份 Markdown 的真实差异不允许硬编码"H1=书、H2=章、H3=词条"：

| 作品 | H1 | H2 | H3 | 实际特点 |
| --- | --- | --- | --- | --- |
| 广雅疏证 | 1 | 13 | 426 | H2 常见序、表、卷；H3 可为篇名或词群条目 |
| 经义述闻 | 1 | 33 | 2317 | H2 常见卷；H3 多为案例题名 |
| 经传释词 | 1 | 0 | 160 | 无 H2，卷名混在 H3 标题里 |
| 读书杂志 | 1 | 515 | 4955 | H2 常见目标书和卷；H3 多为条目题名 |

统一为三级是定位路径，不是学术目录。第一版标准不是"目录学完全准确"，而是 passage 能稳定定位。

**Alternatives considered**: 按古籍术语追求"章/卷/篇"的严格对应——四本书体例不同，强行统一会制造更多特例。三级的工程表达更稳：H3 在地位上统一为 `entry_title`，具体含义用 `entry_kind` 区分。

## 4. small 标签处理

**Decision**: 工作文本去掉 `<small>` 标签，标签内文字内容同权并入正文。来源审计用 `inline_notes[]` 记录小字来源。

**Why**: `<small>` 内容有信息价值——真实数据显示：`广雅疏证` 小字约 5797 处（含"反"约 300 处，校勘相关约 445 处），`经义述闻` 约 4718 处（校勘相关约 534 处），`读书杂志` 约 5230 处（校勘相关约 815 处），内容包括反切、音注、校勘说明、补正和整理标记。但 `<small>` 这个标签本身是 DOCX 转 Markdown 时保存"小字号 run"的转换格式，不是训诂语义标签。保留标签会干扰 parser、检索、quote 校验和前端展示。删除内容则丢反切、音注、校勘。

折中方案：正文去标签化（同权），来源审计保留小字元信息（`inline_notes[]` 记录内容、位置、类型、置信度）。

**Alternatives considered**: 长期保留 HTML `<small>` 标签——会持续污染 parser 规则、quote 校验和前端展示，把格式差异误当文本差异。也不选只保留内容丢弃来源——会丧失追溯 DOCX 小字号 run 的能力。

## 5. Passage 定位

**Decision**: 采用多重锚定位（`work_key + title_path + local_ordinal + raw_text_sha256 + normalized_text_sha256 + quote_exact + quote_offset`），不用页码或行号作为主定位键。

**Why**: 页码不统一——四份 Markdown 中，`广雅疏证` 页码命中极少，`经义述闻` 基本没有页码，`经传释词` 很少，`读书杂志` 有少量但不统一。行号只适合当前文件快速跳转，不具备跨版本稳定性。

多重锚的分工：标题路径粗定位，局部序号保证段落顺序，hash 发现文本漂移，quote 和 offset 精确定位证据。passage 是当前最优先补齐的主库缺口——没有 passage，terms、cases、evidences 都无法稳定回到原文。

**Alternatives considered**: 以行号为主定位键——行号随文件编辑必然变化，无法跨版本引用。仅用单一 hash——文本的小修改（如格式调整）会导致 hash 完全失效，无法定位"大致位置"。

## 6. Parser v2

**Decision**: 旧 parser 的"若干词头，某义也"正则方案改为"候选生成 + 风险标记 + 可审计跳过"。不能直接改旧 parser 读 Markdown。

**Why**: 旧 parser 的问题不只是正则写错了——不该摘的被摘入、该摘的被跳过、证据被错误归属、case 被模板包装成确定结论。只修正则解决不了假阳/假阴不可见的问题。

新方案输出分三层（`parsed_items`、`candidate_items`、`skipped_items`），每项记录 `rule_hits`、`risk_flags`、`skipped_reason`，让错误可解释。机器方案负责"稳定、可复现、可批量"；AI 辅助方案负责"复杂语义、关系初判、五步草稿"。共同原则：AI 输出永远是候选或草稿，不能自动覆盖主库。

**Alternatives considered**: 直接改 `SOURCE_FILE` 成 Markdown，用旧正则逻辑继续跑——标题、`<small>`、序跋、转换说明、空行全部混入正则，得到更多 skipped 和假阳。正确次序是先 `markdown_preprocess`，再 `passage_builder`，最后才是 `candidate_extractor`。

## 7. 旧 parser / importer 的模板 case

**Decision**: 主库不继续扩展模板化 case。旧数据保留为展示线索，新主库 v2 保存裸原文结构化和候选索引。五步推理放入人工库。

**Why**: 当前 `importer.py` 的 `cases` 高度模板化，七字段无一逐案识别：

| 字段 | 当前值 | 问题 |
| --- | --- | --- |
| `title` | `广雅疏证「X也」词条群（行N）` | 不是原文标题 |
| `problem` | 固定模板字符串 | 不是逐案疑点 |
| `method` | 固定字符串 | 不是逐案识别 |
| `conclusion` | 模板字符串 | 不是人工结论 |
| `certainty` | 全部"确定" | 不可信 |
| `status` | 全部"草稿" | 只说明未审校 |
| `process_text` | 空 | 没有五步过程 |

`certainty=确定` 和 `status=草稿` 的组合尤其容易误导——这不是数据细节错误，而是整个字段体系在冒充人工结论。

**Alternatives considered**: 继续扩展模板 case，增加更多模板覆盖更多词条——模板永远不能替代逐案人工识别，扩展模板只是在扩大不可信数据的规模。

## 8. term_relations 与 method_profile 的分离

**Decision**: `relation_type` 和 `method_profile` 不能合并。`relation_type` 回答"证明了什么"（结论），`method_profile` 回答"怎么证明"（方法）。`term_type` 从核心 schema 中摒弃。

**Why**: 以"造舟于河"为例：`relation_type = 训释/声转释义`（结论是"造训为相比次"）；`method_profile.concepts = [声训, 书证, 义证, 旧注辨驳]`（用了这些方法证明）。一个 case 可以有一个主要关系，但使用多个方法证明它。若合并，数据无法表达"同一结论由多种方法支持"。

`term_type`（字/词/短语的粒度）实际价值低——在训诂案例中，最重要的不是"它是字还是词"，而是"它和另一个对象是什么关系、用了什么方法证明"。

**Alternatives considered**: 用双层方法词表替代 `relation_type`——方法词表只能回答"怎么证明"，不能回答"证明了什么"。同样使用书证和义证，一个案例可能证明"通假"，另一个证明"误字"，第三个证明"虚词用法"。没有关系字段，后续无法稳定检索。

---

## 9. relation_type 二级分类

**Decision**: 使用 `relation_type + relation_subtype` 二级结构，每条 `term_relations[]` 只保留一个主关系。不用数组形式。

**Why**: `relation_type[]` 数组看似灵活，但会让主关系消失——同时填 `["校勘", "误字", "当作"]`，校勘是大类，误字/当作是细项，混在数组里查询和统计会很乱。

二级分类：

| 一级 | 二级候选 | 用途 |
| --- | --- | --- |
| 训释 | 同义、反训、声转释义、义界 | A 被解释为 B |
| 校勘 | 误字、当作、衍文、脱文、倒文 | A 应改作 B |
| 字际关系 | 通假、异体、古今字 | A 与 B 的字际关系 |
| 虚词用法 | 语气、连词、介词、代词、助词 | A 是虚词 |
| 句义解释 | 句读、语法、上下文解释 | 重点不在单字 A->B |
| 未定 | 待核、疑似多类 | 暂不能判断 |

**Alternatives considered**: 扁平枚举 14 项混排——同层级混排无法区分大类和小类，统计和检索都会混乱。

---

## 10. 双层方法词表

**Decision**: 双层词表服务于 `method_profile`，不替代 `relation_type`。`训诂术语.md` 只能作为第一批候选词，不能作为唯一权威词表。王宁《训诂学原理》作为理论校准来源，二王四书中的真实表达才是项目自己的证据来源。

**Why**: `训诂术语.md` 本身没有列出参考书目或出处说明，不能当作有明确来源的权威词表。王宁书中也强调旧术语常有定义不严、层级混杂的问题——它提供理论骨架，但不能作为唯一来源。终极权威是二王四书中的真实表达：每一方法概念最终必须是二王实际做过、且能从 passage 中找出的。

两层分工：

| 层 | 字段 | 来源 | 作用 |
| --- | --- | --- | --- |
| 现代方法概念 | `method_profile.concepts[]` | 训诂术语.md、王宁、课程大纲、人工审定 | 统一检索和展示 |
| 二王原文表达 | `method_profile.expressions[]` | 二王四书 passage 原文 | 保留二王实际说法 |

第一版导入 `训诂术语.md` 为候选级概念，每个概念增加 `source_ref`、`definition`、`review_status=pending`。最终升级为 `approved` 的词，必须能挂接至少一个二王案例。

**Alternatives considered**: 以王宁《训诂学原理》为唯一权威——它提供理论层级意识，但二王实践中存在王宁体系未覆盖的表达。以 `训诂术语.md` 直接作为审定词表——无出处说明，不可作为权威。用双层词表替代 `relation_type`——已排除，见第 8 节。

## 11. core_meaning 的替代方案

**Decision**: 不写死 `terms.core_meaning`。全部出现进入 `term_occurrences`；核心释义用 `term_core_profiles` 记录代表性 `primary_occurrence_ids`、`primary_case_ids` 和可生成摘要。

**Why**: 旧方案把第一次导入摘要当成核心释义，会丢掉多义、多 case 和审校状态。新方案中，页面显示"核心释义"时从已审校 occurrences 中选代表性义项，按频次、可信度、作品来源生成摘要；未审校材料只参与检索，不参与权威释义。最小版本甚至可以不生成自然语言摘要，只显示"已审校 case id 列表 + 代表 quote"。

**Alternatives considered**: 人工为每个 term 写死 core_meaning——不可持续，且一个词在不同 case 中义项不同时无法合理取舍。

## 12. works 引用映射 + category 降级

**Decision**: works 改为"规范作品表 + 动态候选 + 原标签保留"——遇到 `皋陶謨` 这类篇名时，同时保存 `raw_work_label='皋陶謨'`、`normalized_work='尚书'`、`mapping_rule='chapter_to_work'`、`confidence='high/medium/low'`。未知作品进入候选，等待人工合并。`category` 降级为可生成的页面分组，不作为人工必填核心字段。

**Why (works)**: 旧 `works` 来自预设书名和篇名映射（`CANONICAL_WORK_NAMES` 和 `_CHAP_TO_WORK`），不是动态从原文完整统计。它有粗粒度浏览价值，但不能证明精确出处。新方案保留原标签可以追溯映射是否正确，避免映射错误后无法回溯。

**Why (category)**: `category` 容易成为第三套模糊分类——既像关系，又像方法，又像页面栏目。最稳做法是用 `relation_type` 和 `method_profile.concepts` 生成页面分组。例如 `relation_type=校勘/误字` 可归入"校勘类"，`relation_type=虚词用法` 可归入"虚词类"。人工不必直接填写 `category`。

**Alternatives considered (works)**: 只保留映射后结果，丢弃原标签——映射错误时无法回溯。删除 works 表——丢失粗粒度浏览价值。

**Alternatives considered (category)**: 保留为核心必填字段——会造成第三套并行分类体系，与 `relation_type` 和 `method_profile` 重叠且不一致。

## 13. AI 检索场景与本地工具桥

**Decision**: 区分四类检索场景（DOCX 标注整理、parser 候选审核、人工标注辅助、网站/智能体问答），每类检索对象和输出不同，不能混成一个"RAG"。API 模型通过本地工具桥间接查询文件——本地程序注册 `search_passages`、`get_passage`、`validate_quote`、`get_method_vocab` 等函数，模型返回工具调用意图，本地执行查询后只把必要片段返回模型。

**Why**: API 模型不能直接读本地文件——这是技术事实。工具桥方案让模型间接"查本地文件"，同时控制 token 开销（只传 top-k passage，不传全书；长 passage 截断到候选周边窗口；相同检索和 prompt 可缓存）。这条路在 10000 元预算内可行，主要花开发时间和少量 API 费用。

**Alternatives considered**: 把所有文件内容全量塞入 prompt——上下文爆炸、费用不可控、且无必要（大部分内容与当前候选无关）。让 AI 直接调用操作系统文件 API——不安全且不可靠。不做工具桥，让模型凭现有 slim JSON 自由发挥——没有真正查询四部 Markdown、主库或方法说明的输出只是猜测，缺乏 source span 追溯。

## 14. 五步推理

**Decision**: 五步固定为"发疑、设问、取证、释理、结论"，在 JSON/API 层使用五个并列字段（`problem_discovery`、`research_question`、`evidence_collection`、`reasoning`、`conclusion`），不使用 `steps[]` 数组。

**Why**: 本项目五步已经固定，不是变长步骤。使用五个并列字段有三个好处：表单更直接（成员看到五个独立框，而不是在一个数组里找位置），校验更简单（检查五个 key 存在即可），前端展示更稳定（不需要遍历数组并猜测步骤名称）。缺项更容易显式标为 `missing`。

**Alternatives considered**: `steps[]` 数组——适合不固定步骤数，但这里五步固定，数组反而增加了解析和校验复杂度。数据库将来若需要历史版本，可另建扩展表，但 API 层仍输出五个字段。

## 15. Benchmark 与训练决策

**Decision**: 暂不训练模型。现阶段少说"训练集"，多说"gold cases / dev set / test set / benchmark"。预算硬上限 10000 元，优先路线是 API 模型 + 本地结构化数据库 + 混合检索 RAG + 强校验。

**Why**: 当前最大瓶颈不是模型不会说，而是缺 passage、quote 校验、关系标准和已审校 gold cases。没有这些，训练只会学习不稳定标注和模板化旧 case。10000 元预算下，把钱花在 API 调用、检索、校验和少量人工审校上更有效。

不优先本地部署大模型、LoRA、PEFT 或 RAFT。只有当 gold cases 足够多且 RAG+prompt 已达到瓶颈，才重新评估训练。

**Alternatives considered**: 现在就收集数据做 SFT/LoRA——没有足够高质量已审校 gold cases，训练只会固化模板化旧 case 的错误模式。本地部署大模型——10000 元预算无法覆盖 GPU 租用和部署运维成本。

## 16. 工程字段与状态统一

**Decision**: 全项目统一使用 `machine_result` 和 `human_review`，不再区分 JSON/API 层和 SQL 层命名。`status` / `review_status` 使用一个全局小枚举：`pending`、`draft`、`approved`、`rejected`、`uncertain`。`case_term_relations` 必须保留 `relation_subtype`。方法词表当前是候选级，使用 `review_status=pending` 起步。

**Why (machine_result / human_review)**: 字段名的首要目标是降低工程和标注的心智成本。此前曾出现 `machine_result`、`machine_draft_json`、`machine_result_json` 等混用：JSON 层、SQL 层、说明文档不一致，开发者按一个名字查另一个名字会出错。统一命名后，不论字段最终以 TEXT、JSON 文本还是结构化列存储，都叫 `machine_result` / `human_review`；存储形态由 schema、字段类型或注释说明，不进入字段名。

**Why (status)**: `status` 若按机器、人工、SQL、词表分别发明一套值，前端、导入脚本和校验器都会变复杂。五个值已经覆盖当前需要：`pending` 表示待处理，`draft` 表示机器草稿，`approved` 表示通过，`rejected` 表示失败、拒绝或退回，`uncertain` 表示人工审校后仍存疑。不同字段只取必要子集：

| 字段 | 枚举值 |
| --- | --- |
| `machine_result.status` | `pending` / `draft` / `approved` / `rejected` |
| `human_review.status` | `pending` / `approved` / `rejected` / `uncertain` |
| SQL `review_status` | `pending` / `approved` / `rejected` / `uncertain` |
| `method_concepts.review_status` | `pending` / `approved` / `rejected` |

**Why (relation_subtype)**: `relation_type + relation_subtype` 已经确定为二级关系结构。若 SQL 只保留 `relation_type`，二级分类只能塞进 `note`，后续无法查询和统计。因此 `case_term_relations` 必须含 `relation_subtype TEXT`，允许为空。

**Why (method concepts)**: 方法词表候选级不是错误，而是项目当前阶段的正常状态。`训诂术语.md`、王宁《训诂学原理》和课程大纲可作为候选来源，但第一批 `approved` 概念应从 30-50 个 gold cases 的人工标注中反向确认。在此之前，`method_profile.concepts` 可用于提示、初标和检索建议，不能当作无需审校的自动分类依据。

**Why (JSON quotes)**: JSON 示例中若原文或说明文字含 ASCII 双引号 `"`，必须写作 `\"`；中文引号 `“”`、直角引号 `「」`、双直角引号 `『』`、书名号 `《》` 本身不破坏 JSON。不能为了解决 JSON 语法问题而把原文引号粗暴改成书名号。引号闭合属于文本质量检查，可另做 `quote_balance_check`。

**Alternatives considered**: 保留 `_json` 后缀区分存储形态——会把实现细节暴露到字段名，并导致 JSON/API 与 SQL 两套命名。保留 `not_run/not_generated/unreviewed/needs_revision/validated` 等旧状态——同义值太多，校验和前端都要写兼容逻辑。把候选方法词表直接当 approved 分类——会在 gold cases 尚未建立前制造大量伪确定分类。
