# V2 四项问题实践研究报告

> 注意：本文件是 2026-08-12 执行修复前的研究快照，不是当前状态表。当前 canonical 来源、字段语义和运行结果以 [10-V2统一工作流与数据库状态规范.md](10-V2统一工作流与数据库状态规范.md)、[09-当前状态与目标V2对照表.md](09-当前状态与目标V2对照表.md) 和 `v2/data/real_runs/batch_migration_report.json` 为准；本文件中的 `approved=2`、`source_documents=4` 等数字仅保留用于说明修复前的发现。

> 研究状态：基于当前工作区真实文件、现有 V2 批量迁移报告和现有 SQLite 工作库的实践核查。报告中的数据库批量结果沿用已完成的迁移运行；本轮研究只做只读核查，没有重跑会写入数据库或批量报告的迁移命令。

## 1. 研究目的与结论先行

本研究核查四项问题：同一路径被重复登记为多个来源；外部引文未进入 canonical passage；旧 AI JSON 缺少 `target_work` 或证据；full JSON 上下文能否作为证据。判断标准是：能否支持 V2 中的来源追溯、机器校验、人工复核和后续 gold 晋级，而不是能否让案例尽快通过机器校验。

结论如下：

- 修复前工作库确实存在同一《读书杂志》Markdown 路径的两条来源登记。旧记录没有 passage，新记录承载 4,987 个 passage；根因是把内容摘要当成来源身份。现已改为 `(work_key, source_file)` 唯一，版本变化交给 Git 或上游 revision 记录。
- 121 条 evidence 中，41 条（33.88%）挂接到当前已加载的 canonical passage，80 条（66.12%）来自未加载的外部来源并保持 `quote_check=unchecked`。这说明“外部引文未进入 passage”是当前数据边界问题，不等于这些引文已经被证明错误。
- 17 个旧 AI 案例中有 13 个（76.47%）的 `target_work` 字段存在但为空；其中全部 13 个《经传释词》案例都为空。另有 1 个案例（5.88%）的 `evidences` 为空。V2 正确地把这些记录保留为 rejected 审计记录，不能把旧 JSON 的 `status=草稿` 或 `certainty=确定`解释为人工通过。
- full JSON 上下文对未挂接 canonical passage 的 80 条引文只命中 11 条（13.75%，其中 exact 10 条、punctuation_normalized 1 条）；其余 69 条（86.25%）未命中。即使命中，它也只能证明引文曾出现在旧的 DOCX/标注 JSON 上下文中，不能替代外部原典 passage、版本和页码核验。因此 full JSON 应保留为迁移线索和回溯证据，不能直接作为 canonical evidence，也不能触发 machine approved 或人工 gold。

当前数据库的状态边界是安全的：17 个案例全部 `human_status=pending`，`v_gold_cases=0`；机器通过的 2 个案例仍在 `machine_draft` 生命周期中，不能称为人工 gold。

## 4. 问题一：同一来源文件被重复登记

### 4.1 实际证据

修复前冲突分组为 1 组，占当时 3 个来源 work 的 33.33%。两条记录的 `work_key` 和 `source_file` 完全相同，创建时间不同；旧记录有 0 个 passage、0 个关联 case，新记录有 4,987 个 passage、2 个关联 case。整个数据库因此有 4 个 source document 行，而批量报告只处理 3 个当前 source profile。该现象证明来源身份设计会留下孤立记录，并不证明两份不同原典曾同时参与案例。

### 4.2 源码根因

旧实现把内容摘要的一部分并入 `source_document_id`，schema 却没有对 `(work_key, source_file)` 建立唯一约束；文件只要发生换行或格式变化，就会产生第二个 source row。passage ID 仍只由 `work_key + local ordinal` 组成，后写入的记录会接管 passage，旧 source row 则成为孤立记录。现实现改用稳定的 `work_key + source_file` 身份并添加唯一约束，文件版本由 Git 或上游 revision 负责。

### 4.3 影响、severity 与 confidence

- `severity=high`：若不先确定 canonical 版本，案例、passage、行号和引文无法稳定地指向同一来源版本；后续 quote 校验可能看似通过，但 provenance 不能说明针对哪个文件版本。
- `confidence=high`：两条来源记录、创建时间、各记录 passage 数量和源码冲突机制均已直接查询或逐行核对。
- 当前影响是“历史版本混入且无显式 superseded 状态”，不是已经证明当前两个版本的文字都同时用于案例。旧版本当前无 passage，说明实际风险更接近 lineage 不完整，但仍不能把它当作无害。

### 4.4 修复方案与自动化门禁

1. 先由项目负责人确认 `1460a906...` 是否为《读书杂志》的 canonical Markdown；旧 `153408495...` 不删除，标记为 historical/superseded，并记录确认依据和时间。
2. source registry 以稳定来源 ID 和上游 revision 记录 lineage；不要让文件内容变化产生第二个来源身份。
3. passage 写入时强制检查来源身份和路径一致，避免新版本无提示地接管旧 passage。
4. 批处理前置门禁：同一 `(work_key, source_file)` 只能有一条来源登记；所有 case 的 `source_passage_id` 和 evidence passage 必须属于该 canonical source document。
5. 报告门禁：发现 version conflict 时批处理可以保留审计记录，但不得输出“来源已确定”或把受影响案例升级为 machine approved/gold。

## 5. 问题二：外部引文未进入 canonical passage

### 5.1 实际证据

当前 121 条 evidence 的来源解析和 quote 状态如下：

| 分类 | 数量 | 比例 | 实际字段含义 |
|---|---:|---:|---|
| `source_resolution=canonical_passage` | 41 | 33.88% | 在本次加载的原典 Markdown passage 中找到 |
| `source_resolution=external_source_unavailable` | 80 | 66.12% | evidence 声称来自其他 work，但该 work 没有进入本次 passage corpus |
| `quote_check=passed` | 41 | 33.88% | 当前 canonical passage 的严格命中 |
| `quote_check=unchecked` | 80 | 66.12% | 外部来源未加载，保持未核验，不伪造失败或通过 |

15/17 个案例至少包含一条未加载的外部 evidence：2 个广雅案例和 13 个经传释词案例；2 个读书杂志案例的 4 条 evidence 全部挂接当前读书杂志 passage。两个广雅案例分别有 8/22 和 21/29 条 canonical evidence，其余 14/22 和 8/29 条为 external unavailable，所以结构上可用但被保留为 machine draft。经传释词的 13 个案例共有 66 条 evidence，其中只有 8 条挂接当前经传释词 Markdown，其余 58 条没有外部 canonical passage；这些案例还叠加了 `target_work` 缺失，因此总体为 rejected。

进一步把这 80 条未挂接 evidence 放到项目现有四部原典 Markdown 的全部 passage 中检索，仍然没有任何 exact 或规范化命中（`0/80`）。因此当前结论不是“它们一定错误”，而是“它们不在当前四部 canonical corpus 中，必须补登记外部来源后才能核验”。

### 5.2 源码根因

`v2/scripts/run_batch_migration.py:33-46` 只配置三份 primary Markdown；`run_batch_migration.py:253-266` 每个旧 AI JSON 只构建并入库其对应的那一份 Markdown passage。`legacy_ai_adapter.py:217-240` 会把 evidence 的 `work` 保留，但只在当前传入的 passage 列表中查找 quote。批处理随后在 `run_batch_migration.py:308-319` 中把“有其他 work 名称但没有 passage”标为 `external_source_unavailable`，并把 `quote_check`改为 `unchecked`。

这个行为是正确的边界处理，但当前数据模型还没有外部 source registry、外部版本、版次/页码和外部 passage，因此无法完成第二阶段的严格校验。`annotation_evidences`允许 `passage_id`为空（`annotation_v2.sql:83-95`），所以系统可以保存未核验线索，但不能把它误读成已核验引文。

### 5.3 影响、severity 与 confidence

- `severity=high`（对引用可用性）：80/121 条 evidence 不能支持当前工作库中的严格引文校验；若直接用于结论或网站，会造成来源覆盖率被高估。
- `severity=medium`（对当前迁移流程）：系统已经将其保留为 `unchecked` 或 draft/rejected，未直接升级，所以暂未形成 gold 污染。
- `confidence=high`：数量来自 SQLite 和批量报告，且来源分类由脚本逐条写入 `evidence_json`；当前未声明外部引文为错误，只声明“未在已加载 corpus 中核验”。

### 5.4 修复方案与自动化门禁

1. 建立外部来源 registry：至少包括 `work_key`、规范名称、来源文件、edition/version、页码或定位信息、上游 revision、录入时间和 canonical 状态。
2. 将外部典籍按同一 passage builder 或等价规则进入 source_documents/passages；保留原始文字、规范化文字、行号/页码和字符偏移。
3. 对 `external_source_unavailable` 只允许进入 machine draft 或 human review，不允许进入 machine approved 的可交付集合，更不允许进入 gold。
4. 自动门禁：每条 evidence 必须满足“`passage_id`存在且属于 canonical source document，quote substring/normalized match 通过且偏移有效”；否则 `quote_check=unchecked`，案例不能通过机器审批。
5. 对外部 evidence 的工作名进行规范化映射，不能用字符串“看起来像同一本书”代替来源登记；合并来源时必须保留原始 `source_work`。

## 6. 问题三：旧 AI JSON 缺少 target_work 或证据

### 6.1 实际证据

三份旧 AI JSON 共 17 个案例：

| 检查 | 数量 | 比例 | 分布 |
|---|---:|---:|---|
| `target_work` 非空 | 4 | 23.53% | 广雅 2、读书杂志 2 |
| `target_work` 字段为空字符串 | 13 | 76.47% | 经传释词 13/13 |
| `evidences` 非空 | 16 | 94.12% | 仅经传释词“已，既也”为空 |
| `evidences=[]` | 1 | 5.88% | `legacy-ai:11`，标题“已，既也” |

经传释词旧 JSON 的 13 个案例 `target_work` 都是空字符串；12 个案例有 66 条 evidence，1 个案例无 evidence。当前 V2 校验结果中，13 个经传释词案例全部 rejected；每个都出现 `missing_required:target_work` 和 `jsonschema:target_work: '' is too short`，其中 `legacy-ai:11`另有 `missing_required:evidences` 和 `jsonschema:evidences: [] is too short`。

需要区分两类问题：`target_work` 是旧 JSON 的字段值缺失；其他 evidence 的 `passage_id=None`则主要是外部来源未加载造成的来源解析缺口。二者不能都简单称为 OCR 错误，也不能靠把状态改成 approved 解决。

### 6.2 源码根因

`v2/src/erwang_v2/legacy_ai_adapter.py:260-278` 直接将 `legacy_case.get("target_work", "")` 和旧 evidence 列表映射到 V2，没有根据标题或引文内容擅自推断 `target_work`，也没有为不存在的 evidence 生成占位证据。`v2/src/erwang_v2/validate_annotation_case.py:11-19` 将 `target_work` 和 `evidences`列为必填；`validate_annotation_case.py:55-58`检查空值；逐条 evidence 在 `:74-82`要求 passage 存在；JSON Schema 在 `annotation_case.v1.schema.json:6-15`要求两个字段，`26`要求 `target_work`至少一个字符，`48-50`要求 evidence 至少一条。

因此根因不是 V2 适配器“漏写”字段，而是旧数据本身没有足够信息，V2 又正确地拒绝了不完整记录。旧 JSON 中的 `status=草稿`和 `certainty=确定`被保存在 `_migration`/`human_review.legacy_*`中，但没有覆盖 V2 的 `human_status=pending`。

### 6.3 影响、severity 与 confidence

- `severity=high`：13/17 案例无法形成完整 V2 case；其中 1 个没有任何 evidence，不能支撑可复核的结论。
- `confidence=high`：空值比例直接来自三份旧 JSON；拒绝原因同时出现在批量报告、数据库 `machine_result_json`和 schema/validator 代码中。
- 这 13 个案例已经被保存为 rejected 审计记录，因而当前没有被误当作 gold；但它们暂时不能作为可靠的机器候选交给后续发布流程。

### 6.4 修复方案与自动化门禁

1. 对经传释词建立明确的目标来源映射：从旧 DOCX/full JSON、原典定位或人工复核中确认 `target_work`；无法确认时保持空值并标记 unresolved，不用模型猜测后直接入库。
2. 对 `legacy-ai:11`补找原始 evidence；若原始材料确实没有证据，应保留 rejected，而不是制造一条泛化引文。
3. 对外部 evidence先进入 source registry/passages，再重新计算 `passage_id`、quote check 和 source location。
4. 自动门禁：`target_work`非空、`evidences`至少 1 条、每条 evidence 有非空 quote、来源已登记、passage 存在、引文定位校验通过；任一项不满足都不能成为 machine approved。
5. 复核通过后仍只改变 `human_review`，不能把机器校验通过等价为人工 gold；只有人工批准才允许生命周期进入 `gold`。

## 7. 问题四：full JSON 上下文是否能作为证据

### 7.1 实践核查结果

三份 full JSON 都是 `annotation_docx_full_json_v1`，但文档形态不同：广雅有 190 个 paragraph、12 个 annotation block、9 个 comment；经传释词有 97 个 paragraph、19 个 comment；读书杂志有 66 个 paragraph、14 个 annotation block。它们包含 `source_file` 和 paragraph 文本，但这些字段只指向旧 DOCX 标注包，不是外部《说文解字》《礼记》等原典的版本凭据。

对 121 条 evidence，当前脚本只对未挂接 canonical passage 的 80 条统计 full JSON 上下文：

| 上下文结果 | 数量 | 占未挂接 evidence | 解释 |
|---|---:|---:|---|
| exact | 10 | 12.50% | quote 原样出现在指定 paragraph 文本 |
| punctuation_normalized | 1 | 1.25% | 去除标点、空白、格式控制字符后命中 |
| 合计命中 | 11 | 13.75% | 只能证明旧标注上下文包含该文本 |
| not_found | 69 | 86.25% | 在指定 paragraph indexes 的文本中未找到 |

一个可复核的 normalized 例子是 `legacy-ai:3` 的 evidence 0：来源标记为《礼记·檀弓》郑玄注，paragraph index 为 `[1]`，quote 为“以與已字本同”；旧 full JSON paragraph 中存在相同语句，但夹有零宽格式字符，因此被 compact-text 规则判为 `punctuation_normalized`。一个 exact 例子是 `legacy-ai:15` 的 evidence 0：full JSON paragraph `[73]`包含“已！予惟小子！”。这两个例子都没有提供对应外部原典的版次、页码、上游 revision 或独立 passage ID。

### 7.2 源码根因与证据边界

`run_batch_migration.py:110-118`只读取 full JSON 的 `paragraphs[index].text`；`:121-136`只做原样 substring 和去标点/空白/控制字符后的 substring。它没有校验评论内容、外部来源文件、版本、页码，也没有把 full JSON paragraph 作为 `passages`写进 source_documents。因此该检查的语义是“旧 AI/标注包上下文复现”，不是“原典来源复核”。

当前批处理的安全处理是正确的：当 evidence 没有 canonical passage 且其 `work`不是当前 primary work 时，`:312-317`将其标为 `external_source_unavailable`并把 `quote_check`保持为 `unchecked`；上下文命中只写入 `annotation_context_check`，没有将其升级为 passed。这个字段设计应继续保持非晋级性质。

### 7.3 影响、severity 与 confidence

- 作为迁移线索：`severity=medium`，`confidence=high`。11 条命中可以帮助定位原旧文档中的段落，减少人工寻找成本。
- 作为原典证据：`severity=high`，`confidence=high`。full JSON 不足以证明引文出自所标记的外部典籍，更不足以证明版本和文字准确；若将其直接作为 evidence，会把“旧标注包中出现过”误报为“原典核验通过”。
- 69/80 未命中也说明 full JSON 不是稳定的证据覆盖层，不能用它补齐所有外部引用。

### 7.4 修复方案与自动化门禁

1. 在 evidence 中保留两条独立链：`annotation_context`（full JSON 路径、paragraph indexes、context match）和 `canonical_evidence`（source document、passage、quote check、字符偏移）。
2. full JSON 命中只能提高迁移优先级或生成待核验任务，不能改变 `quote_check=unchecked`为 `passed`，不能改变 human status，也不能进入 gold。
3. 外部原典核验完成后，才将对应原典文件登记为 source document、切成 passage，并重新计算 quote match/location；full JSON 作为 provenance 辅助保留。
4. 自动门禁：任何 evidence 若只有 `annotation_context_check in {exact,punctuation_normalized}`而 `passage_id is null`，必须阻止 machine approved；报告中分别统计 context 命中和 canonical quote 通过。

## 8. 综合修复顺序

建议按以下顺序继续实践，避免在错误来源版本上修数据：

1. 确认《读书杂志》的 canonical 路径与 Git 版本；旧重复登记只保留在修复前备份中，不进入新工作库。
2. 建立外部来源 registry，优先覆盖本批次已出现的外部 work；将其原典或可靠来源切成带上游 revision 和明确定位的 canonical passages。
3. 重新处理外部 evidence，区分“原典 passage 通过”“仅 full JSON 命中”“完全未核验”。
4. 通过原始材料或人工复核补齐经传释词的 `target_work`；为“已，既也”补 evidence 或明确保持 rejected。
5. 重新运行 schema、quote 定位、source lineage 门禁；仍将所有 human status 保持 pending，待人工审校后再决定是否进入 gold。

## 9. 建议的 V2 自动化门禁清单

| 门禁 | 规则 | 当前结果 | 失败动作 |
|---|---|---|---|
| source lineage | 同一 `(work_key, source_file)` 只能有一个来源登记 | 修复前失败：1 组/3 work | 阻止 canonical 交付，保留冲突报告 |
| source passage ownership | case/evidence passage 必须属于确认的 canonical source document | 当前旧版本存在孤立 source row | 标记 provenance 风险，不能静默接管 |
| case schema | required fields、`target_work`非空、term/evidence 最小数量满足 | 13/17 失败 | rejected，要求补源数据或人工确认 |
| evidence provenance | evidence 有 source work、passage、quote 定位校验 | 80/121 暂未满足 | 保持 unchecked/draft |
| full JSON boundary | context 命中不能替代 canonical passage | 当前已遵守 | 只作迁移线索，不升格 |
| state boundary | `human_status=approved` 才能进入 gold | 当前 17 pending、gold 0 | 禁止机器结果直接发布为 gold |

## 10. 最终判断

这四项问题不是四个互不相关的清洗小问题，而是同一条证据链的四个断点：来源版本决定 passage 身份；外部来源决定 evidence 能否挂接；旧 JSON 完整度决定 case 能否进入结构化校验；full JSON 只能提供历史上下文，不能替代 canonical 原典。当前 V2 的“机器库与人工状态分离、机器案例早入库、未人工批准不进 gold”原则在这次实践中是有效的，应该继续保持。

本轮最重要的可执行结论是：先解决 source lineage，再补外部 canonical passage，再补 `target_work`/缺失 evidence，最后才进入人工审校。当前 2 个 machine approved 仍是机器状态，4 个 machine_draft 仍是机器草稿，13 个 rejected 是审计记录；17 个案例均不是人工 gold。
