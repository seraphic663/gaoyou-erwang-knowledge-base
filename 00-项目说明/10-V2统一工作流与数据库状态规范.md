# V2 统一工作流与数据库状态规范

> 生效日期：2026-08-12
>
> 最近复核：2026-08-30；数据库计数、状态边界和线上 V2 只读接口与本规范一致。
>
> 适用范围：`v2/`、`04-项目文献/D-标注/`、V2 统一工作数据库及其后续网站/主库适配器。
>
> 规范级别：本文件是当前 V2 工作流的优先解释；旧文档中“AI 输出不能入库”的表述，统一解释为“不能未经机器校验直接进入 gold/主库”，不得再理解为“机器结果不能进入工作数据库”。

## 1. 总原则

V2 使用一个统一的工作数据库，同时保存机器生成记录和人工审校记录。机器记录可以在通过结构、来源和引文校验后提前入库；人工审校不是入库前置条件，而是从机器草稿晋级为 gold/正式数据的必要条件。

机器状态和人工状态永远分开。`machine_result.status=approved` 只表示机器校验通过，不表示考据结论正确，也不表示人工确认；`human_review.status=approved` 才表示该案例获得人工审校通过。

旧 AI JSON 不作为 V2 的规范格式，但不能舍弃。它是迁移材料、初始草稿、回归测试样本和来源记录；新流程可以直接从候选 passage 调用 AI，生成同一套 V2 `annotation_case.v1`。

## 2. 规范 workflow

```text
    原典 Markdown / 归档底本
        │
        ▼
预处理 -> passage、标题路径、行号、文本版本信息
        │
        ▼
候选抽取 -> parsed_items / candidate_items / skipped_items / 风险标记
        │                         │
        │                         └─ candidate_items（原文机器候选层）
        │
        ├─ 旧 AI JSON -> legacy_ai_adapter ─────┐
        ├─ 旧 dictionary.db -> legacy adapter ───┤
        └─ 新候选 -> AI input -> AI output ──────┤
                                                ▼
                                 annotation_case.v1 草稿
                                             │
                                             ▼
                         Schema / 枚举 / quote / 来源校验
                                             │
                                             ▼
                     统一工作数据库：机器案例先入库
                                             │
                                             ▼
                               人工审校队列
                                             │
                         ┌───────────────────┼───────────────────┐
                         ▼                   ▼                   ▼
                    approved             uncertain            rejected
                         │
                         ▼
                  gold / 主库 / 网站快照
```

旧 AI JSON、旧机器库和新 AI 输出都只负责提供机器材料，二者必须汇合到同一个 V2 case schema 和同一个数据库入库接口，不得各自维护一套状态语义。原文入口先进入 `candidate_items`；候选本身不是案例，只有明确的 AI/案例适配步骤才生成 `annotation_case.v1`。

## 3. 旧 AI JSON 的定位

旧 AI JSON 保留原文件，不覆盖、不改写。迁移时使用 `legacy_ai_adapter` 生成新的 V2 case，并在 `_migration.provenance` 中保留旧文件、案例序号、旧数据库导入信息和映射说明。

旧 AI JSON 可以作为：

- V2 初始机器案例的来源；
- AI 输出格式迁移和回归测试材料；
- 现有问题、证据、字词关系和过程文本的整理结果；
- 后续人工审校任务的候选队列。

旧 `dictionary.db` 也不需要舍弃，但它的性质不同：它是旧 parser/importer 产出的机器库。V2 只做机械字段映射和可追溯再加工，保留旧 case/term/evidence ID 及缺失链接，不把旧的 `确定`、`草稿` 或既有结论重新解释成人工确认。

当前两类“机器/AI”材料必须分开说：网站主数据库 `02-数据库/data/dictionary.db` 不是 DeepSeek 输出，而是 `02-数据库/main/source.txt -> parser.py -> importer.py` 的机器解析结果；`02-数据库/data/annotations.db` 才是 DOCX/full JSON 经 DeepSeek 规范化后形成的 17 条 AI 标注工作稿。二者都可以进入 V2 机器工作库，但 `origin`、上游文件和再加工类型必须分开记录。

旧 AI JSON 不可以直接作为：

- 人工 gold case；
- benchmark 标准答案；
- 主库或网站的正式结论；
- `certainty=确定` 的人工确认凭据。

## 4. 统一数据库与状态

V2 工作数据库默认位于 `v2/data/real_runs/annotation_v2.db`（正式部署时可配置路径），不是旧 `02-数据库/main` 的直接覆盖。数据库中机器和人工记录共用 `annotation_cases`，通过以下字段区分：

| 字段 | 作用 | 例值 |
| --- | --- | --- |
| `origin` | 记录案例来源 | `legacy_ai_json_reprocessing`、`legacy_dictionary_db_reprocessing`、`original_markdown_ai`、`original_markdown_machine_extraction` |
| `machine_status` | 可查询的机器状态 | `pending`、`draft`、`approved`、`rejected` |
| `human_status` | 可查询的人工状态 | `pending`、`approved`、`rejected`、`uncertain` |
| `review_status` | SQL 查询用的人工状态镜像 | 与 `human_status` 同步 |
| `lifecycle` | 案例晋级阶段 | `machine_draft`、`human_review`、`gold`、`rejected` |
| `machine_result_json` | 模型/parser/validator 输出 | 保留校验器、错误和版本信息 |
| `human_review_json` | 人工审校结果 | 未审校时必须保留 `pending` |
| `case_json` | 完整 V2 案例 | 保留五步、关系、证据和迁移信息 |

案例的 `_migration` 必须说明来源层和再加工类型：`machine_output_reprocessing` 表示对旧机器库/旧机器产出的再加工；`original_text_machine_extraction` 表示直接对王氏原文做 parser/candidate/auditor 抽取；`original_text_ai_generation` 表示原文候选经 AI 再加工；旧 AI JSON 则用 `legacy_ai_json_reprocessing` 表示其迁移路径。来源文件、来源记录 ID、source/passage/candidate ID、上游 revision、模型和 prompt（若有）都应随记录保存。它们只说明“材料从哪里来、经过什么处理”，不证明学术结论正确。

`target_work` 表示被考据作品的单值兼容字段；无法从原始材料确认唯一对象时不得猜测，使用 `target_works=[]` 和 `target_scope.status=unresolved` 保留未决状态。`evidence_state=source_no_citation` 表示原文明确没有书证，不能用空字符串或伪造引文冒充完整案例。

机器可以根据旧 evidence 中明确给出的 `source_work` 生成 `target_works` 候选，但这只是缩小核查范围；此类记录必须标记 `target_scope.status=machine_inferred`、`confidence=candidate_only`，不能写入 resolved `target_work`，也不能因此把案例升级为 `machine approved`。当前机器侧已为 12 条案例生成候选范围，另有 1 条没有 evidence、没有候选范围的案例。

机器案例通过校验后写入 `lifecycle=machine_draft`；人工开始处理时进入 `human_review`；只有人工通过后才能进入 `lifecycle=gold`。任何页面、统计或 benchmark 默认不得把 `machine_draft` 当作 gold。

## 5. 入库规则

机器结果可以提前入库，但必须先完成：

1. `annotation_case.v1` 结构校验；
2. 必填字段、关系类型、状态枚举和模板标记校验；
3. `source_passage_id` 和 `evidences[].passage_id` 存在性校验；
4. quote 在对应 passage 中逐字命中，或明确标记为保守规范化命中；
5. source/passage/quote 的来源路径、上游 revision 和字符定位已保存；
6. `machine_result` 与 `human_review` 独立存在，且人工状态初始为 `pending`。

结构无法构成案例的结果应进入 `rejected`；如果案例结构可保存但 target_work、外部底本或语义关系仍未决，可以进入 `machine_draft`，同时在 `machine_result` 中保留明确错误/待办。两种情况都不得进入 gold；应保留运行报告和错误信息，供修复或人工处理。

外部引文必须单独处理：如果 quote 不在当前已登记的 canonical passage 中，不能标记为 `passed`，也不能因为旧 AI JSON 的上下文中出现了相同文字就视为已完成来源核验。此类 evidence 保留在机器案例中，标记为 `unchecked`，并登记到 `external_source_registry`；`source_resolution=secondary_citation_match` 只表示引文在王氏正文中再次出现，`source_resolution=external_source_pending` 表示外部底本尚未登记，二者都不是原典核验通过。待补齐外部原典、建立 passage 后再重新执行 quote 校验。

## 6. quote 与来源定位规则

quote 校验是内容溯源校验，必须保留。它用于确认 AI 或迁移程序没有引用错 passage、制造不存在的引文或在复制过程中改写引文。

来源版本依靠稳定的 `work_key + source_file`、Git 历史或上游 revision 记录；引文完整性依靠 passage 绑定、字符偏移和字符串匹配。任何自动记录都不证明学术结论正确，也不能替代人工审校。

规范化匹配只做 Unicode 兼容形式和空白归一，不自动繁简转换、不自动修复异体字、不自动接受 OCR 字符替换。非逐字命中必须单独标记，不能伪装成严格命中。

## 7. “完成”与“未完成”的边界

以下可以称为“V2 机器链路已跑通”：真实来源能生成 passage，案例能通过 V2 校验，机器记录能进入统一数据库，人工状态仍为 `pending`。

以下才可以称为“案例已成为 gold”：有可追溯人工审校者、审校时间、审校结果和必要修改记录，并且 `human_status=approved`、`lifecycle=gold`。

机器案例数量、机器校验通过数量和 gold case 数量必须分开统计。任何旧字段 `草稿`、`确定`、`已校对` 都必须保留原值并注明来源，不能直接改名后当作 V2 人工状态。
