# 工程实施规范

本文是当前项目的工程化指导。它只写已经确认的方向、字段和流程，后续写代码、改 schema、做标注导入时以此为准。

本文定位：给开发和数据整理使用，重点是"怎么做"。这里的字段、流程、schema、校验规则应尽量无歧义；问题争论和取舍理由不在本文展开，见 `04-决策记录.md`。

## 1. 总体架构

项目分三层：原文层、候选层、审校层。

```text
04/05 原始文献
  -> markdown_preprocess
  -> passages / inline_notes / works / citations
  -> parser candidates
  -> ai_input_json -> ai_output_json
  -> machine validation
  -> annotations.db human_review
  -> reviewed cases / optional migration to main db
```

### 1.1 三个数据库边界

| 数据库 | 责任 | 可删除重建吗 | 是否直接展示 |
| --- | --- | --- | --- |
| `candidate.db` / `workspace.db` | passage preview、标题异常、parser 候选、AI 运行记录 | 可以反复重建 | 默认不直接展示 |
| `annotations.db` | 人工标注、五步、AI 草稿、人工审校、gold cases | 不应随意重建 | 可展示审校状态和标注案例 |
| `main.db` / `dictionary.db v2` | 长期主库、网站索引、已整理案例、terms 重组结果 | 不应随意重建 | 是网站主展示来源 |

数据流：`candidate.db -> annotations.db -> main.db -> website snapshot`。

主库 `dictionary.db` 的定位是规则抽取和检索索引库，不再继续扩展模板化研究结论。人工库 `annotations.db` 的定位是人工标注、AI 草稿和审校工作库，只有已审校案例才可作为 gold cases、benchmark 或迁移到主库的来源。

不建议从旧 `terms` 反推 case。新主库的字词应从已整理案例和 `term_occurrences` 反向生成。

## 2. 原文输入

四部 Markdown 是新 passage 层的主输入：`04-项目文献/A-原著原典/广雅疏证_王念孙.md`、`经义述闻_王引之.md`、`经传释词_王引之.md`、`读书杂志_王念孙.md`。`02-数据库/main/source.txt` 保留为旧 parser 兼容输入和对照材料。

输入文档可以完全去掉 `<small>` 标签。要求是：标签内文字不能丢；如果需要小字号来源审计，则从原 DOCX 或保留 small 的归档 Markdown 重建 `inline_notes[]`。没有 small 归档时也不阻塞 parser，只是 `source_marker` 只能标为 `not_available`。

## 3. 标题与 passage

统一采用三层标题，不追求古籍"章/卷/篇"术语的绝对准确。

| 字段 | 来源 | 说明 |
| --- | --- | --- |
| `document_title` | H1 或文件名 | 文件级作品名，如 `经传释词_王引之` |
| `section_title` | H2；缺 H2 时合成 | 大单元；`经传释词` H2=0，需要从卷名 H3 或 default section 合成 |
| `entry_title` | H3 | 统一称"条目标题"，具体含义由 `entry_kind` 辅助区分 |

`entry_kind` 不是主定位键，只作辅助，可取：`preface`、`section`、`volume`、`term_group`、`case_title`、`function_word`、`editorial`、`unknown`。

每个 passage 至少保存：

```text
passage_id
work_key
document_title
section_title
entry_title
entry_kind
local_ordinal
raw_text
plain_text
normalized_text
raw_text_sha256
normalized_text_sha256
md_line_start
md_line_end
source_note
```

定位采用多重锚，不靠单一页码或行号：`work_key + title_path + local_ordinal + raw_text_sha256 + normalized_text_sha256 + quote_exact + quote_offset`。行号只作本地跳转，quote 和 hash 才负责证据级追溯。

以 `广雅疏证`"古、昔、先……始也"为例，passage JSON 最小格式：

```json
{
  "work_key": "guangya_shuzheng",
  "title_path": ["廣雅疏證卷第一上", "釋詁"],
  "local_ordinal": 1,
  "md_line_start": 55,
  "md_line_end": 75,
  "raw_text": "古、昔、先、創、方、作、造、朔、萌、芽、本、根、櫱、鼃、 <small>戶瓜反</small> 䔞、 <small>律</small> 昌、孟、鼻、業，始也。...",
  "plain_text": "古、昔、先、創、方、作、造、朔、萌、芽、本、根、櫱、鼃、戶瓜反 䔞、律 昌、孟、鼻、業，始也。...",
  "raw_text_sha256": "..."
}
```

## 4. 小字信息

`<small>` 是 DOCX 小字号 run 的转写，不是长期正文标签。工作文本应去掉 `<small>` 标签，小字内容同权并入正文；来源审计层用 `inline_notes[]` 保存其原本来自小字号。

`inline_notes[]` 最小字段：

```json
{
  "note_id": "gy_sz_000001",
  "passage_id": "...",
  "text": "戶瓜反",
  "start_char": 42,
  "end_char": 45,
  "note_type": "fanqie",
  "source_marker": "docx_small_run",
  "confidence": "rule_high"
}
```

`note_type` 初始范围：`fanqie`、`phonetic_note`、`variant_or_collation`、`supplement`、`editorial_note`、`plain_note`、`unknown`。

## 5. Parser

parser v2 的目标不是直接生成定论 case，而是生成候选和损耗报告。

纯机器方案分五步：

| 步骤 | 目标 | 具体做法 |
| --- | --- | --- |
| Markdown 预处理 | 把 md 变成可解析文本 | 解析标题、段落、`<small>`、脚注；生成 raw_text/plain_text/inline_notes |
| passage 切分 | 先定位，不解释 | 按 work > 卷 > 篇/条 > 段落序号切块，记录行号和 hash |
| candidate 抽取 | 给出候选，不直接定稿 | 识别词头行、训义、引用书名、补正、校勘、反切、小字角色；输出置信度和命中规则 |
| rule_auditor | 机器自动标记风险 | 对每个候选写 rule_hits、risk_flags、skipped_reason，区分假阳风险和假阴风险 |
| human_preview | 人工抽检高风险项 | 把高风险候选和 skipped 列给人看，不直接写成确定 case；确认通过后进入 AI 辅助复核 |

候选输出分三类：

| 输出 | 作用 |
| --- | --- |
| `parsed_items` | 机器认为结构较稳定的候选 |
| `candidate_items` | 像条目但风险较高的候选 |
| `skipped_items` | 被跳过的段落、跳过原因和风险规则 |

每条候选都应带 `rule_hits`、`risk_flags`、`skipped_reason` 或 `need_review`。假阳和假阴要可审计，不要只给最终数量。

风险标记示例——一个词头行可以带：

```json
{
  "has_small_tags": true,
  "gloss_single_char": true,
  "has_multiple_books": true,
  "shared_body": true,
  "possible_collapsed_terms": true
}
```

这样即使抽错，也能知道为什么错。

### 5.1 AI 辅助方案

纯机器五步产出 `candidate_items` 和 `skipped_items` 后，AI 辅助方案接手进行语义复核。机器第三步（candidate 抽取）的输出作为 AI 第一阶段（候选复核）的输入，机器第四步（rule_auditor）中的 skipped 项作为 AI 第四阶段（异常解释）的输入。

AI 辅助方案分四阶段：

| 阶段 | AI 输入 | AI 输出 | 审计要求 |
| --- | --- | --- | --- |
| 候选复核 | 单个 passage + 机器候选 | 判断是否为词头/校勘/补正/证据 | quote 必须原文子串 |
| 关系抽取 | passage + term candidates | 原字/训字/校正字关系 | 必须给 source span |
| 五步草稿 | 已确认 case + evidence | 发疑、设问、取证、释理、结论草稿 | 允许缺项，不许硬凑 |
| 异常解释 | skipped 或低置信候选 | 为什么难判、建议人工看什么 | 只作审校提示 |

纯机器方案负责"稳定、可复现、可批量"；AI 辅助方案负责"复杂语义、关系初判、五步草稿"。二者共同原则：AI 输出永远是候选或草稿，不能自动覆盖主库。

## 6. 主库 v2

主库 v2 保存裸原文结构化和候选索引，不保存伪人工结论。建议核心表：

```text
passages
inline_notes
works
work_alias_candidates
citations
evidences
terms
term_occurrences
term_core_profiles
```

`works` 改为动态规范表。已知作品直接关联；未知作品进入候选。引用处必须同时保存原标签和规范映射，例如：

```json
{
  "raw_work_label": "皋陶謨",
  "normalized_work": "尚书",
  "chapter_or_section": "皋陶謨",
  "mapping_rule": "chapter_to_work",
  "confidence": "high"
}
```

`terms` 只保存规范字词。全部出现、训义、证据和关系进入 `term_occurrences`。`term_core_profiles` 不直接承载全部解释，而保存代表性 `primary_occurrence_ids`、`primary_case_ids` 和可生成摘要。

## 7. 关系与方法

`term_type` 不进入核心结构。`category` 也不作为核心字段，只可从其他字段生成页面分组。

核心对使用者表现为两块：`term_relations` 和 `method_profile`。其中 `method_profile` 内部再分现代方法概念和二王原文表达。

| 字段 | 回答的问题 | 示例 |
| --- | --- | --- |
| `relation_type` | 原文对象和训释对象是什么结论关系 | `训释`、`通假`、`误字`、`当作`、`虚词用法` |
| `method_profile.concepts` | 用现代术语概括用了什么方法 | `声训`、`书证`、`义证`、`校勘`、`旧注辨驳` |
| `method_profile.expressions` | 二王原文中实际怎么说 | `一声之转`、`古声同`、`今本譌作`、`當作` |

不要用方法词表替代 `relation_type`。方法词表替代的是旧的笼统 `method_tags`：`method_profile.concepts` 是现代规范层，`method_profile.expressions` 是二王表达层。`relation_type` 是结论关系，不能和方法混在一起。

以"造舟于河"为例：`relation_type=训释`，`relation_subtype=声转释义`；`method_profile.concepts=[声训, 书证, 义证, 旧注辨驳, 比较互证]`；`method_profile.expressions=[造之言曹, 造、次一声之转]`。

当前 `method_profile.concepts` 是候选级方法词表，不是已审定全集。`训诂术语.md`、王宁《训诂学原理》和课程大纲可作为候选来源；这些概念的 `review_status` 初始为 `pending`，第一批 `approved` 概念应从 30-50 个 gold cases 的人工标注中反向确认。候选级不阻塞 passage、candidate、人工标注和 AI 草稿；只是不应把候选词表当作无需审校的自动分类结果。

第一版 `relation_type` 用一级关系，细项放 `relation_subtype` 或 `note`：

| 一级 `relation_type` | 细项候选 |
| --- | --- |
| `训释` | 同义、反训、声转释义、义界 |
| `校勘` | 误字、当作、衍文、脱文、倒文 |
| `字际关系` | 通假、异体、古今字 |
| `虚词用法` | 语气、连词、介词、代词、助词 |
| `句义解释` | 句读、语法、上下文解释 |
| `未定` | 待核、疑似多类 |

## 8. 人工库

人工库 API/JSON 层以一个 case 为中心，五步不再放 `steps` 容器，而是五个并列字段。

最小 case 结构：

```json
{
  "case_title": "平原之隰",
  "source_work": "读书杂志",
  "source_passage_id": "...",
  "target_work": "管子",
  "target_text": "平原之隰，奚有於高",
  "submitted_by": "human:...",
  "reviewed_by": null,
  "term_relations": [
    {
      "source_term": "原",
      "target_term": "隰",
      "relation_type": "当作",
      "relation_subtype": "误字",
      "note": "今本原字疑误"
    }
  ],
  "method_profile": {
    "concepts": ["校勘", "书证", "义证"],
    "expressions": []
  },
  "evidences": [
    {
      "quote": "言平隰之泽，虽有小封，不成于高。",
      "evidence_role": "支持校改",
      "passage_id": "...",
      "quote_sha256": "..."
    }
  ],
  "problem_discovery": "今本\"平原之隰\"与注文\"小封\"不协。",
  "research_question": "是否应改读为\"平隰之封\"。",
  "evidence_collection": "取《管子》注文与上下文为证。",
  "reasoning": "由注文\"小封\"反证今本不协。",
  "conclusion": "当作\"平隰之封\"。",
  "machine_result": {"status": "pending"},
  "human_review": {"status": "pending"}
}
```

JSON 字符串中如果原文或说明文字含 ASCII 双引号 `"`，必须写成 `\"`；不要把原文引号粗暴改成书名号。中文引号 `“”`、书名号 `《》`、直角引号 `「」`、双直角引号 `『』` 本身不破坏 JSON，但仍应保留原文原貌，并用 JSON 解析器校验代码块。

`annotation_cases` 是表，`case_title` 是字段。`term_relations[]` 不能被单个 `source_term + target_term` 覆盖，因为一个 case 可以有多组关系。

## 9. AI 标注链路

四类 JSON 分工：

| JSON | 任务 |
| --- | --- |
| `source_json/full_json` | 档案层，完整保存 DOCX/Markdown 抽取结果 |
| `ai_input_json` | 任务包，只放模型本次需要看的 passage、批注、schema、术语表 |
| `ai_output_json` | 草稿层，保存模型输出，不等于入库 |
| `db_import_json` | 入库层，只放校验通过、字段规范、带 hash 和 review 初态的数据 |

AI 不能直接读取本地文件。本地程序应提供工具：`search_passages`、`get_passage`、`validate_quote`、`get_method_vocab`。模型只拿 top-k passage 和 schema，quote 校验、hash 校验、枚举校验在本地做。

DeepSeek 推荐默认：

```python
client_base_url = "https://api.deepseek.com"
model = os.getenv("DEEPSEEK_MODEL", "deepseek-v4-flash")
temperature = 0
max_tokens = 4096
response_format = {"type": "json_object"}
timeout_seconds = 60
retry = {"max_attempts": 3, "backoff": "exponential"}
```

所有 AI 输出必须经过 `validate_ai_json()` 和人工审校，不能自动入主库。

## 10. 评估、预算和训练

### 10.1 命名规范

现阶段使用 `gold cases/dev set/test set/benchmark`，少说"训练集"。只有真的做 SFT、LoRA、PEFT 或 RAFT 时，才从已审校 gold cases 中切 training set。

全项目统一使用 `machine_result` 和 `human_review`。不再区分 JSON/API 层和 SQL 层命名；即使数据库中保存的是 JSON 文本，也仍使用同名字段，由 schema、字段类型或注释说明存储形态。不要再使用 `machine_draft_json`、`machine_result_json`、`human_review_json`。

| 名称 | 是否训练模型 | 用途 |
| --- | --- | --- |
| gold set | 不一定 | 人工确认的标准答案集合 |
| dev set | 不一定 | 调 parser、prompt、schema、RAG 的开发样本 |
| test set | 不训练 | 锁定不动，用来检验改动是否真的变好 |
| benchmark | 不训练 | 一套任务、数据和指标 |
| training set | 只有微调时才需要 | 用于 SFT/LoRA/RAFT 等训练 |

### 10.1.1 Status 枚举

所有 `status` / `review_status` 必须来自同一个全局小枚举：`pending`、`draft`、`approved`、`rejected`、`uncertain`。不同字段只取其中的必要子集，不再另造同义值。退回修改统一用 `rejected`，具体原因写入 `notes` 或 `review_result`。

| 字段 | 枚举值 | 含义 |
| --- | --- | --- |
| `machine_result.status` | `pending` / `draft` / `approved` / `rejected` | 未运行或待生成 / 已生成草稿 / 机器校验通过 / 机器校验失败 |
| `human_review.status` | `pending` / `approved` / `rejected` / `uncertain` | 待审 / 通过 / 退回或拒绝 / 存疑 |
| SQL `review_status` | `pending` / `approved` / `rejected` / `uncertain` | 可查询的人工审校汇总状态 |
| `method_concepts.review_status` | `pending` / `approved` / `rejected` | 候选待审 / 已审定 / 不采用 |

### 10.2 Benchmark 评分流程

1. 人工选 30-50 个 gold cases，覆盖四书。
2. 每个 gold case 固定标准答案：passage、target_text、term_relations、evidences、relation_type、method_profile、五步、conclusion。
3. parser 跑一遍，评覆盖率、误报率、跳过原因是否合理。
4. AI 在同样输入下生成草稿，评 quote 命中率、关系准确率、方法概念准确率、五步缺项率。
5. 人工审校记录修改量，形成 `ai_revision_rate`。
6. 每次规则或 prompt 改动后重跑 benchmark。

### 10.3 初始指标

| 指标 | 说明 | 评估对象 |
| --- | --- | --- |
| `quote_match_rate` | AI/候选 quote 是否能在 passage 中匹配 | AI 草稿 |
| `passage_hit_rate` | 是否找到正确 passage | 整体链路 |
| `term_relation_f1` | 原文对象/训释对象关系是否完整 | AI 草稿 |
| `relation_type_accuracy` | 关系类型是否与 gold 一致 | AI 草稿 |
| `method_concept_accuracy` | 现代方法概念是否合理 | AI 草稿 |
| `step_completion_rate` | 五步字段是否完整或正确标缺 | AI 草稿 |
| `human_revision_rate` | 人工修改比例 | 整体链路 |

### 10.4 预算

预算硬上限 10000 元。优先路线是 API 模型 + 本地 SQLite/FTS + 少量向量检索 + 强校验。不优先本地部署大模型，不优先 LoRA/PEFT/RAFT。没有足够已审校 gold cases 前，不训练模型。

## 11. 实施顺序

1. **固定工作 Markdown**：标题重建、去 `<small>` 标签但保留文字，原始版本归档。生成 `plain_text`、`inline_notes`、标题路径和 hash。
2. **生成 passage**：`passages.jsonl`、`inline_notes.jsonl`、`title_anomalies.jsonl`。统一 `work_title / section_title / entry_title` 三层；`经传释词` 缺 H2 时合成 section。
3. **建 candidate.db**：跑 parser v2，输出 `parsed_items/candidate_items/skipped_items/audit_flags`，量化假阳/假阴损耗。
4. **建 AI input builder**：只给模型 top-k passage 和 schema。
5. **建 `validate_ai_json()`**：先做 quote/schema/enum/hash 校验。改 AI JSON 流程为 `source_json -> ai_input_json -> ai_output_json -> db_import_json`，每层职责单一。
6. **组织人工标注**：用本文 §8 模板，向成员提供可复制的 JSON 模板和最低填写指引，启动首批标注任务。
7. **建 annotations.db v2 与人工库 schema**：建库保存五步、AI 草稿和人工审校。设计人工库表结构（见 §15）——统一 case JSON，底层拆 `term_relations / evidences / review`，五步保持五个固定字段。
8. **实现本地 AI 工具**：`search_passages / get_passage / validate_quote / get_method_vocab`，控制 top-k、窗口和缓存。
9. **建立 benchmark**：选 30-50 个 gold cases（以"造舟于河"等为起点），先评估 parser/RAG/AI 草稿质量。
10. **迁移到 main.db v2**：从已审校 annotation cases 迁移。设计主库 v2 schema（见 §14），停止扩展模板化 case。
11. **网站改造**：field registry + view config 驱动展示。
12. **训练评估**：最后再考虑。没有足够已审校 gold cases 前，不做 LoRA/RAFT/PEFT。

## 13. Passage 生成规则

输入：四部 Markdown 或去标签 Markdown。输出：`passages.jsonl` 和 `inline_notes.jsonl`。

数据清洗按以下顺序执行：

1. **去掉转换说明**——识别并移除文件开头的转换说明 blockquote，原文存入 `source_note`。
2. **标题清洗**——移除标题中的 Markdown `#` 前缀；移除 `<small>` 标签但将其内文字保留到 `inline_notes`；压缩多余空白，生成 `clean_title`。
3. **标题分类**——H1 -> `document_title`；H2 -> `section_title`；H3 -> `entry_title`。`经传释词` 缺 H2 时，从 H3 中识别卷名合成 `section_title`，后续 H3 作为 `entry_title`。
4. **条目类型初判**——为每个 entry 标记 `entry_kind`（preface / section / volume / term_group / case_title / function_word / editorial / unknown），仅辅助，不影响后续 passage 切分。
5. **正文清洗**——去掉 `<small>` 标签，保留标签内文字；若能识别小字来源，写 `inline_notes[]`。生成三个版本：`raw_text`（保留原始转写）、`plain_text`（去 HTML 标签保留文字）、`normalized_text`（空白归一）。正文按 entry 下自然段切 passage；若段落过短，可与相邻段合并，合并规则要记录。
6. **生成 passage id**——组合 `work_key + title_path_slug + local_ordinal` 生成可读 id；对 raw_text 和 normalized_text 分别计算 sha256 作为漂移校验指纹。

`normalized_text` 只做保守归一：压缩空白、统一全半角空格、去 Markdown 标签。不要自动繁简转换，不要改异体字。

  source_passage_id TEXT,

  machine_result TEXT,

);

## 16. 校验规则

`validate_ai_json()` 和入库前校验至少检查：

| 校验 | 目标 | 执行方式 | 失败处理 |
| --- | --- | --- | --- |
| schema 校验 | JSON 字段完整、类型正确 | `jsonschema.validate()` 或 Pydantic，对照 `annotation_case.v1` schema | 拒绝入库 |
| quote 校验 | quote 是 passage 子串或可归一匹配 | `quote_text in passage.plain_text`，必要时空白归一后再匹配 | 不通过则标 `quote_check=failed` |
| hash 校验 | source、passage、quote 未被悄悄改写 | 入库前对比 `sha256(当前内容)` 与已有记录的 hash 值 | 标为 `needs_review` |
| enum 校验 | relation_type、relation_subtype、status 在受控表中；method_concept 至少标明 pending/approved/free_text | 查 `method_concepts`、`relation_types`、status 枚举表；不在表中的标 `unlisted` | 标为 `rejected` 或写入 review notes，不直接删除原始数据 |
| 五步校验 | 五个字段存在；缺项显式为空 | 检查 5 个 key 均存在；`null` 或 `""` 视为有效缺项 | 缺项标为 `needs_review` |
| 审校校验 | machine_result 与 human_review 不混写 | 两字段必须独立填写，不得互相复制 | 拒绝混写 |
| case_title 校验 | case_title 非空 | 检查字段非空 | 拒绝入库 |
| passage_id 校验 | source_passage_id 若存在，必须在 passages 表中 | 查 passages 表 | 标为 `needs_review` |
| AI quote 来源校验 | AI 输出不得新增无来源 quote | 逐一比对 AI 输出中的 quote 与输入材料 | 拒绝入库 |

quote 校验第一版采用严格子串匹配；第二版再加入空白、标点归一匹配。不要做繁简转换自动匹配，避免误配。

## 17. AI 本地检索 workflow

第一版不必急做 tool calls，可以先做本地检索拼 prompt。

```text
用户/脚本选择 case 或 candidate
  -> search_passages(query, filters)
  -> 取 top-k passage 和周边窗口
  -> build_ai_input_json
  -> DeepSeek JSON mode
  -> ai_output_json
  -> validate_ai_json
  -> db_import_json
  -> 人工审校
```

`ai_input_json` 必须限制大小。建议默认 top-k=5，每个 passage 截断到候选前后各 500-800 字。长案例可人工扩展窗口。

## 18. 网站展示

网站展示采用配置驱动方式，不提前在页面中写死所有字段。流程为：数据库 schema -> API 字段注册 -> view_config -> 前端组件。

`view_config.json` 必须引用后端已经暴露的字段路径。普通字段可以自动渲染；复杂字段（quote 高亮、五步、term relation 图、审校状态）仍需要专门组件。

```json
{
  "field_registry": {
    "case_title": {"label": "案例标题", "type": "text"},
    "term_relations": {"label": "字词关系", "type": "relation_list"},
    "method_profile.concepts": {"label": "现代方法", "type": "tag_list"},
    "human_review.status": {"label": "审校状态", "type": "status"}
  },
  "views": [
    {
      "view_id": "annotation_case_detail",
      "title_field": "case_title",
      "sections": [
        {"title": "基本信息", "fields": ["source_work", "target_work", "target_text"]},
        {"title": "字词关系", "component": "term_relations"},
        {"title": "方法", "fields": ["method_profile.concepts"]},
        {"title": "五步过程", "fields": ["problem_discovery", "research_question", "evidence_collection", "reasoning", "conclusion"]},
        {"title": "审校", "fields": ["machine_result.status", "human_review.status"]}
      ]
    }
  ]
}
```

第一版先做只读 preview：case 列表、case JSON 展示、quote 高亮、AI 草稿与人工审校状态区分。等 schema 稳定后，再把详情页做成配置驱动组件。
