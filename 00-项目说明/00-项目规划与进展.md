# 项目规划与进展

> 更新日期：2026-08-30
>
> 当前 V2 工程、文件包和数据库口径以 `03-工程、文件包与V2规范.md` 为准。

## 当前判断

项目已经越过“用 1 个 passage 和 2 个案例验证 schema”的原型阶段。Markdown 预处理、passage 构建、候选审计、旧数据适配、统一工作库、机器校验、工作队列、审校任务包、只读网站接口和受控审校事务均已实现并通过现有测试。

当前不能把“机器链路跑通”写成“V2 知识库完成”。工作库中的 7,581 个案例全部仍是机器草稿和人工待审状态，`review_events=0`、gold=0；下一阶段的中心是解决来源与目标定位并开展真实人工审校。

## 已完成的工程阶段

1. 四部王氏原典已生成稳定来源登记和 passage，并完成 6,749 个候选项的机器审计。
2. 旧 `dictionary.db`、旧 AI JSON 和原文候选已经适配到同一 `annotation_case.v1` 合约和同一 V2 工作数据库。
3. 当前 V2 工作库位于 `v2/data/real_runs/annotation_v2.db`，保存 35 个来源文档、15,496 个 passages、6,749 个候选、7,581 个案例和 13,990 条证据。
4. 机器状态、人工状态和 lifecycle 已分离；结构、外键、来源、队列和状态边界验证通过。
5. 目标典籍、外部来源、外部 passage/quote 和案例人工审校已经分别生成队列与 `review_task.v1` 任务包。
6. 网站 `/v2-database.html` 已提供案例浏览和质量报告，案例从详情进入五步 AI 审校；正式写入仍通过独立开关和受控事务提交。

## 当前未完成边界

1. 7,581 个案例尚无人工审校事件，不能进入 gold 或 benchmark。
2. 100 个外部来源尚未登记独立 canonical 底本；121 条外部证据仍在 passage/quote 处理队列中。
3. 7,962 个 target-work resolution 项仍需消歧；机器候选只能缩小范围，不能替代人工确认。
4. 7,241 条证据尚未完成 canonical quote 核验；王氏正文中的二次命中和 legacy-derived passage 都不能冒充外部原典核验。
5. CloudBase 的 V2 数据卷和 V2 API 尚无当前验证证据；Railway 是已验证的线上 V2 入口。

## 下一阶段优先级

### P0：建立可审计的人工作业

1. 先处理 target-work、外部来源和外部 passage 队列中会阻塞案例审批的项目。
2. 选择少量来源清楚、引文可核的真实案例开展审校 pilot，记录稳定 reviewer、field decisions、evidence decisions 和唯一 `operation_id`。
3. 每次写入后重建工作队列、审校任务包和 V2 验证报告，确认状态变化可追溯且没有绕过 gold gate。

### P1：形成首批 gold 与 benchmark

1. 在 canonical target passage、quote 校验和字段决定齐全后审批首批案例。
2. 先形成覆盖不同著作、关系类型和难度的 30—50 条人工 gold cases，再建立 benchmark。
3. 机器数量、人工通过数量和 benchmark 数量始终分开统计。

### P2：正式展示与长期维护

1. 设计 gold 到正式主库/网站快照的导出层，不直接覆盖旧兼容库。
2. 明确 Railway/CloudBase 的持久卷、备份、恢复和只读/写入开关策略。
3. 在真实审校反馈稳定后再调整 schema、任务粒度和成员填写项，避免凭空扩表。

## 阶段完成标准

下一阶段不能以“又生成了文件”作为完成标准。至少需要：存在真实人工审校事件；通过案例满足 canonical target passage 与 quote gate；gold 数量可从数据库独立查询；任务包、数据库和验证报告一致；网站不会把 machine draft 展示成已审校结论。
# 项目规划与进展

> 更新日期：2026-09-19
>
> 当前文件只回答三件事：中期要完成什么、为什么做这些、什么情况下停止扩张。

## 1. 当前判断

项目已经完成了较大规模的机器工程底座：四部王氏原典已建立 passage 和候选层，旧 AI JSON 与旧机器库已进入统一 V2 工作库，机器状态和人工状态分离，网站已有 V2 浏览和五步 AI 审校入口。

但工程底座还不是中期研究成果。当前最重要的缺口是：

明确复核命题 → 真实人工判断 → 修订 → 确认版本 → 可追溯展示。

因此中期不再以增加机器案例、扩展旧 parser 或清洗全库为主要目标，而以少量案例的真实结构化复核为中心。

## 2. 中期目标

本阶段成果名称统一为：

> 考据过程结构化复核案例

目标是完成三条核心案例，第四条只在前三条和文件归档稳定后再考虑：

| 顺序 | 案例 | 当前工作库性质 | 中期作用 |
| --- | --- | --- | --- |
| 1 | 平原之隰 | legacy-ai:1 | 校准人工判断标准和真实工时 |
| 2 | 譕臣 | legacy-ai:2 | 与前例形成有限的方法比较 |
| 3 | 造舟于河 | candidate-shell:jingyi_shuwen_1103_candidate | 将既有代表案例转成新的中期增量 |
| 4 | 已，语终辞也 | legacy-ai:14 | 可选扩展，不影响前三例完成 |

三例完成仍必须以质量标准为前提；不能为了凑数量把存疑案例强行写成完成。

## 3. 结构化复核完成标准

一条案例必须同时满足：

1. 案例边界明确，围绕一个主要判断组织上下文。
2. 原文文件、位置和使用版本固定。
3. 关键解释可以逐项回到原文或明确列出的材料。
4. 人工判断每条关键证据承担的作用，检查漏步、跳步和过度推断。
5. 明确区分王氏主张、项目对论证的重建和项目尚未独立验证的内容。
6. 保存真实人工意见、修订依据、确认版本和未决事项。

“结构化复核完成”不等于“全部外部底本已核验”，不等于“王氏结论已被项目独立证明”，也不自动等于 V2 lifecycle=gold。

## 4. 四个工作包

| 工作包 | 预算 | 交付 |
| --- | ---: | --- |
| A 案例复核 | 9 小时 | 首例校准，随后完成其余核心案例的人工判断、修订和确认 |
| B 证据与版本归档 | 3 小时 | 固定原文、AI 初稿、人工意见、修订稿、确认稿和展示稿的一一对应 |
| C 规则与方法提炼 | 2 小时 | 一页操作规范、一组有限案例比较、Agent 帮助与错误记录 |
| D 固定成果展示 | 4 小时 | 从确认稿生成一个稳定阅读入口 |
| 返工缓冲 | 2 小时 | 处理引用、版本、文字和展示不一致 |

执行顺序固定为：

A 首例校准 → B 同步建版本链 → A 完成其余案例 → C 提炼 → D 展示。

B 不能等所有案例完成后再补，C 不能脱离真实修改预先编写，D 的正式内容只能来自确认版本。

## 5. 文件包优先，V2 接入从严

中期案例以 v2/research/midterm-pilot/ 下的文件包作为唯一编辑源。原典、旧数据库、旧 AI JSON 和既有 V2 记录保持只读。

第一例文件包稳定后，才可以在隔离副本中用不超过约一小时试接 V2 正式 review。试接受阻就停止，不让数据库接入拖延中期产出。

没有正式入库时，只能表述为：

> 已形成可追溯复核文件包，并与现有 V2 记录建立对应。

不能写成“V2 人工审校工作流已经完成入库”。

## 6. 不在本轮范围内

- 全库 7,581 个案例人工审校。
- 全部 target_work、外部来源和外部 passage 消歧。
- 全面 canonical 底本核验。
- 批量自动升 gold。
- CloudBase 部署。
- 通用 Agent 平台。
- 无关架构重构。
- 继续扩大旧 parser 的模板案例。

申报材料中的“不少于 60 条”和答辩材料中的“不少于 300 条”仍是未解决的口径冲突。本阶段三例 pilot 只能作为可信的阶段性增量，不能冒充完成其中任何一个数量指标。

## 7. 中期交付物

最终至少应有：

- 已完成案例及其复核范围；
- 每例完整的原文、版本、证据和人工意见链；
- 确认版本和固定展示版本；
- 一页可执行操作规范；
- 一组有实例支持的案例比较；
- Agent 辅助、人工阅读和人工修改时间记录；
- 未决事项清单；
- 中期成果展示入口。

## 8. 统一验收问题

沿任一已完成案例倒查：

> 展示页面中的每个关键解释，能否回到确认版本；确认版本能否回到真实人工意见和修改依据；修改依据能否回到确定的王氏原文；下一例能否用同一套规则继续处理？

不能回答其中任一环，就不能把该案例称为结构化复核完成。
