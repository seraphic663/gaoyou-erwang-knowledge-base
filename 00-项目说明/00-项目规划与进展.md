### 当前判断

现在应先做一个可跑通的 demo 标注闭环，不要先把所有缺失和重复都工程化成正式库表。原因很简单：目前最大风险不是表还不够多，而是 `Markdown -> passage -> quote 定位 -> annotation_case.v1 -> validator -> 人工库草表` 这条链还没有被真实案例验证。先把链路跑通，才能知道哪些字段真有用、哪些字段只是设计上看起来完整。

工程上最优雅、最简单、可用的做法是：先做一条薄的纵切 demo，只覆盖 1 个 passage prototype 和 2 个案例；缺失/重复问题只处理到“不阻塞 demo、不制造错误数据”的程度。不要现在就一次性重建完整主库 v2，也不要把 `relation_types`、`evidence_role`、字段级来源审计等都先做成复杂后台管理系统。

### 先做 demo，但带最小约束

第一阶段目标是验证链路，不是扩表。先建以下文件：

1. `annotation_case.v1.schema.json`
2. `passage_builder.py` 或至少 `passages.jsonl` prototype
3. `validate_annotation_case.py`
4. `examples/造舟于河.annotation.json`
5. `examples/平原之隰.annotation.json`

demo 必须覆盖这些校验：

1. `source_passage_id` / `evidences[].passage_id` 能指向 passage prototype。
2. `evidences[].quote` 能在 passage 文本中严格匹配，至少生成 `quote_sha256`。
3. `case_title`、`submitted_by`、`source_work`、`target_work`、`target_text`、`term_relations[].source_term`、`term_relations[].target_term`、`evidences[].quote`、`conclusion` 这 9 项齐全。
4. `【必填】`、`【建议】`、`【选填】` 不能进入正式样例或数据库草表。
5. `machine_result.status`、`human_review.status` 只使用文档规定的小枚举。

### 缺失问题如何处理

`passages` 是第一优先级，但第一版不需要直接改完整主库。先生成 `passages.jsonl` 或临时 `candidate.db` 里的 passage prototype，只要字段足够支持 quote 定位、hash 和回查原文即可。跑通后再决定是否迁入主库 v2。

`method_expressions -> method_concepts` 映射先用 JSON 或最小表表达即可，不要先做复杂术语系统。demo 只需要证明 `一声之转` 这类二王表达可以挂到 `声训` 这类现代方法概念。

`relation_types / relation_subtypes` 和 `evidence_role` 先做成 validator 内置词表或小 JSON 词表，不急着建后台维护表。它们的第一用途是防止成员和 AI 自由发挥，不是立刻支持复杂管理。

字段级来源审计第一版先保持粗粒度：`submitted_by`、`machine_result`、`human_review`。如果 demo 后发现多人协作会频繁改同一字段，再加 `field_provenance` 或修改日志。现在提前全字段审计会让 schema 变重。

模板标签清洗必须现在做，因为它成本低、收益高，能直接防止模板文字污染样例和数据库。

### 重复问题如何处理

`evidence_role` 和 `method_profile.concepts` 保持分层：前者只说单条证据在论证中的作用，后者说整案用了什么现代方法。validator 可以先允许少量相近词，但文档和示例必须体现两者语义不同。

`source_location` 和 `source_passage_id` 同时保留：`source_passage_id` 是主定位键，`source_location` 是人可读缓存和 passage 尚未匹配时的兜底。

审校者字段以 `human_review.reviewed_by` 为准，顶层 `reviewed_by` 只作为列表展示、旧数据兼容或 SQL 索引用的冗余字段。两处同时出现时必须一致。

`relation_note` 和 `method_profile.expressions[].quote` 可以引用同一句原文，但语义不同：前者解释 A/B 关系，后者记录二王方法性表达。不要为了去重把二者合并。

多个 `status` 可以保留，但必须带命名空间：`machine_result.status`、`human_review.status`、SQL `review_status`。前端显示时不要只写“状态”，要写“机器状态”或“审校状态”。

### 第一阶段完成标准

用 1 个 passage prototype 跑通：Markdown -> passage -> quote 定位 -> hash。

用 2 个标注案例跑通：模板 JSON -> validator -> 人工库草表。

开 2-3 人 pilot 标注前，准备一份空白模板和两份示例，不要直接全员铺开。

第一阶段结束后再回头决定哪些缺失要正式建表。若 demo 证明字段稳定，再进入主库 v2；若 demo 暴露字段负担过重，优先删减成员填写项，而不是继续加表。
