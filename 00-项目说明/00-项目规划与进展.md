# 项目规划与进展

> 当前版本：2026-09-29
>
> 本文只回答项目现在研究什么、当前阶段交付什么、下一阶段怎样扩展。数据库和运行事实以 05-当前状态与执行评估.md 及生成报告为准。

## 1. 项目核心

项目名称和历史工作可以继续使用“高邮二王考据过程知识库建设及应用”，但研究内核不应停留在数据库或网站建设。

当前统一定位是：以高邮二王考据材料为案例，把问题、出处、证据角色、推理、结论强度和未决状态组织成可追溯、可评价的考据任务，研究检索和模型系统能否在来源约束下完成证据获取、判断和核验。

数据库负责组织材料、版本和 provenance；检索负责取得候选证据；人工复核负责确认论证；后续的 agent harness 负责规定工具、流程和核验行为。网站是研究操作和成果展示层，不是项目进展的主要计量单位。

## 2. 三阶段路线

| 阶段 | 研究重点 | 当前状态 | 完成证据 |
| --- | --- | --- | --- |
| 基础设施 | 来源登记、passage、candidate、case、evidence、状态和检索 | 机器底座已形成 | V2 验证报告、队列和任务包 |
| 中期生产 | 少量考据过程结构化复核案例 | 当前主任务 | 人工决定、修订稿、确认稿、证据链和固定展示 |
| 评价研究 | benchmark-ready corpus、generic baseline、领域化 harness 和失败分析 | 后续路线 | 冻结任务集、统一预算下的比较和可复核指标 |

三阶段之间不能跳写。基础设施不等于人工确认，中期案例不自动等于 benchmark gold，研究设想不等于已经完成的 agent 实验。

## 3. 当前中期目标

本阶段成果名称统一为“考据过程结构化复核案例”。它针对一个确定的王氏文本范围，人工复核案例边界、问题、证据作用、推理关系和结论强度，并保存修订后的确认版本与未决事项。

一条案例只有同时满足以下六项，才可称为结构化复核完成：

1. 案例边界明确，围绕一个主要判断组织必要上下文。
2. 原文文件、位置和使用版本固定；影响解释的字形或异文问题已经处理，或已明确缩小判断范围。
3. 关键解释可以回到确定材料，并区分王氏原文、王氏所引材料、项目重建和项目独立查见。
4. 人工实际判断每条关键证据承担的作用，检查漏步、跳步、夸大和额外补入。
5. 王氏主张、本次复核范围和尚未独立核验的内容分开表达。
6. 保存真实人工意见、修改依据、确认版本和未决事项；实质修改后重新确认。

这一定义不等于全部外部底本已核验，不等于王氏结论已经由项目独立证明，也不自动等于 V2 gold。

## 4. 案例顺序

| 顺序 | 案例 | 当前性质 | 本阶段作用 |
| --- | --- | --- | --- |
| 1 | 平原之隰 | legacy-ai:1 | 校准人工判断和真实工时 |
| 2 | 譕臣 | legacy-ai:2 | 与首例形成有限的方法比较 |
| 3 | 造舟于河 | candidate-shell:jingyi_shuwen_1103_candidate | 将既有代表案例转成新的中期增量 |
| 4 | 已，语终辞也 | legacy-ai:14 | 只有前三例和归档稳定后才考虑 |

首例应先独立阅读王氏原文，再查看 AI 草稿，以降低锚定效应。关键来源或字形问题投入约 30 分钟仍无可控路径时，缩小命题、保留待核或换例，不降低复核标准。时间不足时依次取消第四例、V2 接入和自动化便利、页面扩展，最后才减少第三例。

## 5. 中期 20 小时工作包

| 工作包 | 预算 | 交付 | 超时处理 |
| --- | ---: | --- | --- |
| A 案例复核 | 9 小时 | 首例校准和三条核心案例的人工判断、修订、确认 | 先取消第四例，再减少核心案例 |
| B 证据与版本归档 | 3 小时 | 原文、AI 初稿、人工意见、修订稿、确认稿和展示稿的对应链 | 取消 V2 接入和自动化便利 |
| C 规则与方法提炼 | 2 小时 | 一页操作规范、有限案例比较、Agent 帮助与错误记录 | 缩为单例说明或一组比较 |
| D 固定成果展示 | 4 小时 | 从确认版本派生的稳定阅读入口 | 采用固定快照，不做通用编辑器 |
| 返工缓冲 | 2 小时 | 引用、版本、文字和展示一致性 | 不用于临时新需求 |

执行顺序固定为：首例人工校准 → 同步建立版本链 → 完成其余案例 → 从真实修改中提炼规则 → 从确认版本生成展示 → 统一验收。

## 6. 文件包和 V2

中期文件包位于 v2/research/midterm-pilot/，是本阶段案例正文和确认版本的唯一编辑源。每例至少保留稳定 case_id、原文位置和版本、AI 初稿、人工意见、修订稿、确认稿、展示稿或生成指针、未决事项和工时记录。

V2 生产数据库默认只读。第一例文件包稳定后，才可在隔离副本中限时试接正式 review；如果接入要求补全全库队列、改生产数据或消耗中期主要时间，立即停止，文件包仍作为正式中期成果。

## 7. 从中期案例到 benchmark

现有检索 benchmark 只评价 retrieval layer，不能代表端到端考据任务集。后续 benchmark-ready case 还需要明确任务问题、结构化答案、证据角色、来源状态、难度、hard negative、unresolved 规则和评价方法。

建议保持以下顺序：

1. 先完成少量真实人工确认案例。
2. 从确认稿抽取任务字段和证据角色，标记哪些内容仍不可评分。
3. 冻结训练、开发和测试边界，避免同一案例或同一证据链泄漏。
4. 在相同模型、材料、工具和预算下比较 LLM-only、普通检索/RAG、generic search agent 和 domain-specific harness。
5. 报告证据召回、错误来源、无依据陈述、答案正确率、拒答质量、人工修改量和成本。

agent harness 是后续评价对象，不是本轮必须建设的通用平台。当前五步卡首先是案例生产和审计工具。

## 8. 不在当前范围内

- 全库 7,581 个案例人工审校。
- 全部 target_work、外部来源和外部 passage 消歧。
- 全面 canonical 底本核验。
- 批量自动升 gold。
- 通用 Agent 平台、多 Agent 数量竞赛或无明确评价的聊天功能。
- 无关架构重构和继续扩大未经核验的 machine cases。

申报材料中的“不少于 60 条”和答辩材料中的“不少于 300 条”仍没有换算定义。本阶段 pilot 是独立的可信增量，不冒充完成任一数量指标。

## 9. 阶段验收

沿任一完成案例倒查：展示中的关键解释能否回到确认版本；确认版本能否回到真实人工意见和修改依据；修改依据能否回到确定的王氏原文；下一例能否使用同一套文件、复核和展示规则继续处理。

只有当上述链条闭合，并且未把案例写成精校、gold、全库完成或外部原典独立核验时，中期成果才成立。
