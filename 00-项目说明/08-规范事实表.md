## 1. 事实等级与使用规则

| 等级 | 含义 | 证据优先级 |
| --- | --- | --- |
| `current` | 当前工作区实际存在的文件、代码、数据库和数据 | 实际文件/数据库/脚本 |
| `decided` | 项目已经在说明文档中确定的目标规则 | `03-工程实施规范.md`、`04-决策记录.md` |
| `planned` | 文档提出但当前尚未实现的模块或产物 | `00-项目规划与进展.md`、`02-总体架构与问题分析.md`、`05-工程启动评估.md` |
| `legacy` | 旧 parser、旧数据库或旧字段，保留作兼容和对照，不作为 V2 规范 | 当前代码、旧 schema、旧数据库 |
| `pending` | 需要通过 OCR、抽样、人工审校或外部依赖进一步确认 | 本表另注明核查任务 |

发生冲突时，先按以下顺序判断：

1. 当前文件、脚本和数据库说明“现在是什么”；
2. `03` 和 `04` 说明“V2 应该是什么”；
3. `01` 和 `07`说明成员如何使用；
4. `00`、`02`、`05`说明进展、问题和实施顺序。

## 4. V2 的规范数据流

    原典 Markdown / 归档底本
      -> markdown_preprocess
      -> passages + inline_notes + title_anomalies
      -> candidate extractor + risk auditor
      -> (旧 AI JSON adapter 或新 AI input/output)
      -> annotation_case.v1
      -> schema / quote / enum / hash 校验
      -> V2 统一工作数据库（机器案例先入库）
      -> human_review
      -> gold cases / benchmark
      -> main.db v2 / website snapshot

四个边界必须保持：

1. `candidate` 是机器候选，不是人工结论；
2. `machine_result` 和 `human_review` 独立记录；
3. 机器案例通过校验后可以先进入统一工作数据库，但不能因此称为 gold；
4. 只有有可追溯人工审校依据的案例才能称为 `gold case`；
5. 旧 AI JSON 保留作迁移材料、初始草稿和回归测试，不作为 V2 规范格式；
6. 旧 `dictionary.db` 和旧 importer 只作兼容、检索或对照，不继续扩展模板化 case。

## 5. Passage 和原文处理规范

| 事项 | 规范事实 |
| --- | --- |
| 主定位 | `work_key + title_path + local_ordinal + raw_text_sha256 + normalized_text_sha256 + quote_exact + quote_offset` |
| 标题 | `document_title / section_title / entry_title` 是工程定位路径，不等同于古籍目录学的章卷篇分类 |
| `<small>` | 工作文本去标签但保留文字；来源信息进入 `inline_notes[]` |
| `raw_text` | 保留原始转写和必要格式信息 |
| `plain_text` | 去 HTML 标签但保留文字，供检索和 quote 校验 |
| `normalized_text` | 只做保守空白归一，不自动繁简转换、不自动改异体字 |
| 行号/页码 | 行号只用于当前文件跳转；页码不能作为跨版本主定位键 |
| quote | 默认要求在 passage 中严格命中；归一化匹配必须单独标记 |

## 6. 案例字段规范

### 6.1 最小提交字段

以下 9 项构成最小可提交 case：

    case_title
    submitted_by
    source_work
    target_work
    target_text
    term_relations[].source_term
    term_relations[].target_term
    evidences[].quote
    conclusion

### 6.2 关系和方法分层

| 字段 | 记录内容 | 示例 |
| --- | --- | --- |
| `relation_type` | A 与 B 的主结论关系 | `训释`、`校勘`、`字际关系`、`虚词用法`、`句义解释`、`未定` |
| `relation_subtype` | 主关系的细分 | `声转释义`、`误字`、`当作`、`通假`、`古今字` |
| `method_profile.expressions[]` | 二王原文中的实际表达 | `一声之转`、`读为`、`當作` |
| `method_profile.concepts[]` | 现代方法概念 | `声训`、`书证`、`义证`、`异文校勘` |

`relation_type` 记录结论关系，不能和方法词表合并。候选方法概念初始为 `review_status=pending`，不能自动视为已审定概念。

### 6.3 五步字段

| 中文步骤 | 英文字段 | 当前规范 |
| --- | --- | --- |
| 发疑 | `problem_discovery` | 疑点从哪里来 |
| 设问 | `research_question` | 把疑点变成可验证问题 |
| 取证 | `evidence_collection` | 证据材料和证据类型 |
| 释理 | `reasoning` | 证据如何支持判断 |
| 结论 | `conclusion` | 最终判断；最小 case 必填 |

API/JSON 层使用五个并列字段，不使用 `steps[]` 作为主结构。缺项必须显式留空或标记 `missing`，不能硬凑。

## 7. 状态规范与当前旧值

### 7.1 V2 状态

| 字段 | V2 允许值 | 含义 |
| --- | --- | --- |
| `machine_result.status` | `pending` / `draft` / `approved` / `rejected` | 机器运行和机器校验状态 |
| `human_review.status` | `pending` / `approved` / `rejected` / `uncertain` | 人工审校状态 |
| SQL `review_status` | `pending` / `approved` / `rejected` / `uncertain` | 可查询的人工审校汇总 |
| `method_concepts.review_status` | `pending` / `approved` / `rejected` | 方法概念候选或审定状态 |
| SQL `origin` | `legacy_ai_json_reprocessing` / `legacy_dictionary_db_reprocessing` / `original_markdown_ai` / `original_markdown_machine_extraction` | 案例来源和再加工入口，不代表审核结论 |
| SQL `lifecycle` | `machine_draft` / `human_review` / `gold` / `rejected` | 案例晋级阶段 |

### 7.2 旧值处理原则

当前旧库中的 `草稿`、`已校对`、`已审核` 和 `确定` 不能直接改名为 V2 状态。迁移时必须保留原值，并根据是否有可追溯审校记录决定是否填充 `human_review`。没有证据时不能把 `确定` 推断为人工通过。
