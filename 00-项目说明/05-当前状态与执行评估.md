## 2. 项目是否具备开工条件

具备。已有原典 passage、V2 工作库、只读检索、五步卡、审计记录和来源状态，不需要先重新设计数据库或建设通用 Agent 平台。

真正缺口是把工程能力转换成至少一例真实、可追溯、可展示的人工复核成果，并据此确认后续 benchmark 字段是否可操作。

## 4. 风险和停止条件

| 风险 | 应对 |
| --- | --- |
| AI 叙述造成锚定 | 首例先独立阅读 |
| 外部引文缺版本 | 保留未决，不写成 canonical |
| 案例范围过大 | 缩小命题，不硬填五步 |
| 页面和确认稿分叉 | 页面只从确认稿生成 |
| V2 接入拖延 | 文件包先行，隔离试接限时 |
| 时间不足 | 先取消第四例，再减少核心案例 |
| 研究方向扩张过快 | 先完成案例闭环，不先建通用 agent 平台 |

出现以下情况应停止扩展功能：

- 连续案例都需要大幅重写 AI。
- 人工总负担没有下降。
- 关键来源约 30 分钟仍无可控路径。
- 页面开发开始挤占案例复核。
- V2 接入要求改生产数据或补全全库队列。
- benchmark 字段尚未由真实案例证明，却开始批量扩展 schema。

## 5. 不在本轮范围

- 全库人工审校。
- 全部 target_work、外部来源和外部 passage 消歧。
- 全面 canonical 底本核验。
- 批量自动升 gold。
- 通用 Agent 平台、多 Agent 数量竞赛和无评价的聊天功能。
- 无关架构重构。
- 继续扩大未经核验的 machine cases。

申报材料“不少于 60 条”和答辩材料“不少于 300 条”的口径冲突仍未解决。三例 pilot 只能作为可信的阶段性成果，不能冒充完成数量承诺。

## 6. 统一验收问题

沿任一案例倒查：展示中的关键解释能否回到确认版本；确认版本能否回到真实人工意见和修改依据；修改依据能否回到确定的王氏原文；下一例能否用同一规则继续处理。

对长期研究再加一问：这个案例是否已经具备明确任务、答案、证据角色、难度、未决规则和可重复评价方式。

如果不能回答前一个问题，就不能称为结构化复核完成；如果不能回答后一个问题，就不能称为 benchmark-ready case。
