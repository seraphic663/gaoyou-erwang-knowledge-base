# 高邮二王「農」检索与字词关系统计核查（核查于 2026-10-29，更新于 2026-10-30）

> 2026-10-29 的核查只读代码、数据库和网站接口。2026-10-30 按请求修改了 corpus 检索页面和检索桥接代码，以开放可选单字检索；数据库、原典与机器案例数据均只读，未部署。工作树其他改动均保留。

## 结论

1. 你遇到的是两处不同的检索边界：`/terms` 是旧字词目录，词头模式搜「農」返回 1 条、全文模式返回 48 条，但记录都来自《广雅疏证》的旧目录；`/corpus` 虽有四书索引，却把单字「農」过滤掉，所以返回 0 条。
2. 你截图中的「字詞關係—訛混／脫訛」在当前人工候选 Markdown 中分别有 5 条和 1 条，但这 117 个案例全是「草稿／待核」；这些只能作为候选标注数，不能当作二王四书的学术总量。
3. 目前没有可复核的四书「訛混、脫訛、通假」统一总数。现存 477 条「音训·通假字」是旧词条目录的启发式分类；V2 中 8 条「通假」关系和 3 条「误字」关系也全是未审核机器草稿。不同来源、不同计数单位不能相加。
4. 字词库确实是旧来源：它由旧 parser 从单一《广雅疏证》`source.txt` 生成；当前 815 个结构化案例全部标为「广雅疏证卷第一上／释诂」。它不是四部著作的统一字词库或人工审定案例库。

## 1. 为什么「農」在 corpus 网站搜不到

修改前，`/corpus` 前端把查询发到 `/api/corpus/unified-search`，其中原典检索调用 `retrieveOriginalForUnifiedSearch`，最终进入只读桥接脚本 [corpus_retrieval_bridge.py](../../solution/website/scripts/corpus_retrieval_bridge.py#L53)。`query_tokens()` 只保留长度至少为 2 的 token；单字「農」因此变成空 token，`retrieve()` 直接返回 `candidate_count=0`，没有查询正文索引。线上只读接口复核得到：`query="農"` 为 0；两字查询 `農民`、`農力`、`農器`、`農父` 分别能命中《读书杂志》《经义述闻》《广雅疏证》《经传释词》。

现在 corpus 页新增「允许单个汉字检索」选项，默认关闭，保留双字及以上的快速路径。开启后，单个汉字只查二王原典四部，不调用仍以双字索引为基础的外典检索；页面显示前 8 条，并显示原典候选数。此功能修改了前端、HTTP 路由和 Python 桥接层；数据库未重建、未改写，线上也未部署。外典单字检索仍未支持。

四部原典确实都已进入当前 corpus 数据库，且对应来源状态为 `canonical_active`；其正文及标题命中分布如下。正文字符次数不含标题字段。

| 著作 | 索引 passage 数 | 正文含「農」的 passage／字数 | 标题含「農」的项目数 |
| --- | ---: | ---: | ---: |
| 《读书杂志》 | 4,987 | 103／180 | 5 |
| 《广雅疏证》 | 428 | 37／203 | 0 |
| 《经义述闻》 | 1,967 | 102／178 | 5 |
| 《经传释词》 | 150 | 3／4 | 0 |

例如《读书杂志》`農民`条讨论今本「農民歸利」应作「民性歸利」；这个正文 passage 已在索引中（原文行 401–402）。《经义述闻》的「農」命中也分布于不同篇目。网站 corpus 页面每次只显示排名靠前的 8 条，所以页面显示条数不能当作全集统计；候选计数若触及查询候选上限，也只能报告“至少”该数。单字开关写入页面 URL 的 `single_char=1`，可分享同一查询模式。

检索库与当前四份原典文件内容一致，但这些 Markdown 的文件头说明它们由 DOCX 抽取、尚未校勘；因此这是“索引覆盖了当前文件”的证据，不等于证明文本已完成底本校勘，见 [《广雅疏证》文件头](../../data/A-原著原典/广雅疏证_王念孙.md#L3)及其余三书对应文件头。

## 2. 字词库是否陈旧

字词目录页面向 `/api/browser` 取旧主库快照，而不是从 corpus passage 生成词条；它的字段是词头、类别、释义、备注和旧案例链接，见 [terms.js](../../solution/website/web/assets/js/terms.js#L28) 与 [shared.js](../../solution/website/src/data-sources/shared.js#L206)。线上只读响应中，词头模式搜「農」返回 1 条（旧词条 ID 1562），全文模式返回 48 条旧目录记录。48 是提及文本匹配数，不是 48 个经人工确认的「農」考据条目。

旧主库的来源在 [legacy-db 说明](../../solution/legacy-db/README.md#L18) 中明确为《广雅疏证》`source.txt`，并标为旧机器解析展示库；当前四书 corpus、人工标注库和 V2 工作库是独立数据层。只读统计显示旧主库有 3,385 个唯一词头、815 个案例、7,120 条证据；815 个案例的卷篇字段全部是「广雅疏证卷第一上／释诂」，方法字段则全部是同一条泛化模板「声训、通假、书证、义证、语法对文」。旧库虽登记 49 种被引用的外部著作，但这不代表它收录了四部二王原典的字词关系。

当前文件时间也显示了版本差：旧 `dictionary.db` 为 2026-04-01，`source.txt` 为 2026-08-12，网站 SQLite 快照为 2026-09-30；四部原典 Markdown 文件为 2026-10-25。时间戳本身不能证明内容错误，但旧库的来源范围、案例卷篇字段和代码链路都确认它没有跟四书检索库同步扩充。

旧分类不能当作审定的关系计数。[parser.py](../../solution/legacy-db/main/parser.py#L258) 用「X之言」「讀爲／讀若」「方言」等字符串规则推断类别；其余默认「同义实词」。当前目录的 477 条「音训·通假字」因此是受规则影响的唯一词头条数，不是独立通假关系条数。导入器还把 `core_meaning` 截到 100 字，见 [importer.py](../../solution/legacy-db/main/importer.py#L45)；字词详情通过 `/api/term` 读取静态快照，页面本身不调用 AI，见 [term-detail.js](../../solution/website/web/assets/js/term-detail.js#L145)。

从旧 SQLite 的数据粒度看，49 个 `works` 是引文来源目录（被引用的书目），`passages=0`；其中只有《广雅疏证》与四部研究对象之一重名，另三部不在旧库里。`terms` 按唯一字形去重，case 按原书行号和训释聚组，evidence 只有被引书名与短引文，没有 `source_passage_id`。线上旧库快照与本地 `dictionary.db` 的五表逐行一致，说明部署快照与该旧 DB 同步；但旧 DB 没有记录所用 `source.txt` 的哈希或版本，因此不能证明数据库已追上 2026-08-12 的源文件。旧库 2026-04-01、快照 2026-09-30 的时间戳只作提示，不单独作为陈旧性的证明。结构定义见 [legacy-db schema.sql](../../solution/legacy-db/main/schema.sql#L29)，逐行解析、去重与分组逻辑见 [importer.py](../../solution/legacy-db/main/importer.py#L26)。

## 3. 「訛混／脫訛／通假」现有可数数据

你的截图类别出现在人工标注材料的「字詞關係」栏。对当前 117 份案例 Markdown 按该栏的独立标签只读计数：

| 候选标签 | 案例数 | 当前状态 |
| --- | ---: | --- |
| 訛混 | 5 | 草稿／待核 |
| 脫訛 | 1 | 草稿／待核 |
| 通假文字关系 | 4 个案例在自由文本栏中提到 | 草稿／待核；未规范化为关系子类 |

五条「訛混」见 `047`、`063`、`064`、`068`、`069`；一条「脫訛」见 `050`。例如 [047「俱止於棲」](../../data/D-标注/03-案例Markdown/047-读书杂志-战国策-俱止於棲-卢飞宇.md#L30) 标为「訛混」，[050「血流至足」](../../data/D-标注/03-案例Markdown/050-读书杂志-战国策-血流至足-卢飞宇.md#L40) 标为「脫訛」。`通假` 自由文本标签见 `002A`、`002B`、`075`、`076`，但不是规范子类；对应候选 JSONL 仍保留 `human_review.status=pending` 与 `machine_result.status=draft`，例如 [047](../../data/D-标注/04-案例JSONL/manual_annotation_cases.annotation_case.v1.candidates.jsonl#L57) 和 [050](../../data/D-标注/04-案例JSONL/manual_annotation_cases.annotation_case.v1.candidates.jsonl#L60)。这不是四书全集计数：当前 117 个案例在标注数据库里均为「草稿／待核」。

人工标注库的关系表只有 `relation_type`，没有可用于截图子类统计的 `relation_subtype`，见 [schema.sql](../../solution/legacy-db/annotation/schema.sql#L45)。例如 `047`、`050` 的结构化 term 行都是 `relation_type=未定`、`related_term=未抽取`；类别仍只在自由文本里。117 案例的 206 条结构关系行分属 `未定 90、训释 40、校勘 29、字际关系 28、虚词用法 18、句义解释 1`，所以这个人工库也不能直接提供“通假／误字”子类总数。

V2 表有 `relation_subtype` 字段（见 [annotation_v2.sql](../../v2/schemas/annotation_v2.sql#L276)），当前 13,423 条关系行中有 8 条 `字际关系／通假`（涉及 3 案）和 3 条 `校勘／误字`（涉及 2 案），11 行全部来自 `legacy_ai_json_reprocessing`；所有 7,581 个案例都是 `machine_draft/draft/pending/pending`，没有已保存的人工审校事件。这些数字只能称机器候选计数。人工 Markdown 中的「訛混」「脫訛」、旧库的「音训·通假字」、V2 的「误字」「通假」是不同来源和标签口径，没有已建立的跨库映射，不应直接等同或累加。

另一个限制是检索 API 本身没有覆盖关系字段：`GET /api/v2/cases?q=通假` 返回 0，因为案例列表 SQL 搜案例标题、正文与出处等字段，不搜索 `annotation_terms.relation_type/relation_subtype`（[v2_acceptance_bridge.py](../../v2/scripts/v2_acceptance_bridge.py#L910)）。因此数据库虽已有可分组的 subtype 候选行，当前网站案例搜索不能据此统计。

## 4. 原书里已有的校勘数字

王念孙《广雅疏证》自序给出了一组作者自计的校勘项：[广雅疏证_王念孙.md](../../data/A-原著原典/广雅疏证_王念孙.md#L23) 列「譌」578、脱 491、衍 39、先后错乱 123、正文误入音内 19、音内字误入正文 57，按该段口径合计 1,307 项。这只针对《广雅》正文和音释的校勘，不是四书的「讹误／通假」总数，也没有统计通假。

现代整理说明给出另外两组口径：[读书杂志_王念孙.md](../../data/A-原著原典/读书杂志_王念孙.md#L93) 将《读书杂志》校正项列为误字 1,259、补脱 460、乙倒 149、删衍 531，四项合计 2,399；同一说明在[第 39 行](../../data/A-原著原典/读书杂志_王念孙.md#L39)称《经义述闻》全书约 2,300–2,400 条，其中校正讹字、倒文、衍夺“六百余条”。这两项是虞万里 2013 年出版说明中的整理者统计／概述，不是王引之本人给出的统一精确计数。不同书的统计口径也不能直接相加。

## 5. 更新方向

- corpus 的可选单字查询已在本地代码实现；默认双字及以上，单字只查二王原典，页面显示数与候选数分开展示。外典仍限双字及以上。
- 字词库与案例库更新应保留来源、源文件哈希、parser/生成版本、行号或 passage ID、原始 ID、生成来源和审核状态；旧词条、四书 passages、人工候选、V2 机器候选不能因字形相同而直接合并。
- 计数前必须固定粒度：一次明确判断、案例、关系对、唯一字头或字词出现次数分别报告；同一条论证多次提及不得在没有口径说明时重复累计。

## 6. 大型 V2 案例库：记录量不等于 AI 完成量

当前 `annotation_v2.db` 有 7,581 个案例、13,423 条 term/关系行、13,990 条 evidence。按案例来源拆开：6,745 条 `original_markdown_candidate_shell`、815 条 `legacy_dictionary_db_reprocessing`、17 条 `legacy_ai_json_reprocessing`、4 条 `original_markdown_ai`。四书 6,749 条原文候选壳／AI 代表案例的作品分布为《读书杂志》4,308、《经义述闻》1,893、《广雅疏证》396、《经传释词》148；每部仅抽取 1 条代表候选调用 AI，其余 6,745 条是确定性壳记录。README 说明与统一入库链分别见 [v2/README.md](../../v2/README.md#L115) 和 [run_unified_ingress.py](../../v2/scripts/run_unified_ingress.py#L317)。

这意味着“7,581 个案例”不能写成“7,581 个 AI 分析案例”。6,745 个 shell 用来物化候选位置，带原文和 `未定` placeholder，但不代表已经做出关系判断；脚本明确将它们标作未进行 AI 语义生成（[run_unified_ingress.py](../../v2/scripts/run_unified_ingress.py#L196)）。另外 815 条源自旧字词库再加工，17 条来自旧 AI JSON 再加工；只有 4 条 `original_markdown_ai` 是本批原典候选的代表 AI 分析输入。

全库 7,581 案例的 `machine_status=draft`、`human_status=pending`、`lifecycle=machine_draft`、`review_status=pending`；`v_gold_cases=0`、`review_events=0`、`resolution_events=0`、`five_step_audit_records=0`。候选表里的 `candidate_status=approved` 仅表示原文抽取候选获准物化，不表示案例被人工审定或升为 gold。当前 13,423 个 term rows 中有 13,384 条 `未定`，涉及 7,565 个案例；明确的 `通假` 为 8 行/3 案、`误字` 为 3 行/2 案，另有 6,745 个原文候选 placeholder、6,628 条旧词库关系记录。详细 schema 和生成状态见 [annotation_v2.sql](../../v2/schemas/annotation_v2.sql#L276)、[run_unified_ingress.py](../../v2/scripts/run_unified_ingress.py#L248) 与 [v2/README.md](../../v2/README.md#L237)。这些都是机器草稿库存数，不是二王四书学术统计。

目标字词对的定位也没有完成：74,171 条 `candidate_target_locations` 中 73,888 条仍为 `not_searched`、139 条 `candidate_match`、117 条 `no_match`、27 条 `same_source_only`；`target_work_resolution_queue` 仍有 7,962 项。案例物化覆盖不等于目标位置已解析，也不等于关系证据已经配对。

当前四部 canonical Markdown 的 SHA-256 与 V2 active source version 全部相同；在内存中重跑 passage builder 后，四部 passage 全字段都与 DB 相符：4,987/4,987、428/428、150/150、1,967/1,967。因此没有证据表明当前原文 corpus 因抽取滞后而漏 passage；遗留词库不含四书全量关系是另一类覆盖问题。candidate_items 的 candidate_text 没有完全重复，case_json 完全重复数为 0；但 case_title 有 90 组重复标题，多出 356 案例行（如同一“王念孙校”标题可对应不同段落），不能按标题去重。`passages.raw_text_sha256` 有 1,185 组重复、超出组内首条共 5,710 行，几乎都来自按 legacy-derived evidence 重复物化的 passage；这是关系/证据物化粒度，不足以证明数据损坏，也不应直接删重。

6,749 条 candidate_items 的 `approved` 表示抽取候选经规则物化，不是人工审批：抽取器匹配配置中的提示词，审计器只校验 passage 存在及文本非空（[candidate_extractor.py](../../v2/src/erwang_v2/candidate_extractor.py#L6)、[candidate_auditor.py](../../v2/src/erwang_v2/candidate_auditor.py#L6)）。旧字词目录中 477 条“音训·通假字”连接到 891 条词条—案例链接，涉及 368 案；V2 导入后的 6,628 条 legacy term-case link 仍落为 `relation_type=未定, relation_subtype=词`，并没有被转换成通假判断。V2 的 7,241 条 evidence 仍为 `unchecked`，只有 6,749 条 `passed`；来源 passage 有链接不等于目标关系已核实。

`relation_subtype` 在 V2 schema 中是 nullable 字符串，没有枚举、外键或 check constraint（[annotation_v1 schema](../../v2/schemas/annotation_case.v1.schema.json#L44)、[annotation_v2.sql](../../v2/schemas/annotation_v2.sql#L276)、[validate_annotation_case.py](../../v2/scripts/validate_annotation_case.py#L27)）；人工标注库又没有 subtype 字段，旧库只用自动推断的词条 category。相同的“通假／误字”统计口径目前无法跨这三套库直接求和。

当前 UI 也无法回答 subtype 计数：`/cases?source=v2` 只筛作品和 machine status，不筛 subtype；案例详情不显示 subtype；`/quality` 只汇总 schema 与案例概数，不读取人工标注快照，也不按 subtype 分组。案例列表关键词 SQL 不搜 `annotation_terms`，所以线上 `/api/v2/cases?q=通假` 返回 0，而数据库实际有 8 行通假 subtype。当前本地配置还可能指向只有 2 案的 `local_test/annotation_v2.local.db`，与 Railway 使用的 `real_runs/annotation_v2.db` 不同。要做可靠统计，需先固定类别规范、关系粒度和审核口径，再为列表/报告增加 `relation_type + relation_subtype + review status + origin` 分组及来源过滤。

可复核的只读 SQL 口径如下；执行时使用 `mode=ro&immutable=1`：

```sql
SELECT origin, COUNT(*) AS cases
FROM annotation_cases
GROUP BY origin
ORDER BY cases DESC;

SELECT ac.origin, t.relation_type, t.relation_subtype,
       COUNT(*) AS relation_rows,
       COUNT(DISTINCT t.case_id) AS cases,
       COUNT(DISTINCT t.source_term || char(1) || t.target_term) AS exact_pairs
FROM annotation_terms t
JOIN annotation_cases ac USING (case_id)
WHERE t.relation_subtype IN ('通假', '误字')
GROUP BY ac.origin, t.relation_type, t.relation_subtype
ORDER BY t.relation_subtype;

SELECT lifecycle, machine_status, human_status, review_status, COUNT(*)
FROM annotation_cases
GROUP BY lifecycle, machine_status, human_status, review_status;
```

只按 `relation_subtype` 汇总会把草稿当成结论；报告统计时至少要同时保留 `origin`、relation 大类/子类、案例数、关系行数、去重词对数和 human/review 状态。V2 evidence 状态当前为 `passed 6,749、unchecked 7,241`；来源段落 7,581 案全有链接，但目标段落只有 815 案有链接。不能把“有 source passage”当成“目标关系已核实”。

截至本核查时，最稳妥的报告方式是：当前人工候选池有 5 条「訛混」和 1 条「脫訛」标签；结构化 V2 草稿有 8 条「通假」关系行；四书完整的、经人工核验的学术总数尚未建立。
