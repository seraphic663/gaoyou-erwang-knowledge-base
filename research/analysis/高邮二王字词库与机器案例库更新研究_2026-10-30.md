# 高邮二王字词库与机器案例库更新研究

核查日期：2026-10-30。本文综合只读检查、两路 Luna Max 子代理报告与当前检索页实现，讨论字词库和 V2 机器案例库怎样更新，以及“通假／误字”目前能统计到什么程度。没有调用 DeepSeek API、重跑导入器、改写数据库或部署。

## 建议

采用“确定性解析负责来源、位置和候选；DeepSeek 负责提出结构化关系草稿；人工审核后才能计入已确认统计”的分层方案。不建议在规则解析器与 API 之间二选一，也不建议把全部候选直接批量重跑后覆盖现库。

先保留旧《广雅疏证》字词库作为带来源标记的历史版本；在副本上设计新版关系模型与确定性入库；先做 60–80 条分层人工评测，再按小批次调用 API。统计页面必须分开显示机器候选、人工待核和人工确认，并按案例、关系行、唯一字词对分别计数。

## 现有数据究竟代表什么

| 数据层 | 当前数量 | 可据此说明什么 | 不能据此说明什么 |
| --- | ---: | --- | --- |
| 旧字词库 | 3,385 个词头、815 个案例、7,120 条证据 | 旧 parser 生成的《广雅疏证》词条与证据规模 | 四部原典的统一字词关系总量 |
| 旧库“音训·通假字” | 477 个唯一词头、891 条词头—案例链接、涉及 368 案 | 规则命中的旧分类记录量 | 477 条通假关系或人工确认数 |
| V2 案例库 | 7,581 案例 | 不同来源记录合计 | 7,581 个 AI 分析或已审定案例 |
| V2 原典候选壳 | 6,745 案 | 规则定位并物化的原文段落草稿 | 6,745 次语义分析或 6,745 个字词判断 |
| V2 明确 subtype | 8 行“通假”／3 案；3 行“误字”／2 案 | 17 条旧 AI JSON 再加工产生的机器声明 | 经审核的二王学术总数 |

旧库“通假字”分类由字符串规则生成：例如 `读为／读若` 命中便可能进入此类，其他词条往往落入默认类别；分类逻辑见 [旧 parser](../../solution/legacy-db/main/parser.py#L258)。旧词条按字形去重，没有明确的“本字—借字”关系记录。`dictionary.db` 与 2026-08-12 的 `source.txt` 之间没有可核对的源文件哈希，因此不能仅凭现有库证明它已更新到该源版本。

V2 的 7,581 案例由 6,745 个原典候选壳、815 个旧词库迁移案、17 个旧 AI JSON 再加工案和 4 个原典代表 AI 案例构成。当前案例均为机器草稿／待核；人工审校事件和 gold 均为 0。6,749 个原文候选的“approved”只表示段落通过结构检查、文本非空，不表示学者批准。分来源、状态和口径的完整核查见[现有统计报告](高邮二王字词关系与讹误通假统计核查_2026-10-29.md#L73)。

眼下数据库已有 `relation_subtype`，但它是自由字符串，缺少枚举与受控术语；旧人工标注库没有 subtype 字段；旧字词库的 category 又是另一套机器分类。因此“訛混／脫訛／误字／通假”目前无法跨来源直接相加。V2 的案例搜索 SQL 也不查 `annotation_terms` 关系子表，故搜索“通假”得到 0 条不等于库中没有机器候选；现状与可复核 SQL 见[统计报告](高邮二王字词关系与讹误通假统计核查_2026-10-29.md#L35)及 [V2 案例桥接查询](../../v2/scripts/v2_acceptance_bridge.py#L910)。

## 机器解析与 API 各自应做什么

| 环节 | 确定性代码 | DeepSeek API |
| --- | --- | --- |
| 来源与版本 | 生成 source hash、作品／版本身份、passage ID、行号和字符位置 | 不让模型决定底本身份 |
| 候选定位 | 对词形、提示语、标记结构等做可重放抽取，并保留规则版本 | 补充可能的关系候选，不负责证明规则召回完整 |
| 关系判读 | 校验字段、引用子串、词项是否确实出现在来源中 | 对明确上下文提出关系类型、方向、字词对、理由和证据引用草稿 |
| 最终结论与统计 | 聚合不同来源、版本与审核状态 | 不让模型输出直接变成确认数；机器 confidence 只用于排序 |

当前候选抽取覆盖 6,749/7,532 个原典 passage（约 89.6%）；另有 783 个 passage 没被规则选中，只能说明“未被当前规则选中”，不能当作“没有讹误或通假”。旧候选文件与当前抽取器的风险标记不完全一致，故更新前应冻结实际使用的 parser／rule commit 与输入哈希，不能假设现有 JSONL 可由当前规则逐字段重建。抽取与审计代码见 [candidate_extractor.py](../../v2/src/erwang_v2/candidate_extractor.py#L6) 和 [candidate_auditor.py](../../v2/src/erwang_v2/candidate_auditor.py#L6)。

建议将新数据拆为三个实体，而不是把所有判断塞进案例 JSON：

1. **来源版本与 passage**：source document、版本／底本、文件 SHA-256、解析器版本、稳定 passage ID、原文偏移与行号。
2. **关系主张**：source/target 字词、关系大类与受控 subtype、方向、原始作者措辞、机器／人工提出者、弃答原因、审核状态。
3. **证据片段**：引文原文、source hash、passage ID、起止偏移、证据作用及自动子串核验结果；每条关系主张都引用一个或多个 evidence ID。

每次 AI 运行另写 append-only run/result：保留 candidate ID、source hash、taxonomy version、prompt hash、model/effort、请求标识、输入与输出 token、缓存命中、finish reason、原始响应、错误和重试。使用这些字段构造幂等键，避免“换 prompt 后覆写旧答案”；新旧草稿并存，审核决定单独记录。

## 为什么不能直接重跑现有导入

旧库全量导入器会先 reset 数据库，见 [importer.py](../../solution/legacy-db/main/importer.py#L151)。V2 统一入库脚本也不是 6,745 条安全 API 调度器：它只对每部书抽一个代表样本；函数默认 `with_ai_samples=True`，有可用 key 时会调用 API，只有显式加 `--no-ai-samples` 才关闭，见 [run_unified_ingress.py](../../v2/scripts/run_unified_ingress.py#L241) 和 [CLI 参数](../../v2/scripts/run_unified_ingress.py#L590)。对相同案例 ID 的写入会覆盖机器／人工状态并重建 term、evidence、process 行，见 [run_unified_ingress.py](../../v2/scripts/run_unified_ingress.py#L424) 与 [database.py](../../v2/src/erwang_v2/database.py#L355)。

V2 的 source document ID 由 `work_key + source_file stem` 推导，passage ID 则按 `work_key + ordinal` 生成；数据入库逻辑见 [database.py](../../v2/src/erwang_v2/database.py#L129) 和 [passage_builder.py](../../v2/src/erwang_v2/passage_builder.py#L46)。新批次应先在 DB 副本中核对来源 key、路径与 ID 的映射，再执行任何 upsert；不能因路径看似相同就认定它会覆盖正确版本。

安全路线是先对当前 DB 和静态快照制作校验副本，在副本上增建版本化表或独立结果库；给旧数据保留 `origin=legacy` 和原始类别，不做静默映射；先产出新版本差异清单，再决定如何展示。不要向当前真实库直接重新执行 ingest，也不要用案例标题作为去重键。

## 评测和分批更新计划

1. 冻结四部原典文件、旧字词库、V2 DB 的只读快照与哈希；确认每种来源是否允许进入新分析。当前四部原典 passage 与 active source hash 相符，但原文文件仍有未校勘说明；索引一致不代表底本已学术核定。
2. 先定义并由研究者审定类别规范，保留原始标签，制作旧分类到新分类的映射表；歧义项可多标或“未定”，不可强制塞入“通假／误字”。
3. 建立 60–80 条盲评集，覆盖四书、短／长段落、每类正例与易混例、当前规则命中与未命中段落。专家先独立标关系方向、证据和弃答，再冻结 prompt 与 schema。
4. 小样本跑 API，评估 JSON/schema 合规率、引文是否精确连续出现在来源中、关系方向、各 subtype precision/recall/F1、弃答质量、无据断言率和人工审阅时间；对部分样本重复请求以测输出稳定性。
5. 达到事先设定的逐类门槛后，每批 25–50 条，持续写草稿层；对所有“误字／訛混／脫訛／通假”逐条人工复核。复杂关系、长段落和外典证据不足项进入双人复核；不合格项保留为 pending。
6. 统计页面同时显示来源、关系大类／子类、机器／人工状态、关系行数、案例数、去重字词对数；将“已确认”限定为满足审核状态的关系，且过滤条件写入 URL。

## DeepSeek 成本与模型选择

DeepSeek 官方计价页当前把模型别名列为 `deepseek-flash`，对应 DeepSeek-V4.1-Flash-1017；旧 `deepseek-v4-flash` 名称已退役但暂时仍路由到新 Flash。官方现行价格按百万 token 计：Flash 输入缓存未命中为非高峰 $0.15／高峰 $0.30，输出为 $0.60／$1.20；缓存命中输入为 $0.003／$0.006。离峰价格是高峰的一半，具体价格与时段以[官方计价页](https://api-docs.deepseek.com/quick_start/pricing/)为准。API 响应支持报告 prompt cache hit/miss token，见[官方缓存说明](https://api-docs.deepseek.com/guides/kv_cache/)。

本地 2026-10-25 的 `<small>` 边界试验有 84 次调用、58,684 prompt tokens、549,667 completion tokens（其中 515,330 reasoning tokens），不是通假／讹误分类任务。若机械地按每次用量乘以 6,745 条，约为 4.71M 输入与 44.14M 输出 token；按当前 Flash 未命中输入价格估算，非高峰约 $27.2、高峰约 $54.4。这个数字只是“旧高推理任务的压力对照”，不是新任务预测：新 schema、提示词、上下文长度、缓存命中和输出上限都会改变用量。运行记录与评测边界见[试验报告](../../solution/corpus-standardization/evaluation/small-boundary-20261025/REPORT.md#L3)。

所以目前无法严谨断言现有 100 元余额能否覆盖全量：应先用冻结的 60–80 条评测样本实跑，记录 `prompt_tokens`、`completion_tokens`、`reasoning_tokens`、cache hit/miss 与错误重试，再按官方当前价格和实际汇率计算上下界。本文没有调用 API，也没有读取账户余额。

## 本轮检索实现与手动核验

当前检索页默认保留双字及以上的快速入口，单字词需显式启用；多词默认全部命中（AND），另可切换任一命中（OR）。单字词查询只进入二王原典索引。结果页底部有页码跳转，`page=N` 写入 URL；原典结果链接使用 `#corpus-result-N`，例如 `page=2#corpus-result-11`。实现位置见 [corpus.html](../../solution/website/web/corpus.html#L39)、[corpus-browser.js](../../solution/website/web/assets/js/corpus-browser.js#L302)、[corpus-browser.js 的 URL 恢复与结果锚点](../../solution/website/web/assets/js/corpus-browser.js#L633)、[HTTP 路由](../../solution/website/src/http-server.js#L384) 和 [原典检索桥](../../solution/website/scripts/corpus_retrieval_bridge.py#L182)。

本地页面手动核验了 `農 毋`：AND 返回 19 段，OR 返回 390 段；AND 下页码跳转到第 2 页显示第 11–19 段，首条结果链接带 `page=2#corpus-result-11`。这是当前本地索引上的 UI/检索行为检查，不是四书关系计数，也没有验证外典单字检索（该模式当前有意不启用）。

## 边界

本研究给出数据和工程更新路线，不宣称已得到王氏“通假／误字”总量。当前可复核的是机器候选库存数与 pending 状态；要回答学术数量，仍须先定分类口径，再逐条核对原典、外证和作者实际判断，并报告尚未审完的覆盖范围。
