# 26大创项目网站部署迁移分析报告

更新时间：2026-05-01

## 1. 结论先行

当前网站实际采用的是 `Railway` 部署，而不是纯静态托管。

它的运行方式是：

- 仓库根目录作为部署入口
- 平台执行 `npm start`
- 启动 `03-项目网站/server.js`
- 通过 Node.js 原生 HTTP 服务同时提供静态页面和 `/api/*` 接口
- 运行时优先读取 `03-项目网站/data/sqlite-snapshot.json`

因此，这个项目可以迁移到国产平台，而且迁移难度不高。原因很简单：它不是依赖复杂中间件的系统，而是一个 `Node 18+ + 静态文件 + 本地 JSON 快照` 的轻量 Web 服务。

如果目标是“尽量接近 Railway 的使用体验”，我给出的推荐顺序是：

1. `腾讯云 CloudBase Run`
2. `Sealos`
3. `阿里云 SAE`

我的判断是：

- 如果你最在意“像 Railway 一样，连 Git 仓库就能跑”，优先看 `CloudBase Run`
- 如果你更在意“界面化、部署快、适合演示和团队试用”，优先看 `Sealos`
- 如果你更在意“国产大厂、后续正式化、可扩到企业级”，看 `阿里云 SAE`

## 2. 当前网站到底是怎么部署的

### 2.1 代码层证据

仓库根目录已经明显按 Railway 组织：

- 根目录 `package.json` 把启动命令定义为 `node 03-项目网站/server.js`
- 根目录 `railway.toml` 指定：
  - `builder = "NIXPACKS"`
  - `startCommand = "npm start"`
  - `healthcheckPath = "/api/health"`
- 根目录 `README.md` 直接写明线上地址是 `https://gaoyou-demo1.up.railway.app/`
- `03-项目网站/src/config.js` 显式兼容 Railway 的 `PORT` 和 `RAILWAY_VOLUME_MOUNT_PATH`
- `03-项目网站/README.md` 也直接写明推荐部署到 Railway，并说明根目录部署方式

### 2.2 本地行为核验

我在本地实际启动后访问 `/api/health`，返回结果为：

- `ok: true`
- `source: sqlite`
- `sourceLabel: SQLite 实库`
- `works: 49`
- `terms: 3385`
- `cases: 815`
- `evidences: 7120`

这说明当前线上思路不是“容器里直接连 SQLite 写库”，而是：

`02-数据库/dictionary.db` -> `sqlite_bridge.py export` -> `03-项目网站/data/sqlite-snapshot.json` -> Node 服务读取快照

换句话说，线上运行时只要能稳定读取快照文件，就能工作。

## 3. 当前系统对部署平台的真实要求

这个项目对平台的要求，比一般全栈系统低很多。

### 3.1 必需能力

- 能运行 `Node.js 18+`
- 能暴露一个 HTTP 端口
- 能提供公网访问
- 能设置环境变量
- 最好支持健康检查

### 3.2 非必需能力

当前阶段并不必须有：

- 独立数据库实例
- Redis
- 对象存储
- 消息队列
- 容器编排能力

### 3.3 需要注意但不是硬门槛的能力

- 如果以后想在线修改 `demo-db.json`，就会涉及持久化存储
- 如果以后要做正式域名对外展示，国内平台通常会涉及 ICP 备案
- 如果以后要自动部署，Git 仓库触发链路是否顺手会很关键

### 3.4 一个关键判断

这个站点不能直接当成“纯静态网站”丢到静态托管里。

原因是它不只是 `index.html`，还依赖：

- `/api/health`
- `/api/bootstrap`
- `/api/search`
- `/api/browser`
- `/api/term`
- `/api/case`

所以平台必须能跑后端进程，不能只会托管 HTML/CSS/JS。

## 4. 为什么它很适合迁移到国产平台

当前项目具备 4 个对迁移非常有利的条件：

### 4.1 运行时极轻

后端只用 Node 标准库，没有看到必须额外装的 npm 依赖，也没有 Redis、MySQL、PostgreSQL 之类外部依赖。

### 4.2 数据读路径简单

线上主链路优先读 `sqlite-snapshot.json`，这意味着线上不必再安装 Python，也不必再直接读取 SQLite。

### 4.3 对文件系统依赖弱

在 `sqlite` 模式下，服务主要是读取快照文件，不是频繁写本地磁盘。这对大多数云托管平台都比较友好。

### 4.4 已有健康检查接口

`/api/health` 已经存在，适合直接接到国产 PaaS 的健康检查配置里。

## 5. 国产替代方案对比

下面的比较重点不是“大而全”，而是围绕“像 Railway 一样方便”来评估。

### 5.1 方案 A：腾讯云 CloudBase Run

#### 适配度

很高，属于本项目最像 Railway 的国产替代方案之一。

#### 适合这个项目的原因

- 官方文档明确支持：
  - 本地代码部署
  - Git 仓库部署
  - 容器镜像部署
  - CLI 部署
- 官方文档明确支持从 GitHub、GitLab 等仓库部署
- 官方文档明确支持自动部署
- 官方文档强调按实际使用付费，并支持缩容到 0
- 有默认访问域名，适合测试

#### 对本项目的实际影响

这个项目迁到 CloudBase Run，最自然的方式是：

1. 保持根目录作为部署入口
2. 增加一个很薄的 `Dockerfile`
3. 在 CloudBase 里配置服务端口和最小实例数
4. 部署后用 `/api/health` 做健康检查

#### 优点

- 使用心智和 Railway 很接近
- Git 部署路径成熟
- 适合轻量 Web 服务
- 国内访问通常比 Railway 更友好
- 与腾讯云自家存储、数据库衔接顺

#### 缺点

- 官方 Git 文档中，公共仓库更多是“手动更新”；自动部署优势主要体现在授权的个人/私有仓库
- 自定义域名用于正式生产时，官方文档要求完成 ICP 备案和 SSL 证书配置
- 若以后要把“本地文件写入”当长期持久化方案，需要改成挂载存储或对象存储思路

#### 对你的项目的综合判断

如果你的目标是“把 Railway 换成国内、但依旧尽量保持轻量和省心”，它是第一推荐。

### 5.2 方案 B：Sealos

#### 适配度

高，但它更像“云原生开发+部署平台”，而不是完全复刻 Railway 的 Git 即部署体验。

#### 适合这个项目的原因

- 官方文档支持应用管理、外网访问、自定义启动命令、环境变量、持久化存储
- Sealos 官网强调自动分配公网域名、HTTPS、按量计费、暂停不计费
- DevBox 到上线形成一体化链路，适合小团队协作和快速演示

#### 对本项目的实际影响

Sealos 更推荐的姿势通常是：

1. 在 DevBox 中构建项目或生成镜像
2. 通过应用管理部署镜像
3. 设置端口、环境变量和外网访问

也就是说，它通常比 Railway 多一层“镜像/发布版本”的概念。

#### 优点

- 可视化很强
- 分配公网地址很快
- 支持持久化存储和数据库等扩展
- 适合演示型、迭代型、团队协同型项目
- 停机不计费这点对学生项目友好

#### 缺点

- 思维模型比 Railway 稍重一些
- 更偏“容器应用管理”
- 自定义域名在中国大陆使用时，官方明确要求备案；并且备案云厂商要与所选可用区匹配

#### 对你的项目的综合判断

如果你更希望“图形界面操作多一些、发布和演示直观一些”，Sealos 值得考虑，尤其适合答辩展示或阶段性演示环境。

### 5.3 方案 C：阿里云 SAE

#### 适配度

中高，技术上完全可迁，但操作心智明显比 Railway 重。

#### 适合这个项目的原因

- 官方支持源码部署和镜像部署
- 官方源码部署支持 `Node.js`
- 官方支持从 `GitHub`、`Gitee`、`GitLab`、`Codeup` 导入源码
- 官方支持 Push 到指定分支自动触发构建
- 默认提供公网/内网访问地址，正式环境再绑自定义域名

#### 对本项目的实际影响

理论上，这个项目可以在 SAE 走“源码部署 Web 应用”路线，不一定非要自己先做镜像。

这点很重要，因为它意味着：

- 你不一定要先补完整容器流水线
- 可以直接把 Node 项目作为源码接入

#### 优点

- 大厂平台，后续扩容和正式化路线清楚
- Node 运行时、源码部署、自动构建链路都比较完整
- 未来如果要接 WAF、CDN、更多企业能力，会更顺

#### 缺点

- 平台概念更偏企业级
- 控制台配置项、网络与域名概念比 Railway 多
- 官方默认公网地址更偏测试用途
- 自定义域名访问需要备案，正式化流程更完整也更繁琐

#### 对你的项目的综合判断

如果你后面希望把这个原型进一步正规化，或者老师更认阿里云体系，SAE 是靠谱路线；但若只追求“像 Railway 一样省脑子”，它不是最优先。

## 7. 我给你的推荐方案

### 7.1 最推荐：迁到 CloudBase Run

适用于：

- 你要一个尽量接近 Railway 的国产替代
- 你还想保留 Git 驱动部署
- 你希望平台尽量替你管掉运维细节

原因是它最接近现在这条链路：

`Git 仓库 -> 自动构建 -> Node 服务上线 -> 默认公网地址 -> 自定义域名`

### 7.2 第二推荐：迁到 Sealos

适用于：

- 你更看重演示、界面操作、团队协同
- 你希望后面顺手接数据库、对象存储等能力
- 你能接受“镜像/发布版本”这一层抽象

### 7.3 第三推荐：迁到 SAE

适用于：

- 你后续要长期稳定运营
- 你希望走阿里云正式化路线
- 你可以接受更重一点的平台配置心智

## 8. 迁移时最少需要改什么

### 8.1 基本上不需要改业务代码

原因：

- 已支持 `PORT`
- 已有健康检查接口
- 已把数据层整理为快照文件读取
- 当前不依赖外部数据库服务

### 8.2 最可能需要补的，是部署描述文件

若迁移到 CloudBase Run 或 Sealos，最稳妥的做法是补一个 `Dockerfile`，例如：

```dockerfile
FROM node:18-alpine
WORKDIR /app
COPY package.json ./
COPY 03-项目网站 ./03-项目网站
ENV NODE_ENV=production
EXPOSE 3000
CMD ["npm", "start"]
```

这个项目因为几乎没有运行时依赖，所以镜像会比较简单。

### 8.3 需要确认的环境变量

若保留当前读取逻辑，建议至少确认：

- `PORT`
- `DATA_SOURCE`
- `DATA_DIR`

如果继续走快照文件部署，一般甚至不必额外设太多变量。

## 9. 迁移风险与规避建议

### 9.1 风险一：把它误判成静态网站

这是最容易犯的错。

规避方式：

- 不选纯静态托管产品
- 必须选能跑 Node 服务的产品

### 9.2 风险二：把“本地文件写入”当正式持久化

当前线上最稳的是“只读快照”。

规避方式：

- 演示环境保持 `sqlite-snapshot.json` 只读部署
- 真要在线修改数据，再单独设计对象存储或数据库

### 9.3 风险三：低估域名备案时间

如果要换成你自己的正式域名，国内平台基本都会碰到备案流程。

规避方式：

- 先用平台默认域名完成迁移验证
- 再考虑自定义域名与备案

### 9.4 风险四：在答辩前临时换平台

如果当前 Railway 还能稳定打开，而近期目标只是答辩或展示，立即换平台未必划算。

规避方式：

- 先保留 Railway 作为现有演示链路
- 再并行搭一套国内环境
- 新环境验证稳定后再切换主展示地址

## 10. 最务实的落地建议

如果你现在就要推进迁移，我建议按这个顺序做：

1. 先不要动业务代码
2. 先补一个最小 `Dockerfile`
3. 优先试 `CloudBase Run`
4. 先用平台默认域名跑通 `/api/health` 和首页
5. 确认 `/api/bootstrap`、`/api/search`、`/api/browser` 正常
6. 迁移稳定后，再决定是否上自定义域名和备案

如果你问我一句最直接的话：

可以换，而且很好换；从“像 Railway 一样方便”的角度看，最值得优先试的是 `腾讯云 CloudBase Run`。

## 11. 我建议的下一步

如果你准备真的迁移，而不是只做可行性分析，那么下一步最合理的是：

1. 我直接给这个仓库补一份可用于国产平台的 `Dockerfile`
2. 顺手补一个 `.dockerignore`
3. 再给你写一份“CloudBase Run 实操部署步骤”

这样你就不是只有分析报告，而是能直接开始迁移。
