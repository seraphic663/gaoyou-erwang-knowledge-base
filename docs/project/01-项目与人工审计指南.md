# 项目与人工审计指南

> 当前版本：2026-09-30
>
> 本文是中期参与者的操作入口。它只说明怎样读一例、怎样作人工判断、怎样保存证据，不要求成员手写 V2 工程字段。

## 1. 先理解项目

项目研究的是王念孙、王引之（二王）的考据过程。一个合格案例要让读者看清楚：王氏在处理什么问题，哪些材料承担什么证据作用，王氏怎样从疑点走到解释或校改，以及哪些内容仍待核验。

本阶段成果名称是“考据过程结构化复核案例”。它不是机器草稿，不自动等于精校、benchmark-ready case 或 V2 gold。

## 2. 标准工作流

1. 从 V2 工作库选择案例，并记录稳定 case_id。
2. 固定本次复核的主要命题、原文范围、版本和必要上下文。
3. 先独立阅读王氏原文，写下自己对问题和主要主张的理解。
4. 查看 AI 五步草稿、检索材料和已有 evidence。
5. 逐步检查草稿、来源、证据作用、推理和结论强度。
6. 对每一步选择认可、修改或存疑，并记录理由。
7. 保存 AI 初稿、人工意见、修订稿、确认稿、未决事项和工时。
8. 只从确认稿生成固定展示。

AI 负责定位、整理、对照和提示；人工负责语义判断。人工不需要填写 passage_id、task_id、operation_id 或 SQL patch。

## 3. 五步判断卡

| 步骤 | 要回答的问题 |
| --- | --- |
| 问题发现 | 疑点从哪里来，为什么需要考据 |
| 研究问题 | 本案具体要解决什么问题 |
| 证据收集 | 使用了哪些材料，它们分别属于什么证据类型 |
| 推理 | 每条证据怎样支持、限制或改变判断 |
| 结论 | 在当前材料和范围内可以作出多强的判断 |

五步允许写“未显述”或“尚未确定”，不允许为了字段完整补造原文没有的推理。

每一步只能作一个决定：

- 认可：当前草稿在本范围内可以保留。
- 修改：人工改写，并说明修改原因。
- 存疑：保留限制或待核事项，不强行确定。

认可时不必重复抄写 AI；修改或存疑时必须写人工文本或理由。

## 4. 证据检查

每条关键证据至少检查五件事：

1. 文字是否存在于当前绑定材料。
2. 它是王氏原文、王氏引用、项目整理还是外部材料。
3. 它在本案中承担什么作用。
4. AI 是否把“出现过”写成“已经核验”。
5. 结论强度是否超过证据。

必须明确区分王氏主张、项目对论证的重建和项目尚未独立验证的内容。secondary citation match、external candidate、legacy-derived passage 和 full JSON 命中只能作为定位或线索，不能直接写成外部原典核验通过。

## 5. 首例和人工成本

首例必须先独立阅读，再看 AI 草稿。后续是否增加 AI 备料比例，以首例实际错误和人工负担决定。

至少记录独立阅读、AI 准备、补查、修改和确认时间；Agent 或模型时间单独记录。连续两例需要大幅重写，或辅助后人工总负担没有下降，应停止新增模型功能，只保留定位、排版和格式转换。

生成和保存时记录实际使用的模型、推理设置、预算、prompt 版本、用量、案例指纹、审校人和时间。模型选择是生产方式属性，不是质量等级。

## 6. 案例完成标准

只有同时满足以下条件，才称为结构化复核完成：

1. 案例边界明确。
2. 原文文件、位置和版本明确。
3. 关键解释可以回到确定材料。
4. 人工判断了证据作用和推理关系。
5. 王氏主张、项目重建和项目独立核验边界分开。
6. 有人工意见、修改依据、确认版本和未决事项。

该状态不等于全部外部底本已核验，不等于王氏结论已被项目重新证明，也不自动等于 benchmark-ready case 或 V2 gold。

## 7. 文件包

中期文件包位于 research/midterm-pilot/，建议一例一个目录，至少包含：

- case manifest：case_id、命题、范围、版本和审校人。
- source snapshot：原文、位置、上下文和读取说明。
- AI draft：原始五步草稿、生成配置和材料范围。
- human review：独立阅读、逐步决定、修改理由和未决项。
- revised version：修订稿。
- confirmed version：人工确认的中期正文。
- display：从确认稿派生的展示文本。
- open issues：外部来源、版本、字形和其他未决事项。
- time log：阅读、AI、补查、修改和确认工时。

确认版本发生实质修改后，原确认状态失效，必须重新确认。页面不能另维护第二份实质正文。

## 8. 协作和 Git 最小规则

- 先确认工作区和分支，不覆盖他人未提交内容。
- 只提交本次明确的案例文件包或说明文件。
- 不使用 git add . 或 git add -A。
- 不提交 API key、缓存、数据库 journal、临时 PDF 和大体量归档。
- 提交前运行 git diff --check。
- 未经明确要求，不 push、不合并、不改写远程历史。

## 9. 不应误报

- 页面能生成五步，不等于案例完成。
- 五步审计记录不等于正式 V2 review。
- 检索 benchmark 不等于端到端考据 benchmark。
- machine_status=approved 不等于人工通过。
- 结构化复核案例不等于精校或 V2 gold。
- 三例 pilot 不等于完成 60/300 数量承诺。
- Agent 或模型辅助不等于质量等级。
