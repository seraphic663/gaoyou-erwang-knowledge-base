# 架构、证据与数据边界

> 当前版本：2026-09-30
>
> 本文说明材料如何进入研究环境、证据可以支持什么以及未来研究抽象放在哪里。工程契约见 03；当前事实见 05。

## 1. 总体研究架构

项目的长期结构是：

    原典与版本
      -> provenance-aware corpus
      -> passage、case、evidence 和检索环境
      -> 人工确认的任务与 benchmark
      -> 领域化 harness 和 agent
      -> 系统评价与失败分析

当前已经实现的主要是前两层和检索基础能力；中期先生产人工确认案例，后续才建立端到端 benchmark 和 agent 对照实验。

## 2. 当前实现的五个层次

1. 原文与版本层：四部王氏原典、外部底本和归档材料。
2. V2 机器工作层：passage、candidate、机器案例、来源状态和结构校验。
3. 中期人工复核层：AI 草稿、人工意见、修订稿和确认稿。
4. 展示层：从确认稿或明确的只读材料生成页面。
5. V2 正式 review 层：正式人工事件、状态变化和 gold gate。

中期重点是第三层和第四层；长期研究增加的是任务定义、评价层和 harness，不是把第二层无限扩张。

## 3. 当前数据流

    原典和旧材料
      -> passage 与来源登记
      -> candidate 和机器校验
      -> V2 统一工作库
      -> 选择中期案例
      -> AI 五步草稿和只读检索
      -> 人工复核文件包
      -> 确认版本
      -> 固定成果展示

V2 正式 review 是另一条受门禁约束的路径：

    V2 工作库
      -> target、source、evidence 解析任务
      -> 受任务绑定的正式 review
      -> review events
      -> human status
      -> gold 或保持未决

五步审计卡可以读取 V2 材料，但不替代外部来源核验，也不自动写入正式 review 结果。

## 4. 数据库角色

| 数据库或层 | 当前性质 | 中期使用 |
| --- | --- | --- |
| dictionary.db | 旧 parser 机器解析库 | 历史、兼容和迁移对照 |
| annotations.db | 旧 DOCX/AI 工作稿库 | 历史输入和案例背景 |
| annotation_v2.db | V2 统一机器工作库 | 选择案例、读取材料和建立对应 |
| midterm-pilot 文件包 | 少量案例的研究工作源 | 正文、人工意见、确认稿和展示稿的唯一编辑源 |

数据库是 corpus 的组织、版本和 provenance 基础，也是 agent 的研究环境；它不是自动产生学术结论的唯一研究对象。中期文件包不是第四个主数据库。

## 5. 状态和证据层级

| 状态 | 可以说明什么 | 不能说明什么 |
| --- | --- | --- |
| machine draft | 机器材料已结构化保存 | 不等于人工确认、benchmark gold 或学术结论 |
| canonical source passage | 当前登记版本中有可定位文字 | 不自动证明解释正确 |
| secondary citation match | 王氏正文或旧材料出现相同文字 | 不等于外部原典已核验 |
| external source pending | 需要补外部来源 | 不等于引文错误 |
| candidate available | 有候选文件或页面 | 不等于 canonical |
| legacy-derived passage | 由旧机器材料派生的定位载体 | 不等于原典证据 |
| structure-reviewed case | 指定范围的论证重建已人工确认 | 不等于全部底本核验或 V2 gold |
| benchmark-ready case | 具备可评价任务、答案、证据和难度定义 | 不等于已完成系统比较 |
| V2 gold | 通过正式 V2 review gate | 不表示所有相关材料都已核验 |

full JSON 只能作为旧标注上下文和迁移线索，不能替代 canonical passage、版本和外部原典核验。

## 6. Corpus、benchmark 和 agent 的关系

Corpus 是经过来源和版本组织的研究材料与任务案例集合。Benchmark 是在 corpus 上冻结的任务、答案、证据、数据划分、指标和运行协议。一个人工复核案例可以进入 corpus，但只有达到字段和评价要求后才能进入 benchmark-ready 集合。

当前已有的 retrieval benchmark 只评价检索和排序层。未来的端到端 benchmark 还需要评价答案、证据归因、错误来源、无依据陈述、证据不足时的拒答和人工修改量。

当前五步卡是 AI 辅助审计流程，不自动等于 agent。后续 harness 至少需要明确可用工具、检索范围、状态记忆、查询改写、停止或拒答规则、证据核验步骤、输出 schema 和预算，并保存完整轨迹。

## 7. 主要证据风险

### 7.1 来源身份

同一 work_key 和 source_file 必须对应稳定来源身份。换行、格式变化或重新导入不能静默制造第二个当前来源。活动来源应能回到稳定来源标识、文件路径、上游 revision、canonical status、passage 和 quote。

### 7.2 外部引文

王氏正文提到外部典籍，不等于项目拥有该典籍的 canonical 底本。中期可以把它作为王氏论证材料或待核线索，但不能写成项目已经独立查见外部原典。

### 7.3 target_work 或 evidence 缺失

无法确认 target_work 时保留 unresolved；缺 evidence 时保留 rejected 或待补状态；不根据标题猜测，不制造占位引文。

### 7.4 full JSON 命中

full JSON 的 paragraph 或 comment 命中，只证明旧标注包中出现过相同文字，不能单独证明外部版本、页码、原典准确性或 quote gate 通过。

## 8. 中期案例边界

- 平原之隰：区分王氏以注文支持校改和项目已经查见异本。
- 譕臣：区分字形、训义、上下文和押韵的作用。
- 造舟于河：明确原文、字形和结论中的待核问题，并形成相对立项阶段的新版本链。
- 已，语终辞也：材料范围过粗时先缩小子段或暂缓。

每例确认稿都要列出已确认材料、王氏主张、项目重建、外部未核验项和下一步所需材料。

## 9. 不作为当前主路径

- 让成员从 DOCX 空白表格手写整条 V2 案例。
- 让旧 JSON 工作台作为主要入口。
- 让外部迁移表提交后才能进入五步卡。
- 为中期继续建设独立 candidate.db 或重复的主数据库。
- 把全量 machine candidate 扩张当作中期成果。
- 在没有任务、指标和对照的情况下建设通用 Agent 平台。
