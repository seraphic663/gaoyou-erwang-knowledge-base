### 项目定位、立项边界与当前缺口

立项的核心研究对象是**单条考据的形成过程**。一条案例应把问题、解释、证据和判断之间的关系重新组织出来，使读者能够理解“为什么产生疑问、王氏怎样解释、哪些材料承担什么论证作用、结论如何得到”。著作、原文片段、词目和证据承担材料组织作用；数据库承担稳定组织和追溯；网站承担阅读、检验和展示；标注规范保证后续案例可以按统一规则继续生产；方法认识需要从多个实际案例比较中产生。

立项时已经存在网站、代表案例、旧数据库检索和部分人工标注材料，因此中期继续展示这些既有成果本身没有新增性。当前相对于立项已经形成的主要增量是原典 passage 定位、多来源统一 V2 工作库、来源追踪、机器与人工状态分离、候选层、审校任务以及受控提交机制。这些属于真实工程进步，但尚缺一个完整实例证明这些工程能力已经转换成经过人工确认的研究整理成果。Astra 最终将当前核心缺口概括为：

> **明确复核命题 → 真实人工决定 → 修订 → 确认版本 → 可追溯展示。**

这一判断与当前仓库状态一致：现有工作库已经可以承载人工审校，但当前 `review_events=0`、gold=0，仍没有通过该工作流留下的真实人工结果。

当前机器库存的规模不应继续作为中期建设重点。已有 V2 文档显示四部原典 passage、候选、案例、证据和多类工作队列已经大规模建立；大量记录仍属于 candidate shell、legacy migration 或 machine draft。继续扩大这一层的边际展示价值很低。优先级应转向少量案例的人工过程复核和成果化。

立项数量口径存在一个尚未解决的事实冲突：申报书要求“不少于 60 条代表性案例的精校整理”，答辩第 16 页写“不少于 300 条精选案例”，现有材料没有定义“精校”“精选”的换算关系。不能自行解释成“60 条精校 + 300 条候选”。本轮 pilot 应单独定义为阶段性成果，既不冒充 60/300 数量指标，也不等待该问题解决后才开始执行。

当前五字段和立项五/六环节之间无需为中期重新设计 schema。现有过程表包含五个主字段；本批处理中，“设问”可以同时承载“需要回答的问题”和“待检验的解释”，原文没有展开某一环节时明确写“未显述”；案例内部出现明确类推时单独说明，跨案例的方法比较放入方法提炼文件。该处理能够保持原始方法框架，同时避免为了字段完整而人为补造推理。

### 中期成果标准与人工判断范围

建议正式采用中间成果名称：

> **考据过程结构化复核案例**

操作定义：针对一个确定的王氏文本范围，对案例边界、问题、解释、证据作用和推理重建进行人工复核，保存人工决定、修订后的确认版本和仍未解决的事项。它确认的是“当前项目对这段论证的重建是否准确”，不自动扩大到对全部底本、外部引文、音韵、训诂或王氏最终结论的独立重新证明。

一条案例达到“结构化复核完成”，必须同时满足六项标准：

1. **案例边界明确。**围绕一个主要判断组织，包含完成该判断所需上下文，不因 passage 切分或数据库结构截断实际论证。
2. **来源和文字依据固定。**可以回到确定文件、位置和版本；影响解释的疑字、异文等问题已经处理，或者明确缩小相应判断范围。
3. **关键解释逐项有据。**重要陈述可以回到原文，明确区分原文明说、整理者推断、王氏所引材料和项目独立查见。
4. **论证关系经过人工判断。**人工实际确认“这条材料在这里承担什么作用”，检查漏步、跳步、夸大和额外补入。
5. **王氏主张与本次复核范围分离。**页面和文件不能因为重建正确就暗示相关结论已经由项目独立验证。
6. **确认绑定具体版本。**保存真实人工意见、修改和确认记录；任何影响实质解释的修改都要求重新确认。

建议将质量、生产方式和展示选择拆开记录：

| 属性                  | 工程含义                              |
| ------------------- | --------------------------------- |
| 展示草稿                | 可用于阅读或讨论，尚未完成上述人工复核               |
| 结构化复核案例             | 指定范围的论证重建已经人工确认                   |
| 精校案例                | 在结构化复核基础上进一步完成约定范围的底本、关键引文及专业判断核验 |
| Agent 辅助            | 生产方式属性，不代表质量等级                    |
| 固定展示集               | 展示集合属性，不代表其中所有案例具有相同核验等级          |
| V2 lifecycle / gold | 系统状态，继续遵循已有数据库门禁，不用页面标签代替         |

尤其不建议直接将“精校”等同于 `gold`。前者是学术完成标准，当前尚需进一步确定操作定义；后者是 V2 审批机制中的系统状态。

人工负担应压缩到五类语义判断：问题概括是否准确；各证据所承担的作用是否准确；推理过程中有没有跳步或添加原文不存在的连接；结论强度是否超过原文和证据；尚未解决的问题是否完整记录。人工无需填写 passage ID、JSON patch、任务 ID 等工程字段。程序负责文件存在、引用对应、版本一致、缺项和派生展示来源等机械检查；Agent 负责原文定位、旧稿对照、证据整理、过程草拟和疑点提示。

首例必须采用较强人工控制：复核者先独立阅读原文，至少写出一句“王氏正在解决什么问题、主要主张是什么”，再阅读 Agent 卡片。这样可以降低 Agent 解释造成的锚定效应。后续案例依据首例实际效果逐步增加 Agent 备料比例。

Agent 的效率只根据实际人工投入判断。需要记录每例的阅读、补查、修改、确认、归档人工时间，并另记 Agent 准备时间。连续两例出现人工大幅重写、辅助后总负担没有下降，或工具开发持续占用时间而首例仍未确认，应停止新增 Agent 功能，仅保留定位、排版和格式转换能力。

### 文件包、V2 与数据处理

本批成果建议采用**文件包作为唯一编辑源**。原因是现有 V2 写入机制包含任务包、任务 ID、当前状态、operation 幂等、evidence/source 校验以及 gold gate；为了几条 pilot 案例完整接入现有生命周期，可能产生与中期成果不成比例的维护成本。最终审查已经核实：`uncertain` 可以进入 `human_review` 生命周期，`approved` 会触发完整审批检查，`review_events` 可以保存复核相关信息，CLI/API 又受任务绑定约束。现有机制技术上可利用，但“结构化复核完成”目前还不是 V2 已有正式状态。

建议文件链保持：

`固定原文片段 → Agent 初稿 → 人工意见 → 修订稿 → 人工确认版本 → 展示版本`

每例至少保存：

* 稳定案例标识及现有 V2 case/passsage 对应；
* 原文文件、位置、必要上下文、版本信息；
* Agent 初稿及主要依据；
* 原始人工意见；
* 修订稿；
* 明确确认版本；
* 未决事项；
* 展示版本或其生成指针；
* 实际人工工时。

旧 `dictionary.db`、旧 AI JSON、DOCX、既有阅读笔记继续作为历史输入；不为中期回写或清洗这些来源。现有 V2 案例和 candidate shell 作为工作库存，只保存对应 ID。原典保持只读。页面不能独立维护第二份正文，实质内容变化后原确认失效，需要重新复核。

V2 接入仅在文件包首例稳定后尝试。建议在隔离副本中，用不超过约 1 小时试接一个真实案例，复用已有受控提交、任务绑定和状态规则；整案没有达到既有审批要求时保持相应未决状态，不提高 evidence 或 case 质量等级。若受阻，立即停止，文件包继续作为中期正式成果。没有入库时，中期表述应为“已形成可追溯复核文件包，并与现有 V2 记录建立对应”，不写“人工审校工作流已经完成入库”。

当前数据库中还保留部分 `/mnt/d/26大创/...` 历史来源路径，而本轮运行环境是 Windows。pilot 文件包应同时记录稳定来源标识、仓库相对路径和当前 Windows 路径；无需为了这批案例批量重写数据库历史路径。

### 展示与中期表达

固定成果页承担的是“把已经完成的研究整理工作展示清楚”。非技术评审的第一屏建议只回答四个问题：

| 首屏问题      | 内容要求                  |
| --------- | --------------------- |
| 王氏在处理什么？  | 一句话说明争点               |
| 王氏提出什么判断？ | 一句话说明主要解释             |
| 依据怎样发挥作用？ | 2—3 条关键证据及各自作用        |
| 本阶段增加了什么？ | 明确指出本轮新增复核、修订、证据对应或比较 |

第二层再展开完整原文、五步过程、证据、版本、人工决定及未决项；技术 ID、JSON、任务包和迁移日志折叠。V2 工作库可作为深层追溯入口，不建议作为评审第一入口。最终方案已经将固定页面定位为一个稳定阅读路径，不做通用审校编辑器或全站改造。

“造舟于河”应重点形成立项—中期前后对照。由于它已经是立项阶段代表案例，本轮若只是重新展示已有五步内容，新增性很弱；只有产生新的原文对应、字形/表述核查、推理修订、人工决定及确认版本，才可表述为“深化既有代表案例”。

“平原之隰—譕臣”建议作为一组专题比较。比较内容限定在本批证据支持的范围，如注释、文义、字形、训义、押韵分别怎样参与判断，删掉某类材料后解释链条会失去什么。可以称“形成一组案例层面的方法观察”，不扩张成二王考据方法的一般规律。

合理的中期表述可以使用：

> 本阶段在既有原典定位、统一工作库和来源追踪基础上，选取代表案例开展考据过程结构化复核，对问题、依据、推理和结论之间的关系进行了逐项人工确认，并保存修订和未决事项。完成案例已形成可回溯的确认版本和固定展示集；进一步的底本、外部引文和专业判断核验按案例明确保留。

需要避免的表述包括：

* 将机器草稿或字段完整称为“已完成考据重建”；
* 将 `uncertain` 或页面标签称为“人工精校”；
* 将文件包成果表述为“已完成 V2 数据库人工审校”，除非实际写入并验证；
* 将王氏所引材料称为“项目已经独立查见原典”；
* 将几例比较概括成普遍的方法规律；
* 将 Agent 辅助本身作为质量等级；
* 将页面文字润色计算为新的学术成果。

最终审查认可的有效“包装”包括：缩小复核命题、复用旧案例产生真实深化、相邻案例形成小专题、文件包先行、固定快照、真实人机协作过程回放、同一确认稿派生页面/卡片/比较内容。这些策略共同原则是降低实际成本或增加真实证据，并保持边界可核查。

### 工时下降与停止条件

如果实际可投入时间降低，缩减遵循“保护完整链条，减少数量和技术便利”的原则。

约 **8—10 小时**时：保留“平原之隰—譕臣”两例；保留文件归档；形成一页比较和静态成果页；取消第四例、V2 接入、通用自动化、首页大改。这样仍具备“案例复核—方法比较—展示”的完整结构。

约 **4—6 小时**时：只完成一例，包含真实复核、版本链、固定展示和简短操作规则；明确未形成跨案例比较。

整体超时的删除顺序为：

**第四案例 → V2 接入及自动化便利 → 页面交互/全站改造 → 第三案例。**

任何情况下都应保留：真实人工判断、原文与版本对应、确认版本、至少一个稳定可展示成果。案例数量不得通过降低复核标准补齐。

目前没有发现必须先解决全库来源、全部 target_work、所有 candidate shell 或整个 V2 队列才能开始 pilot 的事实阻塞。唯一可能改变执行路线的核心变量，是负责人是否能够理解并确认第一例的关键论证重建。因此首例既是产出，也是生产可行性测试。

最终验收可以沿任一已完成案例倒查：

> **展示页面中的每个关键解释，能否回到确认版本；确认版本能否回到真实人工意见和修改依据；修改依据能否回到确定的王氏原文；下一例能否使用同一套文件、复核和展示规则继续处理。**

满足这条检查，即形成可信的中期增量。后续扩展只需按相同标准增加案例、逐步补齐已列明的独立核验事项，并在维护收益明确后再将成熟流程接入 V2。

### 执行基准

后续真正实施时，建议以以下约束作为固定工程基准：

| 项目    | 执行约束                                                       |
| ----- | ---------------------------------------------------------- |
| 基线    | 先核对当前 `main` 和工作区；`f738601` 仅为审查基线，若 HEAD 已变化则分析影响，不回退用户修改 |

# 附录：长期研究定位草案

> 状态：本附录是已纳入项目路线讨论、但仍需通过人工确认案例和对照实验验证的长期研究定位。它不替代前半部分的中期执行约束，也不把未来的 corpus、benchmark 或 agent 实验写成当前成果。

## 1. 项目定位

本项目的核心，不是建设一个古籍全文数据库，也不是给古籍知识库外挂一个大语言模型问答界面，而是构建一个**面向古籍考据任务的专用智能研究环境**。

整体可以概括为：

> **Corpus / Database + Retrieval + Agent Harness → Domain-Specific Agents**

其中，数据库负责保存和组织可检索、可追溯的研究材料；语料与 benchmark 将真实考据活动转化为可以被计算系统处理和评价的任务；检索系统负责从原典、引文和已有结构化材料中取得证据；agent harness 则规定模型能够访问哪些信息、调用哪些工具、按照什么过程完成任务以及如何核验结果。

项目最终关注的问题不是“模型是否会解释古文”，而是：

> **能否建立一个受原典、证据、出处和任务流程约束的计算环境，使通用大模型能够执行古籍考据中的检索、证据聚合、判断和结果核验。**

## 2. 长期研究的两个核心产物

长期研究路线可以收敛为两个彼此依赖、但能够分别评价的核心产物；中期先生产它们所需的人工确认案例，不要求本轮同时完成二者。

### 2.1 可追溯的古籍考据任务 corpus 与 benchmark

以高邮二王相关材料为主体，将考据活动转化为一组具有明确问题、答案和证据依据的任务。Corpus 是经过来源、版本和证据关系组织的材料与案例集合；benchmark 则是在 corpus 上冻结的任务、答案、证据、数据划分、指标和运行协议。

它不是单纯的 QA 数据集，也不是从现有条目批量生成的问题集合。一个有效案例至少应明确：

- 问题或待解决的考据命题；
- 对应原文及其出处；
- 支持答案所需的证据；
- 最终可核验的答案；
- 必要时标注证据角色、来源状态和任务难度。

任务应覆盖真实考据中不同程度的信息需求，例如：

- 单一原文定位；
- 跨 passage 检索；
- 多证据聚合；
- 同名、异文、简繁和书名歧义；
- 跨文献引证追踪；
- 多步证据链；
- 相互接近但作用不同的 hard negatives；
- 当前材料不足、应保留 unresolved 的案例。

因此，benchmark 的价值不在于题量本身，而在于能否把原本难以定量分析的考据过程转化为一个**具有真实检索难度、明确证据约束和可重复评价方式的 agentic research task**。

现有 V2 中的大量 machine drafts 可以作为案例发现和候选池，但不能直接等同于 benchmark gold。正式 benchmark 应建立在人工筛选和复核基础上。

### 2.2 面向考据任务的 domain-specific agents

第二个核心产物是一套针对上述任务设计的 agent 系统。

它与普通 RAG 或通用 browsing agent 的区别，不应主要建立在“用了几个 agent”上，而应建立在**任务环境、工具和行为约束的领域化**上。

一个典型过程可以表示为：

```
理解考据问题
    ↓
定位相关王氏条目
    ↓
检索原文与引用材料
    ↓
追踪证据来源
    ↓
判断不同证据的作用
    ↓
综合形成答案
    ↓
检查出处、遗漏与无依据推断
```

实现上可以由一个或多个 specialized agents 执行，例如：

- case / query interpretation；
- evidence retrieval；
- citation / source verification；
- evidence synthesis；
- answer verification。

是否采用 multi-agent 不是项目本身的理论前提。真正需要验证的是：

> **领域化 harness 和任务分工是否能够使 agent 比普通 RAG 或 generic search agent 更稳定地完成古籍考据任务。**

因此，`specific agents` 是项目的实现形态，`domain-specific agentic harness` 才是更稳定的技术定位。

## 3. Database 在项目中的位置

数据库仍然是项目的重要基础，但不需要将其强行包装成独立算法贡献。

它主要承担三个作用。

第一，作为 corpus 的组织和版本管理基础，保存 work、passage、case、evidence 等对象及其关系。

第二，作为 agent 的研究环境，使检索结果不只是无结构文本 chunk，而能够附带出处、材料类型、状态和已有关系。

第三，承担 provenance 和审计功能，使系统输出能够回到具体原文和证据，而不是只留下自然语言答案。

因此：

> **Database 是 agent environment 和 benchmark infrastructure，而不是项目唯一的研究对象。**

现有 `canonical / candidate / secondary / unresolved`、`machine / human / gold` 等状态仍然非常重要，因为它们规定了系统“知道什么”和“尚未确认什么”。

这些状态的作用首先是防止机器结果被误报为人工知识，其次才可能在后续实验中作为 retrieval 或 agent verification 的结构化信息使用。

## 4. RAG 在项目中的位置

本项目中的 RAG 不是最终产品，而是 agent 获取外部证据的基础能力。

普通 RAG 通常采用：

```
query → retrieve top-k chunks → generate
```

本项目更关注：

```
research question
    ↓
多轮查询与改写
    ↓
定位相关原文
    ↓
追踪引用与相关证据
    ↓
根据当前研究状态继续检索
    ↓
在证据约束下形成答案
```

因此需要关注的不只是一次检索的 Recall@k，还包括：

- agent 是否知道什么时候应该继续搜索；
- 是否能够根据已有结果重新构造 query；
- 是否找到完整证据链，而不是单个相关 passage；
- 是否被高词面相似但错误的材料误导；
- 是否能够识别“当前证据不足”。

从这个意义上说，RAG 是整个 agent 行为中的 **evidence acquisition layer**。

## 5. 项目不以什么为核心

为了避免后续开发不断发散，需要明确以下内容不构成项目的核心贡献。

### 网站功能不是核心

检索页、案例展示页、审核页、API 和在线部署主要用于数据维护、演示和研究操作。

它们可以是完整项目的一部分，但不能用功能数量代表研究进展。

### machine cases 数量不是核心

数千条机器抽取或机器生成案例主要代表自动化处理能力和候选规模。

它们不等于人工确认案例，更不等于 benchmark gold，也不能单独说明知识库质量。

### “接入大模型”不是核心

单纯增加聊天、问答、摘要或五步自动生成，不构成项目升级。

只有当模型处于明确任务和工具约束中，并能够被系统评价时，才属于 agent 研究的一部分。

### multi-agent 数量不是核心

更多 agent 不天然意味着更强。

如果一个 single agent 在相同工具和计算预算下可以达到相同性能，则多 agent 设计没有必要被包装为贡献。

### 不追求无限扩充古籍范围

当前没有必要同时建设段玉裁、俞樾、王先谦等大型平行知识库。

高邮二王材料已经足以形成主体 corpus。

后续若需要验证泛化，可以选择少量其他考据材料进行 transfer evaluation，而不是重新启动第二套大型数据工程。

## 6. 项目评价方式

项目最终应尽量从“展示系统能够做什么”转向“测量系统究竟做得怎样”。

评价至少分为两个层面。

### Retrieval / browsing ability

衡量 agent 是否取得了完成任务真正需要的证据，例如：

- Recall@k；
- MRR / nDCG；
- evidence recall；
- hard-negative error；
- source / scope violation；
- 检索步数和成本。

### End-task ability

衡量 agent 最终是否解决了考据问题，例如：

- answer accuracy；
- set / slot F1；
- evidence attribution accuracy；
- unsupported claim rate；
- evidence completeness；
- 人工复核后的正确率和修改量。

开放式长文本生成不是主要目标。

benchmark 应尽可能把最终答案设计为可核验、可拆分的结构，使系统性能能够稳定比较，而不是完全依赖另一个 LLM 对一段长答案进行主观评分。

## 7. 实验中的基本比较对象

未来评价系统时，应保持一条清晰的能力递进关系：

```
LLM only
    ↓
Vanilla RAG
    ↓
Generic Search Agent
    ↓
Domain-Specific Agent Harness
```

其中 Generic Search Agent 应获得与本项目 agent 尽量相同的基础模型、检索资源和工具能力，只取消古籍考据专用的任务流程和行为约束。

这样才能回答项目真正的问题：

> **当模型和材料相同时，专门针对古籍考据设计的 agent harness 是否带来了稳定收益？**

内部 ablation 进一步检查：

- 去掉领域化检索策略；
- 去掉问题分解或 planning；
- 去掉证据核验；
- 去掉 final verifier；
- 将 specialized agents 合并为 generic single agent。

项目应优先证明这些设计是否有效，而不是预设每个模块都必须被保留。

## 8. 当前阶段的理解

项目此前主要沿“高邮二王知识库构建及应用”的路线推进，因此已经积累了大量有价值的基础工作：

```
原始文献
→ passage/source registration
→ candidate
→ case/evidence
→ V2 database
→ retrieval
→ machine draft
→ review infrastructure
```

这些工作不需要推倒重来。

新的项目定位只是改变它们之间的主次关系：

```
过去：
文献 → 知识库 → 网站 / AI 应用

现在：
文献
  ↓
可追溯研究语料与数据库
  ↓
agentic benchmark / corpus
  ↓
retrieval environment
  ↓
domain-specific agents
  ↓
系统评价与人工复核
```

因此，前期数据库工程是新路线的基础设施，而不是一条已经废弃的路线。

## 9. 长期建设优先级

后续工作的优先级应逐渐从“增加数据总量”切换到“形成可评价任务”。

优先完成：

1. 明确 benchmark 的任务定义和案例格式；
2. 从现有材料中筛选并人工建立一批高质量 gold cases；
3. 定义不同 difficulty / task type；
4. 建立稳定的 retrieval evaluation；
5. 实现 generic agent baseline；
6. 固化 domain-specific harness；
7. 做 agent-level baseline 和 ablation；
8. 分析失败案例，并据此决定是否需要继续修改 database、retrieval 或 agent workflow。

新增网站功能、扩大 machine case 数量和继续增加未经核验的外部材料，应服从上述目标，而不是成为独立进度指标。

## 10. 最终定调

本项目可以继续使用“高邮二王知识库”作为历史和项目名称，但研究内核应逐渐统一为：

> **以高邮二王考据材料为基础，构建具有明确答案和证据链的古籍考据任务 corpus，并以结构化数据库和检索系统作为研究环境，开发和评价能够自主检索、追踪证据、综合判断并核验结果的 domain-specific agents。**

更简洁地说：

> **我们不是在让 AI“懂古文”，而是在构建一个古籍考据 agent 能够被训练、运行、约束和评价的研究环境。**

数据库提供环境，corpus 定义问题，RAG 提供证据，harness 规定行为，agent 执行任务，benchmark 判断它究竟做得好不好。

这几部分共同构成项目，而不是其中任何一个单独模块。
